# 装得清当前 Web 端角色页面审计

- 日期：2026-10-21
- 范围：企业负责人、设计师、财务
- 环境：本地 dev（Web `127.0.0.1:8080`，后端 `127.0.0.1:8090`）
- 方式：真实账号登录 + 真实页面只读访问 + DOM/操作结构采集 + 现有注册检查
- 状态：审计记录，不代表生产验收

## 一、审计结论

当前 Web 端已经不是空壳，核心业务页面已经有真实数据、真实动作、空状态和部分对象工作空间。页面系统、动作、状态、表单、权限等注册检查全部通过。

但当前主要问题不是“有没有页面”，而是：

1. **角色首页仍然偏入口目录，不是当天经营/工作判断**；
2. **同一实体在不同角色页面中的信息优先级不稳定**；
3. **摘要计数与目标队列存在不一致，影响用户信任**；
4. **技术编号和手机号出现频率偏高，业务主信息不够收敛**；
5. **同一产品里同时存在三栏对象工作面、表格、指标看板、卡片目录四种语法**；
6. **动作密度过高，部分页面缺少“唯一主行动”**；
7. **实体记忆和角色记忆没有形成统一识别系统**。

一句话判断：

> 当前页面“能用”，但还没有达到“用户打开就知道今天做什么、点进去就能完成、做完知道谁接棒”的作业型体验。

## 四、企业负责人角色分析

### 4.1 当前做得好的地方

- 角色身份和数据范围明确：“企业负责人 · 全公司”可见。
- 首页明确提示“不显示 0、不用空队列填充首页”，事实口径意识较强。
- 风险队列、应收、应付、台账都有真实数据，不是静态占位。
- 项目、报价、合同页面能够看到真实金额、状态、客户、房屋和下游关系。
- 财务页面明确区分应收、已收、待收、现金流、账户余额和成本完整性。
- 关键数据缺失时有“成本未完整”“暂无基期”等提示，没有用 0 伪装利润。

### 4.2 主要差距

1. **首页是场景目录，不是今天的工作判断**
   - 当前 `/workbench` 同时展示 3 张重点卡和 23 个场景入口。
   - 页面标题是“业务工作台”，没有把“今天最影响经营结果的三件事”推到唯一主视觉。
   - 与目标设计“先看 3 个经营判断，再展开全部场景”存在明显差距。

2. **BOSS 视角容易进入设计师页面**
   - BOSS 打开 `/designer/customers` 后，页面标题仍是“待我设计”，而不是 BOSS 的经营视角。
   - 角色身份在 shell 中存在，但页面主标题没有延续角色记忆。
   - 需要明确“能力超集”和“当前岗位视角”的区别，避免 BOSS 误以为自己在代替设计师操作。

3. **风险队列需要“经营解释”**
   - 风险表有对象、金额、责任人、时效和动作，但没有统一展示“为什么这是风险、现在不处理的后果”。
   - 认领、指派、处置、关闭四个动作并列，缺少一个唯一主行动和升级路径。

4. **实体信息优先级不稳定**
   - 报价、合同、项目页面同时出现客户手机号、报价号、合同号、项目号、金额、状态和多个业务动作。
   - 没有统一 P0/P1/P2 规则；编号和技术字段容易抢占金额、风险和下一步。

## 五、设计师角色分析

### 5.1 当前做得好的地方

- 设计师有独立角色工作台和菜单，角色识别明显。
- 待我设计页面是三栏结构：客户队列、当前客户房屋、方案与下一步，已经接近对象工作空间。
- 量房、设计、报价、合同都有独立工作台，且明确“不默认打开第一条”或“选择后再进入”。
- 设计方案页说明了量房输入、方案、客户诉求和报价之间的上下游关系。
- 项目工地页明确设计师只进入合法工作区，不代替项目经理推进施工节点。
- 报价详情页包含金额、版本、客户决策、方案、PDF/PPT、跟进和交接。

### 5.2 主要差距

1. **首页摘要与量房队列不一致**
   - 设计师工作台显示“2 套待处理 · 量房中 2”。
   - `/designer/measure` 显示“0 个当前任务”，全部、逾期、今天、已预约、待预约、待交设计均为 0。
   - 这是一条 P0 信任问题：用户会怀疑“系统到底有没有任务”。
   - 需要核对首页统计口径和量房工作台队列的数据源，明确是否“量房中”不计入任务队列，或修复查询条件。

2. **客户与设计页面承担了过多职责**
   - 页面同时处理客户、房屋、量房、方案、诉求、跟进和报价交接。
   - 当前 21 个按钮、1 个搜索框、多个动作入口，主行动不够稳定。
   - 需要区分“客户经营”“房屋设计”“方案工作区”三个工作面，不能靠同一页承载全部。

3. **信息密度过高**
   - 客户手机号完整展示，报价号、方案号和项目号频繁出现。
   - 设计页展示量房、面积、预算、负责人、设计师、画像、诉求、方案、跟进和多个动作。
   - 需要按角色分出 P0/P1/P2，编号只作为追溯信息。

4. **报价/合同页面有“数据展示完整”，但“下一步动作不唯一”**
   - 报价详情有打开设计、进入报价、生成 PPT、生成 PDF、记录诉求、交接合同、查看下一项等多个动作。
   - 页面文字说明多，用户需要阅读后才能判断下一步。

5. **项目与设计之间的交接仍有割裂**
   - 项目工地页是项目列表 + 选择后工作区，设计页是客户 + 房屋工作区。
   - 两者使用不同的身份条和动作语法，设计师需要在两套页面逻辑之间切换。

## 六、财务角色分析

### 6.1 当前做得好的地方

- 财务工作台把现金余额、待收工程款、本月回款、待付账款、现金流、应收逾期、应付到期和项目经营结果放在一屏。
- 财务页面明确区分“现金流不等于利润”“成本未完整不显示利润”。
- 应收、应付、收款、付款、台账、项目账本形成从合同到资金事实的连续链路。
- 凭证页面明确指出“业务凭证不等于法定会计凭证”，边界清晰。
- 删除手工流水要求填写原因，有风险留痕意识。
- 薪酬工作台有周期、待发、待发布工资条、考勤和入口，任务结构清楚。
- 空状态、筛选、口径说明总体较完整。

### 6.2 主要差距

1. **工作台偏指标看板，不是行动队列**
   - 首屏先给 6 个指标、资金闭环、逾期催收、优先付款、口径说明、最近台账。
   - “今天先处理哪三笔”不够明确；用户需要自己从多个表和指标中推断。
   - 财务是高密度角色，但高密度不等于把所有表都堆在首屏。

2. **应收/应付行级动作重复**
   - 应收 25 条、50 个按钮；应付 35 笔、50 个按钮。
   - 每行重复“登记收款 / 项目账本”或“安排付款 / 项目账本”。
   - 需要对象级抽屉和批量处置，减少列表行内动作。

3. **摘要金额与列表口径需要核对**
   - 财务工作台显示“待付账款 ¥1,040.00”。
   - `/finance/payables` 显示“待付金额 ¥1,140.00”。
   - 二者可能存在范围或类型差异，但页面没有明确区分口径。
   - 这是 P0 数据信任问题，必须先确认口径，再谈视觉优化。

4. **凭证模板页复杂度过高**
   - 39 个输入、44 个按钮。
   - 版式模板、字段配置、模板库、预览和复制编辑集中在一页。
   - 需要拆成“模板库 → 模板详情 → 编辑/预览”的渐进流程。

5. **表格页缺少统一对象身份条**
   - 应收、应付、台账都是“汇总数字 + 表格 + 行操作”。
   - 进入某个项目或单据后，才出现更完整的对象上下文。
   - 与设计师三栏对象工作面不一致，用户需要切换认知模式。

- `quoteFinalAcceptanceRate` 当前实现与正式口径不一致，不得作为正式经营指标对外。
- `monthReceiptAmount` 当前实现与正式口径存在差异，需补充差异说明。

## 九、优先整改建议

### P0：先修信任与任务闭环

1. 核对并修复设计师首页“待我量房 2”与量房工作台“0 个当前任务”的不一致。
2. 核对财务首页“待付账款 ¥1,040”与应付页面“待付金额 ¥1,140”的口径差异。
3. BOSS 首页从 23 个场景目录收敛为：
   - 3 个今日经营判断；
   - 3 个进入对象的主行动；
   - 其余场景折叠到“全部场景”。
4. 客户、报价、合同、项目页面统一对象身份条和 P0 字段；完整编号进入 P2 折叠区。
5. 客户手机号按角色和数据范围处理，避免默认完整展示。
6. 所有对象完成后显示新状态、下游对象和接棒人。

### P1：统一页面家族与动作层级

1. 定义并接入 7 类页面模板：
   - 角色工作台 / 入站队列；
   - 对象工作空间；
   - 表单与单据；
   - 审批与安全门；
   - 账本与报表；
   - 业主只读与确认；
   - 系统状态页。
2. 应收、应付、台账的重复行操作改为“对象抽屉 + 批量动作”。
3. 设计师客户/房屋/方案页拆分工作面，减少一页承担全部职责。
4. 凭证模板页拆成模板库、模板详情、编辑/预览三个阶段。
5. 统一空、错、权限、冲突、部分失败和回读状态。

### P2：产品记忆与视觉一致

1. 为客户、房屋、设计方案、报价、合同、增减项、材料、应收、应付、台账、验收、项目建立统一实体徽章和对象指纹头。
2. 建立角色徽章，但不让角色色覆盖页面主色。
3. 空状态、首次使用、完成反馈使用友好背景；金额、账本、审批和合同正文不使用干扰阅读的背景。
4. 统一业务动词：跟进、量房、设计、报价、签约、生效、变更、下单、到场、验收、整改、复验。
5. 统一页面标题、面包屑和角色名称，避免“客户与设计”与“待我设计”混用。

## 十一、结论

当前装得清 Web 端已经具备真实业务页面、真实数据和部分对象工作空间，不能简单评价为“概念化”或“没有用”。  
真正的差距在于：

> **页面已经覆盖业务，但还没有把角色、实体、信息优先级、动作层级和完成交接统一成一套可记忆、可执行的产品体验。**

下一步不应先加页面，而应先修 P0 的“任务与口径一致性”，再用对象卡片、页面家族和实体记忆系统统一现有页面。
