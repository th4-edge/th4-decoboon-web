## XA-20261011-001 ｜ BUG ｜ P1 ｜ 方案推进后前端状态被响应覆盖，「生成报价」被禁用

- 真实用户目标：设计师完成 2 个设计分项后，点「完成设计，进入待谈单」，接着生成客户报价。
- 最小复现：设计工作区（有分项，如 拆除--拆除门窗 2 项、木门 3 樘，合计 ¥3,297.60）→ 点「完成设计，进入待谈单」→ 弹窗「下一步：生成报价」。
- 期望：弹窗内显示「方案已具备 2 个设计分项」，「生成报价」可用。
- 实际：弹窗与页面摘要显示「方案已具备 **0** 个设计分项」、方案金额 ¥0，`生成报价` 按钮 **disabled**；**刷新页面后恢复为 2 项 / ¥3,297.60 且按钮可用**。
- 影响角色：设计师（阻断报价生成，只能靠刷新绕过）。
- 分辨率：1440x900（1024/1280 同源逻辑）。
- 证据：截图 `017-design-complete-attempt`、`019-after-refresh-items-restored`；网络 `POST /api/design/scheme/build => 200`，响应体仅含 `designId/no/name/owner/customer/property/version/style/status/area/layout`（**无 spaces/items/itemCount**）；DB `db_design_item` 该方案 2 行、`db_design.area=27.40`。
- 严重度/置信度：P1 / 高（页面证据 + 请求响应 + 刷新恢复三证）。
- 建议：`advance()` 后不要用 build 响应整体替换 `scheme`，应重新拉取 `design/scheme/info`（或让 build 响应包含 spaces/items/计数投影）。
- 验收标准：推进后摘要与分项数/金额保持一致，`生成报价` 立即可用，无刷新需求。

## XA-20261011-003 ｜ GAP/BIZ ｜ P1 ｜ 报价项目库公式是中文口径，与设计分项专业变量公式体系不统一

- 真实用户目标：设计师直接从企业报价项目库选分项，工程量随区域实测值自动重算。
- 最小复现：从报价项目库选「拆除--拆除门窗」「木门--实木复合烤漆门/无漆门」加入方案 → 查看分项公式与区域工程量联动。
- 期望：库内分项公式使用专业变量（A/P/CP/WP、L/W 已停用）或明确「不随区域实测值重算」的口径。
- 实际：`catalog_item.formula` 全库为中文口径（`(人工单价) × 工程量`、`(材料单价 + 人工单价) × 工程量`），进入设计分项后原样落库；因此这些分项在区域/全屋重算时被判为「非专业变量公式」→ 按 `DEC-063` 降级为**不参与重算**（保留原工程量），无法参与 A 待补、SUM(A) 全屋聚合等能力。
- 影响角色：设计师、店长、财务（同一报价存在「库内公式」与「专业变量公式」两套口径，工程量自动化能力被削弱）。
- 证据：DB `catalog_item.formula`（679 项）、`db_design_item.formula='(人工单价) × 工程量'`；页面「公式待修订」标记实现（`DEC-063`）。
- 严重度/置信度：P1 / 高（口径级，需业务裁决）。
- 建议：由业务智能体裁决「库内公式改为专业变量口径」或「库内分项只按固定工程量、不参与重算」并在 UI 明确标注；避免两套公式体系长期并存。
- 验收标准：任一库内分项的公式口径在全链（设计→报价）唯一且可解释。

## XA-20261011-004 ｜ BIZ ｜ P1 ｜ 单设计师角色无法闭环到交房（合同/验收/交房均需其他角色）

- 真实用户目标：设计师把客户从录入推进到交房。
- 最小复现：报价「提交客户确认」后，依次访问「待我签约」「项目工地」「阶段验收工作区」。
- 期望：至少能看到清晰的下一责任人/下一动作与通知。
- 实际：① 待我签约仅有「生成谈单 PPT / 生成报价 PDF / 生成合同 PDF / 查看项目 / 报价详情」等只读或导出动作，无「发起合同 / 确认生效」；② 我新建的方案无合同、无项目（DB：contracts=0、projects=0）；③ 阶段验收工作区文案明确「项目经理或具备项目参与资格的设计师可提交阶段验收……确认或驳回必须由业主本人执行，员工不得代录」，且对本设计师 `提交阶段验收` 为 **disabled**（非该项目参与人）。
- 影响角色：设计师（单角色不可闭环）；店长/项目经理/业主（必须介入）。
- 证据：截图 `022-designer-contract`、`025-designer-acceptance-view`；页面文案；DB 计数。
- 严重度/置信度：P1 / 高（这是**业务设计边界而非缺陷**，但当前报价提交后没有把「下一责任人」显式交给设计师，容易造成流程停在原地）。
- 建议：报价提交后在设计师端明确提示「下一步由谁在哪个入口登记客户接受并发起合同」，并提供到该角色工作台的说明/通知，而不是让设计师停在只读页面。
- 验收标准：报价提交后，设计师端可读到明确的下一责任人、入口与预计动作。
