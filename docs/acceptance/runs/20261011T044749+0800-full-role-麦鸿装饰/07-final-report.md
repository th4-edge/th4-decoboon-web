# 装得清 Web 端沉浸式审计报告（设计师角色 · 客户到交房闭环尝试）

日期：2026-10-11 ｜ 模式：full-role（角色范围限定设计师）｜ 企业：昭青装饰（本地 dev，com_id 1790000000000000001）
环境：Web `http://127.0.0.1:8080`（commit `c53eb0d`）+ 后端 `http://127.0.0.1:8090/api`（commit `1d6f131`，迁移 106/107）

## 1. 结论摘要

1. **设计师在 Web 上可以独立跑通「客户录入 → 房屋 → 量房 → 设计（区域实测 + 项目库分项）→ 报价草稿 → 提交客户确认」**，且金额口径可逐项核对：分项金额 = 单价 × 工程量；报价 = 小计 × 1.05（5% 税）；方案面积 = 区域实测面积合计。
2. **报价项目库与真实报价单同源**：拆除门窗 ¥28.80、地砖铺贴 ¥71.30、木门 ¥1,080 与附件一致，既有报价 Q1790922936204 ¥126,507.41 ≈ 附件含税共计 ¥126,507.42；说明「用 Web 复现真实报价单」是可验证的价值。
3. **从报价提交到交房不可由设计师闭环**：合同发起/生效、验收提交（非参与人）、业主确认（必须业主本人）均需其他角色；当前报价提交后**没有把下一责任人显式交给设计师**，流程体验上「停在原地」。
4. **发现 1 个 P1 前端状态缺陷（XA-001）**：完成设计后前端用 build 响应覆盖方案，导致 0 分项/¥0/按钮禁用，刷新才恢复。
5. **发现 1 个 P1 口径级问题（XA-003）**：报价项目库公式为中文口径，与设计分项专业变量公式体系不统一，库内分项在设计重算中被降级为「不参与重算」。

## 2. PASS / FAIL / BLOCKED / NOT_TESTED

- **PASS（10）**：登录与身份、客户录入、房屋建档、量房预约、量房结论（含照片必填）、新建方案、区域实测录入、项目库选分项与金额计算、报价生成、报价提交客户确认。
- **FAIL（缺陷）**：XA-001（P1）、XA-002（P2）、XA-005（P2）、XA-006（P2）、XA-007（P3）、XA-009（P3）、XA-010（P3）。
- **BLOCKED（4）**：合同发起/生效、项目立项（新方案无项目）、阶段验收提交、业主确认/交房。
- **NOT_TESTED**：其他角色工作台、App 端对照、真机/弱网、Excel/PDF 导出内容正确性、批量改价。

## 3. 最值得保留的能力

- 主行动驱动的主链（每一步只有一个「下一步」，跨页面状态文案同口径）。
- 报价项目库 → 设计分项 → 报价的「选完即算」闭环，且与真实报价单同源。
- 区域实测面积/周长作为工程量基数的口径（本次实测 15.60/11.80 → 方案面积 27.40 正确汇总）。
- 宽屏三档无横向溢出（4 个关键页面 × 1440/1280/1024）。

## 4. 最大协同断点与整改顺序建议

1. **P1 XA-001**：修复完成设计后的状态覆盖（改为重新拉取 info 或让 build 返回完整投影）——直接阻断报价生成，优先修。
2. **P1 XA-003**：裁定报价项目库公式口径（专业变量 or 固定工程量），消除两套公式体系。
3. **P1 XA-004**：报价提交后给出下一责任人/入口（客户接受与合同由谁登记），并在设计师端提供可执行提示。
4. **P2 XA-002 / XA-005 / XA-006**：抽屉摘要复用服务端投影；量房诉求与设计诉求同源；区域批量录入。
5. **P3 XA-007 / XA-009 / XA-010**：下拉可访问性、Web 自助密码、预算偏差提示。

## 7. 多角色 Web 推进结果（2026-10-11 05:18–05:30，用户已授权）

- 目标「客户录入 → 交房」在 Web 端**不可达**，卡点依次为：客户接受报价（无入口）→ 合同确认签约（无入口、店长被守卫拒绝）→ 确认生效/立项（无入口）→ 指派项目经理（无入口）→ 开工（枚举缺 NotApplicable，400）→ 业主确认（必须小程序授权会话）。
- 其中 4 步已用接口模拟推进并标注 `API_SIMULATED`，以便验证后续链路；Web 端真实 PASS 的动作只有：设计师发起合同、PM 开始任务/完成任务上传证据、PM 提交阶段验收（形成第 1 轮 Pending）。
- 新增缺陷 8 条（XA-012…XA-019），修复顺序与验收标准见 `14-多角色推进与研发修复交付单-20261011.md`。
