## 二、缺陷（研发修复交付）

### XA-20261011-012 ｜ BUG/GAP ｜ P1 ｜ Web 端没有任何「确认合同签约 / 确认生效」入口
- 用户目标：企业负责人或店长在 Web「待我签约」完成复核，签约后生效并生成项目。
- 复现：负责人登录 → `/designer/contract` → 选中待企业确认合同 → 只有按钮「待企业确认签约」且 **disabled**。
- 实际：前端只调用 `project/contract/save`（发起），全站**没有** `project/contract/update` 调用；负责人/店长被指派的唯一动作在 Web 无入口。
- 期望：负责人/店长在该页有「确认签约（填签约价/签约日期）」与「确认生效（生成项目）」两个动作。
- 影响角色：企业负责人、店长（合同主链直接断在 Web）。
- 证据：verify-019；`src/domains/contract/api.ts`（仅 save）；后端 `ProjectAccessContext.requireContractConfirmer/requireProjectCreator`（Boss+StoreManager）。
- 严重度/置信度：P1 / 高。
- 验收标准：负责人/店长在 Web 完成「确认签约 → 确认生效」，合同状态与项目生成事实与后端一致，且刷新后不丢。

### XA-20261011-013 ｜ BUG ｜ P1 ｜ 店长工作台入口指向 `/designer/*`，被路由守卫拒绝
- 复现：店长登录 → 工作台「待我签约 / 待我谈单」→ 点击（href `/designer/contract`、`/designer/quotes`）→ 页面 `/forbidden`「无权访问该页面」。
- 原因：`src/core/router/index.ts:147` 的 `/designer` 路由组 `meta.roles = ['Designer','Boss']`，缺 `StoreManager`；而店长工作台 `workbenchConfig` 把这两项指向该组。
- 影响角色：店长（被产品指名负责合同确认的角色，Web 上完全不可用）。
- 证据：verify-017（`/forbidden`）+ href 抓取 + 路由源码。
- 验收标准：店长可打开「待我签约 / 待我谈单」并完成合法动作；越权对象仍应被服务端拒绝（前端不是唯一门禁）。

### XA-20261011-014 ｜ BUG ｜ P1 ｜ 前端缺 `NotApplicable` 枚举，项目经理「开启阶段」必然失败且无路可走
- 复现：项目经理打开新项目 → 点「开启阶段」→ 400「该阶段已判定为本项不涉及，请先撤销判定再开工」。
- 原因：后端阶段状态 `NotApplicable`（本项不涉及）在前端 `src/domains/project/api.ts` 的 `STAGE_STATUS` 无映射 → `?? 'todo'` 渲染成「待开始」，工作台据此认为可开工并发起请求。
- 附加：撤销「本项不涉及」仅在 App（`ProjectContext` 注释「PM 可在 App 复核撤销」），Web 工作台与验收页都没有撤销入口，也不能对其它阶段「开工」。
- 影响角色：项目经理（项目无法正常开工，主链卡死）。
- 证据：verify-025；`raw/network/verify-pm-open-stage-bodies.txt`（请求体 `{"stageId":"…","status":"Doing"}`，响应 400）；DB 阶段 `NotApplicable`。
- 验收标准：Web 正确显示「本项不涉及」，工作台不提供无效主行动；如需复工，Web 提供撤销入口并二次确认。

### XA-20261011-015 ｜ DATA ｜ P2 ｜ 合同生效自动生成的阶段计划不合理
- 事实：新项目阶段计划 = 开工交底 `NotApplicable`(2026-10-20→10-30)、拆除改造(10-31→2027-01-14，权重 100%)、水电/泥瓦/木作/油漆/安装/竣工各 1 天。
- 影响：工期与权重失真，PM 无法据此排产；同一批既有项目全部阶段为「待开始」，口径不一致。
- 证据：`raw/sql/verify-stage-plan-and-acceptance.txt`、verify-022。
- 验收标准：阶段计划按合同施工行与标准工期合理分摊；被系统判定不涉及的阶段不应吞掉主链起点。

### XA-20261011-016 ｜ BUG/GAP ｜ P1 ｜ 项目生成后无人负责：无项目经理且 Web 无指派入口
- 事实：合同生效生成的项目 `manager_id = NULL`；Web 全站无 `project/project/update` 调用（`managerId` 仅用于展示与筛选）。
- 影响：项目经理工作台按数据范围过滤，新项目对 PM 完全不可见（本次用接口模拟指派后才可见）。
- 证据：`raw/sql/verify-project-generation.txt`、verify-021/022；前端 `src/domains/project/api.ts` 导出清单无更新接口。
- 验收标准：合同生效生成项目时必须确定项目经理（或负责人/店长在 Web 上有指派入口并留痕）。

### XA-20261011-017 ｜ GAP/SEC ｜ P1 ｜ 「客户接受报价」Web 无入口，但接口允许员工直接置为已接受
- 事实：谈单页对「待客户确认」只显示禁用主行动「等待客户决策」，下一接棒写「客户（决策）」；而 `quote/update(status=Accepted)` 对设计师返回 **200**（本次实测），即员工可代客户确认接受。
- 风险：①Web 主链在「客户接受」处断裂；②代客户确认无客户/业主授权凭证与留痕要求，口径需业务智能体裁决。
- 证据：verify-003/005（页面）+ 接口调用记录（不含凭证）。
- 验收标准：明确「谁可以登记客户接受、需要什么凭证、如何留痕」，并在 Web 提供与口径一致的入口。

### XA-20261011-018 ｜ UX ｜ P3 ｜ 同一页面自相矛盾的动作/文案
- 事实：PM 工作台同时显示「任务/阶段动作注册未冻结，当前只读」与实际可点击动作；阶段验收提示写「施工任务完成后，**设计师**可提交验收并上传现场证据」，实际提交人是项目经理。
- 证据：verify-022/031。
- 验收标准：文案与实际能力一致，或改为按角色渲染。

### XA-20261011-019 ｜ BUG ｜ P2 ｜ 合同发起抽屉同样显示「待补充/待确认」（XA-002 第 3 处复现）
- 复现：设计师「发起合同」抽屉 → 客户摘要「电话待补充 · 阶段待确认 · 负责人待确认」，房屋摘要「面积待补充 · 户型待补充 · 状态待确认」，同页客户 360 数据完整。
- 证据：verify-013。
- 验收标准：与 XA-002 合并修复（抽屉摘要复用服务端投影）。

## 三、修复顺序建议（研发）

1. **XA-012 + XA-013**：把「确认签约 / 确认生效」在 Web 落地，并修正店长路由权限（同为 P1 主链阻断，一起改一起回归）。
2. **XA-014 + XA-015**：前端补 `NotApplicable` 枚举与撤销入口；修正阶段计划生成。
3. **XA-016**：合同生效项目必须确定项目经理 + Web 指派入口。
4. **XA-017**：先由业务智能体裁决代客户接受口径，再决定是否补 Web 入口。
5. **XA-019 / XA-018 / XA-002**：抽屉摘要同源、文案与角色一致。

## 四、边界与阻塞（不是缺陷）

- 业主确认（阶段验收/交房）必须由业主本人小程序授权会话执行，员工侧接口一致返回 403；本地 Web 无法完成 → `BLOCKED_OWNER_SESSION`。
- 因此「竣工保洁验收 → 交房」在 Web 单端不可达：即使修复上述缺陷，Web 也只能到「提交验收（待业主确认）」。
