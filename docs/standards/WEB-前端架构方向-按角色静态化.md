# Web 前端架构方向：按角色静态化（路由 + 菜单）

> 状态：**已全部落地（2026-10-11）**：落法取 **A**（按角色装载静态路由集合），注册表文件**已删除**（`GAP-WEB-021`）。
> 落地结果：`src/core/router/index.ts` 557 行 → 118 行；新增 `src/roles/routes.ts`（按角色静态路由集合）与 `src/roles/workbenchHome.ts`（按角色首页卡片）；删除 `src/domains/workbench/navigation.ts` 与 `docs/standards/workbench-navigation.json`；门禁改写为校验静态源。

---

## 1. 用户裁决原文（2026-10-11）

> 我们目前在重构前端 Web，**不需要逻辑注册表的限制**，因为每个角色对应的菜单不同，即使同一页面，因为角色不同，页面逻辑展示都会有差异。
> 所以**每个角色都沉淀出静态路由、静态菜单，不参与任何逻辑判断**。

## 2. 由此确定的规则

1. **每个角色有自己的静态路由集合 + 静态菜单**；两者都是**声明式数据**，不是运行时推导结果。
2. **同一页面组件可以被多角色共用**，但要在**各角色自己的路由集合里各自声明**；页面内部再按角色渲染差异（属页面逻辑，不是路由准入逻辑）。
3. **注册表 `workbench-navigation.json` 已删除**（用户 2026-10-11 追加裁决「注册表文件要删」）。其**业务条款**归档为 `docs/standards/WEB-工作台契约条款.md`（人读，机器不读）；机器契约改为校验三份静态源。
4. **删除运行时角色判断**，包括（现状清单）：
   - `meta.roles` 逐路由判断（24 处）与守卫里的 `to.meta.roles.includes(session.role)`；
   - 区域判断 `isDesignerArea` / `isFinanceArea` 及其**临时白名单** `STORE_MANAGER_DESIGNER_PATHS`（2026-10-11 为店长打的补丁）；
   - `homePathForRole` 分支式重定向；
   - `workbenchesForRole()` 按注册表 `roles` 过滤、`resolveWorkbenchLink()` 的按角色映射。

## 3. 待确认：前端是否保留"按角色装载路由"

| 方案 | 做法 | 结果 |
| --- | --- | --- |
| **A（已采用 ✅）** | 启动/登录后按当前角色**只装载该角色的静态路由集合**（`routesByRole[role]`，查表 = 数据分离，不是 if/白名单） | 越权 URL 落 `/forbidden`（属别角色已知路径）或 404；零条件分支；Boss 切岗位视角时重装集合 |
| **B（严格字面）** | 全局一套路由、**完全不判断角色** | 任何员工可用 URL 打开其他角色的**页面外壳**（数据仍由后端拦截）；需接受"越权外壳可见" |

**两者都不改变一条既定事实**：真正的权限与数据范围兜底在**服务端**（Provider 层角色校验 + 数据范围裁剪）。

## 4. 落地顺序（方案确定后执行）

1. 建 `src/roles/routes/`：按角色拆分 70 条路由的归属声明（共享页面在多角色集合中各声明一次）；

3. 首页入口卡片改为**每角色静态清单**（不再按注册表 `roles` 过滤 + 映射解析）；
4. 注册表运行时退场 → **已按裁决删除文件**；门禁改为校验三份静态源（`check:workbenches` / `check:workspaces`）。
