# 装得清 Web 端建设核心思路

> 状态：**待确认**（确认后作为 Web 开发规范的第一性依据）
> 确立日期：2026-10-06
> 适用范围：`th4-decoboon-web` 全部角色工作台、对象工作空间、列表、表单、单据
> 上位事实源：业务对象、状态、权限、金额/成本/利润口径只以全局 `zhuangdeqing-business` 为准；本文不新增、不修改任何业务口径

---

## 一、我们为什么要重建 Web 端

装得清已经有 App。重建 Web 不是为了"再做一个端"，而是为了：

> **让不同角色用更适合电脑的方式，更便捷、更高效地开展装企业务工作，并与 App 形成逻辑互动与互补。**

拆开说是三件事：

1. **更好的交互**——电脑有更大的操作区域、键鼠、并行窗口，App 的触屏交互迁移过来会低效。
2. **更便捷的服务**——同一件业务在 Web 上应当比 App 更省步骤，而不是把 App 的页面放大。
3. **更有效的经营**——老板与管理者要在 Web 上看到经营结果、风险与异常，而不是浏览业务台账。

**判定标准**：如果某个页面在 Web 上做不完 App 能做的事，或做完比 App 更慢，这个页面就没有存在的价值。

## 二、四条公理（不可协商）

### A1 · App 为准

**App 端的交互、业务、规则、UI 是产品级成果，已经过实际业务使用者认可。**
因此：

- 业务逻辑闭环以 App 为准；Web 不得自创业务规则、状态流转、完成口径。
- 后端逻辑以 App 为准；同一业务事实，两端必须得到同一结论。
- 状态名、动作名、角色归属、权限结论，两端必须一致。

**冲突处理**：Web 与 App 结论不一致时，以 App 为准，并在 Web 侧建立 `DEF-*` 登记，
不得在 Web 单端改文案或自行"修正"。

### A2 · 不新开 API

- **Web 不允许开辟新的后端 API。** 所有请求必须消费 App 已在使用的既有 Provider。
- Web 需要的数据如果 App 已有接口能取到，就用那个接口；取不到时，
  **不是"加一个 Web 专用接口"**，而是回到业务与产品层判断：
  App 是否也需要？是否需要修改 App 契约？——这属于 App 与后端的变更决策，不属于 Web 范围。
- 禁止任何形式的 Web 专属路由、Web 专属字段、Web 专属状态。

**核验方式**：每个 Web 页面用到的 Provider 路由，必须能指出 App 中的对应调用点。

### A3 · 认同 App 的 UI 与交互，但不复刻

我们认可 App 的页面 UI 与交互设计。但 Web 是**电脑 + 键鼠 + 大屏**，操作习惯不同，所以：

- **不允许**把 App 页面等比放大搬过来。
- **必须**利用大屏与键鼠做提升：批量、对账、并行、键盘操作、多列信息、跨对象比较、导出、排期。

一句话：**业务语义跟 App 走，交互形态按电脑重新设计。**

### A4 · 禁止功能菜单堆砌与 CRUD 页面

**这是本规范要解决的核心问题。**

- **绝对不允许**做成传统 Web 的"功能菜单堆砌"——左侧一长串菜单，每个菜单一张表。
- **绝对不允许**出现"以后端模型概念形成的 CURD 页面"——即因为后端有 `Customer` 实体，
  就做一个"客户管理"列表 + 新增/编辑/删除表单。

判断一段功能是否违规，只问一句：

> 这个页面是**从角色和业务场景推出来的**，还是**从后端数据表推出来的**？

从数据表推出来的一律不合格。

## 三、Web 与 App 的关系

### 3.1 必须一致（业务语义层）

| 维度 | 要求 |
| --- | --- |
| 业务对象与状态 | 同一事实、同一状态名、同一含义 |
| 动作可达性 | App 在某状态下能做的动作，Web 同角色同状态必须可达，且不需要记隐藏路径 |
| 角色与权限 | 谁能做谁不能做，两端一致；服务端强制校验 |
| 数据范围 | Company / Store / Team / Self 与项目参与关系一致 |
| 金额与成本 | 同一口径、同一快照、同一完整性判断 |
| 完成条件 | 「完成」由同一领域事实推导，两端一致 |

### 3.2 必须不同（交互层）

| Web 应当更强的地方 | 说明 |
| --- | --- |
| 批量处理 | 一次处理多条同质业务（如批量套模板、批量排期） |
| 对账与核对 | 多列并排、可比较、可标记差异 |
| 并行与上下文保持 | 不丢失列表筛选、不打断上下文 |
| 键盘效率 | 常用动作可纯键盘完成 |
| 信息密度 | 一屏承载更多有效事实，而不是更多卡片 |
| 跨对象比较 | 多客户/多项目/多报价横向对比 |
| 正式输出 | 单据、合同、报表的打印与导出 |
| 经营分析 | 结论先行、风险优先、可下钻 |

### 3.3 分工原则

- **现场与移动场景留在 App**：拍照留证、现场确认、移动审批、即时沟通。
- **坐在电脑前的工作放在 Web**：批量维护、对账、排期、经营分析、正式单据。
- 同一业务事实两端都可推进时，Web 必须让人更省事，而不是更多点击。

## 四、页面从哪里来（场景驱动，不是模型驱动）

### 4.1 页面生成公式

```text
页面 = 角色 × 场景 × 业务对象 × 对象状态 × 该状态下的唯一主行动
```

缺任何一项，页面就不该存在。

### 4.2 准入检查（三问）

新增任何页面/入口前必须回答：

1. **谁**（哪个角色）在**什么状态下**打开它？
2. 他打开后要得到的**第一个答案**是什么？
3. 页面唯一的**主行动**是什么，做完后进入什么状态、交给谁？

答不出来，就不建这个页面。

### 4.3 反堆砌的硬约束

- 不以页面数、菜单数、功能数衡量进度；以**角色闭环数 + 效率提升 + 验收证据**衡量。
- 每个入口必须挂在某个角色的主链闭环上；挂不上就不建。
- 专业列表（台账、项目库、流水）是**能力**，不是岗位主入口，不得直接占据一级导航。
- 禁止"先选功能菜单，再选业务对象"。
- 禁止把 App 的信息流放大成卡片堆。

## 五、首屏三问（每个页面必须回答）

1. **我是谁**：当前员工 + 角色 + 数据范围。
2. **当前有什么待处理**：属于我的待办、风险、逾期、等待他人、待决策（无则明确说明"当前无待处理"）。
3. **下一步该做什么**：唯一主行动 + 为什么现在做 + 谁负责 + 完成条件 + 做完进入什么状态。

页面身份只允许有一处承载，禁止标题重复三次。

---

## 六、可见性与账务底线

- 客户/业主侧只展示可公开事实，不展示内部成本、供应商、员工隐私。
- 成本价、成本明细、利润、毛利率仅企业负责人、店长、财务可见；
  其他角色**不生成该区块**，而不是"把数字隐藏起来"。
- 任一应计成本缺失时，成本完整性为 `false`，利润与毛利率返回 `null`，
  页面显示「成本未完整」——**禁止以 0 成本展示伪利润**。
- 跨企业、跨门店、跨团队的负向可见性，必须与正向用例一并验证。

---

## 七、这份思路用来回答什么

后续所有 Web 规范与智能体，都必须能回溯到本文的四条公理：

| 争议 | 依据 |
| --- | --- |
| 这个业务规则 Web 能不能改？ | A1：不能，App 为准 |
| 这个数据取不到，能不能加个 Web 接口？ | A2：不能，回到 App/后端决策 |
| 能不能照 App 页面做一遍？ | A3：不能，业务一致但交互必须为电脑重设计 |
| 这个页面要不要做？ | A4 + 第四章：从角色场景推得出来才做 |
