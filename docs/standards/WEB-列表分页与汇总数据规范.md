# Web 列表分页与汇总数据规范

> 状态：**已确认并生效（2026-10-21，用户确认）**
> 定位：`docs/standards/WEB-开发规范.md` 的执行细则；Web 列表、分页、统计卡片和后端汇总接口的唯一判定依据。
> 上位依据：`docs/standards/WEB-建设核心思路.md`、后端 `rules.md` §0.4、业务规则 `BR-025 / BR-031`。
> 本文不新增、不修改任何业务对象、状态、权限或金额口径。

---

## 1. 核心规则

```text
任何会随业务数据增长的列表，必须服务端分页；
任何汇总、合计、计数、比例、趋势或排行，必须由后端标准统计接口返回；
前端不得从当前页列表计算业务汇总；
后端统计查询不得使用 JPA N+1、全量实体加载后内存汇总或循环查库。
```

以上四条为并列硬规则，任一条不满足，页面不得通过交付验收。

---

## 2. 适用范围

### 2.1 必须分页的列表

以下形态默认必须服务端分页：

- 收款记录、付款记录、应收、应付、退款、工资、提成、资金台账、凭证等专业列表；
- 客户、房屋、项目、报价、合同、方案等对象列表；
- 审批、待办、风险、日志、消息、操作记录等会持续增长的队列；
- 页面内嵌入的跨对象历史明细，只要数据量可能随时间增长，也必须分页或有明确的服务端上限。

### 2.2 可以不分页的列表

只有同时满足以下条件才可不分页：

1. 数据量有明确业务上限；
2. 上限由服务端保证，不依赖当前样本；
3. 不承担全量查询、对账或历史检索职责；
4. 页面或接口明确说明数据范围。

允许的典型场景：固定枚举、少量配置项、单张单据内有限明细、详情页内固定数量的摘要项。

不允许把“当前只有几条数据”“先用 `size: 100` 够了”作为不分页依据。

### 2.3 汇总数据类型

必须走后端统计接口的数据包括：

- 金额：总额、已收、未收、已付、未付、收入、支出、净额等；
- 计数：笔数、项目数、逾期数、待办数等；
- 比例：回款率、完成率、毛利率、占比等；
- 分类汇总：按账户、类型、状态、门店、人员、月份等分组；
- 趋势、排行和 Top-N；
- 由业务事实推导的完成度、风险和异常数量。

纯展示文案、规则说明和静态标签不属于统计，但不得被伪装成业务指标。

## 3. 列表分页契约

### 3.1 请求

列表接口必须接收：

```text
current      当前页码，从 1 开始
size         每页条数，必须有服务端上限
filters      页面全部有效筛选条件
sort         允许的排序字段和方向
```

要求：

1. `size` 必须由服务端限制最大值，禁止无界查询；
2. 所有业务筛选在服务端完成，前端不得只筛选当前页；
3. 排序必须在服务端完成，并包含稳定唯一键作为次级排序，避免翻页重复或遗漏；
4. 租户、角色、门店、团队、本人及项目参与关系等数据范围必须由服务端强制；
5. 筛选条件变化后页码重置为 1；
6. 禁止以固定 `size: 100/200/1000` 代替分页。

### 3.2 响应

列表响应必须同时提供：

```text
list         当前页记录
total        当前筛选条件下的总记录数
current      服务端确认的当前页
size         服务端确认的每页条数
```

`list` 与 `total` 必须使用同一套租户、数据范围、筛选条件和时间口径。

### 3.3 前端实现

- `total > size` 时必须提供分页控件；
- 翻页必须重新请求服务端，不得在前端切分全量数据；
- 页面必须处理加载中、真实为空、请求失败和无权限状态；
- 返回列表时应恢复页码、筛选、排序和滚动位置；
- 列表搜索、状态筛选、时间筛选不得只作用于当前页；
- 单页展示的“当前页小计”如确需展示，必须明确标注“当前页”，且不能作为经营汇总卡片。

## 4. 汇总数据契约

### 4.1 前端禁令

以下行为一律禁止：

```text
items.reduce(...)               生成金额合计
items.filter(...).length        生成业务计数
items.filter(...).reduce(...)   生成分类汇总
items.map(...).reduce(...)      生成趋势/比率
list.length                     充当全量笔数
page.total                      直接充当汇总卡片数据
```

说明：

- `page.total` 只用于分页导航和“共有多少页”的计算；
- 页面上方统计卡片必须消费独立的后端统计接口；
- 前端只允许做单位换算、千分位、货币符号、百分比字符串等纯格式化；
- 接口失败时必须显示“暂不可确认”，禁止以 0、空数组或当前页数据兜底。

### 4.2 统计接口

统计接口必须：

1. 与对应列表共享筛选条件、权限范围和数据截止时间；
2. 不接收 `current`、`size`，一次返回全部匹配数据的汇总结果；
3. 显式返回 `asOf` 和必要的数据范围说明；
4. 返回页面需要的全部指标，前端不得再次拼算；
5. 指标口径、缺失值规则和权限边界必须登记在指标事实源中；
6. 优先复用已有共享 Provider；确需新增时，必须作为 App/Web 共用的后端能力建设，禁止开 Web 专属接口。

逻辑契约示例：

```text
列表：{domain}/{object}/page
入参：current + size + filters
返回：list + total + current + size

统计：{domain}/{object}/report
入参：filters（不含分页参数）
返回：count + amount + ... + asOf
```

收款、付款等缺少独立 `report` 能力时，页面不得用列表数据临时计算，必须先补齐共享后端统计能力。

### 4.3 列表与统计的一致性

- 列表与统计并行请求时，必须分别维护加载和失败状态；
- 统计失败但列表成功时，卡片显示“统计暂不可确认”，不得清空列表；
- 列表失败但统计成功时，保留统计并提示明细暂不可确认；
- 列表翻页不得改变统计卡片数值；
- 同一筛选条件下，列表总笔数必须与统计接口的 `count` 可对账；
- 金额合计、核销金额、冲正金额等口径必须能追溯到公式或业务规则。

## 5. 后端统计查询效率与 N+1 禁令

### 5.1 必须采用的方式

- 标量指标优先用一条聚合/投影 SQL 返回一行多列，例如 `COUNT`、`SUM`、`AVG`、`SUM(CASE WHEN ...)`；
- 分组统计使用 `GROUP BY`，只返回页面需要的分组字段和指标；
- Top-N、趋势和排行使用 `ORDER BY ... LIMIT N`，禁止先取全量再在 Java 中排序截取；
- 列表只投影页面实际使用字段，禁止加载完整实体图和无关关联；
- 需要业务公式时，允许批量取数后内存计算，但循环体内必须零查询；
- 数据权限、租户和门店范围必须保留在查询层，不得因改为聚合查询而放宽。

### 5.2 禁止的 JPA N+1 与等价反模式

```text
先分页/查询 N 条记录，再逐条访问 LAZY 关联；
for (...) { repository.findBy...(...) }
for (...) { entity.getAssociation().get...() } 触发逐行 SQL
findAll(...) + stream().sum()/count()/groupBy()
全量加载后 Java 排序并截取前 N
为降低 SQL 条数而堆叠重 JOIN 或完整 @EntityGraph
依赖 open-in-view 在事务外补查关联
```

要求：

- 列表关联展示必须使用字段投影、批量预取、受控 `JOIN FETCH` 或等价高效方案；
- `@EntityGraph` 不是 N+1 的通用解法；不得加载页面未使用的完整关联图；
- 统计接口的返回行数不应随业务明细数量线性增长；
- 查询条数在 10 倍数据量下不得随列表条数增长；
- 核心统计接口按 `BR-025 / BR-031` 验证 P95、SQL 条数、返回行数和 10 倍数据量表现；
- 不接受“方法内部耗时正常”替代端到端接口验证。

### 5.3 性能基线

核心读取接口默认遵守：

```text
P95 <= 500ms
P99 <= 1000ms
端到端 SQL <= 30 条
10 倍数据量下 SQL 条数不随列表条数增长
```

复杂报表如确需例外，必须说明原因、降级策略和测量证据，不能静默放宽。

## 6. 交付验收门禁

### 6.1 列表

- [ ] 接口包含 `current / size / total`，且 `size` 有服务端上限
- [ ] 搜索、筛选、排序全部由服务端执行
- [ ] 超过一页的数据能正确翻页，无重复、无遗漏
- [ ] 翻页后统计卡片不变
- [ ] 返回列表时恢复页码和筛选
- [ ] 不存在固定大 `size` 拉取全量数据
- [ ] 加载、空态、错误、无权限状态完整

### 6.2 汇总

- [ ] 页面每个业务统计卡片都有明确的后端 `report/summary` 接口
- [ ] 前端不存在从列表计算金额、计数、比例或排行的代码
- [ ] 统计接口与列表使用同一筛选条件和数据范围
- [ ] 统计接口返回 `asOf`
- [ ] 统计失败显示“暂不可确认”，不以 0 兜底
- [ ] 统计口径已登记，缺失值规则明确

### 6.3 性能与数据权限

- [ ] 端到端 SQL 不超过预算，或无静默 N+1
- [ ] 10 倍数据量下查询条数稳定
- [ ] 列表和统计均验证跨企业、跨门店/团队和越权拒绝
- [ ] 统计接口没有全量实体加载后内存汇总
- [ ] 没有循环体内查询、逐行懒加载或全量排序截取

---

## 7. 存量整改

当前已存在固定条数加载、无分页或前端汇总的页面，均视为技术债，不得作为新页面的实现先例。

存量整改状态与批次证据见 `docs/development/WEB-LIST-PAGINATION-REMEDIATION.md`。

整改顺序：

1. 资金、成本、工资、提成、台账、凭证等金额相关页面；
2. 数据量可能快速增长的客户、项目、合同和待办列表；
3. 其他专业列表；
4. 详情页内嵌的长期历史明细。

整改前不得通过文案把“当前页合计”包装成全量汇总；整改完成后补齐接口、前后端测试、权限负向用例和性能证据。
