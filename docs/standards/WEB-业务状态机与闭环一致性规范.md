# Web 业务状态机与闭环一致性规范

> 状态：生效并强制执行  
> 适用范围：客户、房屋、项目、设计、报价、合同、增减项、应收、应付、验收、阶段和任务等业务状态  
> 上位依据：装得清业务智能体 `SCN/BR/DEC` 中对象状态、权限、金额和闭环规则

> 动作权限、前置条件、幂等和跨对象刷新范围还必须遵循 `docs/standards/WEB-业务动作与闭环注册规范.md`。

---

## 1. 核心问题

状态机问题反复出现的原因不是某个页面映射漏了，而是缺少统一状态模型：

- 前端自己推导状态；
- 每个页面自己维护英文到中文的映射；
- 页面用本地 `status === xxx` 判断动作是否可用；
- 一个动作后只刷新当前对象，不刷新客户、房屋、项目等关联投影；
- 客户主阶段与房屋执行阶段混在一起展示；
- 派生标签、持久化状态和展示状态没有区分；
- 服务端状态、前端缓存和页面投影没有版本核对；
- 验收只看按钮是否出现，验证不了闭环结果一致。

本规范要求：**状态由服务端事实决定，前端只负责展示、解释和触发动作。**

---

## 2. 四层状态模型

```text
服务端持久化状态 / 领域事实
  -> 领域状态适配器
  -> 状态注册表与动作策略
  -> 页面 StateView
  -> 动作后回读与跨对象闭环校验
```

### 2.1 服务端事实

服务端是状态唯一裁决者：

- 持久化状态字段；
- 派生事实标签；
- 当前阶段；
- 允许动作；
- 阻断原因；
- 下一责任角色；
- 关联对象投影；
- revision / version / updatedAt。

前端禁止把本地布尔值、数组长度或页面上下文推导成正式业务状态。

### 2.2 领域状态适配器

每个领域必须提供：

```ts
interface BusinessStateView<TStatus extends string> {
  status: TStatus
  label: string
  tone: StatusTone
  derivedLabels: Array<{ key: string; label: string; tone?: StatusTone }>
  allowedActions: BusinessAction[]
  blockedReasons: string[]
  nextOwner?: string
  source: string
  revision?: string
  updatedAt?: string
}
```

前端只消费 `BusinessStateView`，不在页面重新判断业务规则。

### 2.3 状态注册表

机器可读文件：

```text
docs/standards/business-state-machines.json
```

每个对象必须定义：

- `key`；
- `label`；
- `source`；
- `persistedStatus`；
- `derivedFacts`；
- `statuses`；
- `transitions`；
- `projections`；
- `actionPolicy`；
- `consistencyRules`；
- `businessRefs`；
- `transitionStatus`。

业务状态转换尚未裁决时，必须标记 `pending_business_review`，不得凭前端代码推断。

### 2.4 StateView 页面契约

页面状态区域只能展示：

- 当前主状态；
- 派生行为标签；
- 下一步动作；
- 阻断原因；
- 责任人；
- 最近状态变化时间；
- 关联对象一致性提示。

禁止页面自行计算状态或动作可用性。

---

## 3. 主状态与派生状态

必须区分：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 持久化主状态 | 客户 `PendingMeasure`、项目 `Accepting` | 服务端裁决，前端只展示 |
| 派生行为标签 | 已量房、已报价、已收款 | 从真实领域事实推导 |
| 展示阶段 | 客户摘要阶段、当前房屋执行阶段 | 服务端提供或按明确投影规则生成 |
| 阻断状态 | 成本未完整、材料锁定、验收待业主确认 | 明确原因和恢复路径 |

客户这类多房屋对象必须采用“客户摘要主阶段 + 当前房屋执行阶段”双视图，不得混成一个字段。

---

## 4. 动作策略

每个业务动作必须声明：

- 动作 key 和中文名；
- 角色和数据范围；
- 前置条件；
- 允许状态；
- 目标状态；
- 是否幂等；
- 是否二次确认；
- 失败文案；
- 关联刷新范围；
- 审计要求。

前端按钮只根据服务端返回的 `allowedActions` 显示或禁用；不得使用：

```ts
const canSubmit = status === 'draft' && user.role === 'Finance'
```

作为最终业务权限判断。服务端仍必须再次校验。

---

## 5. 闭环一致性

一个业务动作完成后，必须同时核对：

1. 当前对象状态；
2. 当前对象 revision / version；
3. 关联对象投影；
4. 账务或金额事实；
5. 待办和下一步责任；
6. 历史轮次和审计记录。

典型关系：

```text
量房完成
-> 房产已量房
-> 客户行为标签更新
-> 设计下一步可用

报价客户接受
-> 报价 accepted
-> 合同/交接路径可用
-> 项目立项前置条件更新

收款登记
-> 应收已收/部分收款/已收清
-> 资金台账写入
-> 项目回款指标更新

合同变更客户确认
-> 变更状态 customerConfirmed
-> 任务、材料、应收、成本重算投影一致
```

任何一步缺失，都不得只用前端文案掩盖。

---

## 6. UI 展示规则

- 状态必须使用统一 `StatusTag` 和注册 META；
- 不得直接显示英文枚举；
- 同一状态在全 Web、App 和财务页面中文一致；
- 不得只靠颜色表达状态；
- 同一状态在主列表、详情、侧栏和弹窗中必须一致；
- 状态变化后必须显示更新时间、操作人和下一责任人；
- 失败时显示“暂不可确认”并保留恢复路径，禁止伪装成完成。

---

## 7. 自动门禁

新增命令：

```bash
npm run check:states
```

检查：

- 状态机注册表字段完整；
- 所有状态都有中文和状态色；
- transition 引用必须指向已注册状态；
- 业务概念枚举集合必须覆盖状态机注册；
- 页面不得直接渲染裸状态；
- 不得新增未登记的本地状态 META；
- 动作不得绕过服务端 allowedActions；
- 修改状态后必须声明关联刷新范围。

---

## 8. 验收定义

每个状态机动作必须覆盖：

- 正常流转；
- 重复提交；
- 非法前置条件；
- 越权；
- 并发冲突；
- 服务端失败；
- 刷新后回读；
- 关联对象一致性；
- 历史轮次和审计；
- App/Web 同事实一致。

只有页面截图或按钮出现，不算状态机验收通过。

---

## 9. 交付定义

- [ ] 业务状态已登记 `business-state-machines.json`；
- [ ] 中文标签和 tone 已定义；
- [ ] 状态来源和服务端 Provider 已明确；
- [ ] 派生标签与持久化状态已区分；
- [ ] 动作策略和前置条件已业务裁决；
- [ ] 页面只消费 `BusinessStateView`；
- [ ] 操作后关联对象已重新读取或按契约局部更新；
- [ ] `npm run check:states` 通过；
- [ ] 真实浏览器验证闭环后状态和关联投影一致。

---

## 10. 结论

选择器规范解决“选什么、怎么选、怎么回显”；状态机规范解决“当前是什么、能做什么、做完后其他对象是否一致”。

两者必须共同作为 Web 产品研发的底层约束，不能依赖设计师逐页记忆。
