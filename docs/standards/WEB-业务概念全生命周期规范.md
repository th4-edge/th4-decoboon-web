# Web 业务概念全生命周期规范

> 状态：生效并强制执行  
> 适用范围：`th4-decoboon-web` 中所有业务概念的选择、回显、展示、状态和枚举映射  
> 上位依据：装得清业务智能体 `DEC-021/022/023/024/025/026/028`、`BR-019/020/021/022/023/024/026`

> 状态流转、派生状态和跨对象闭环还必须遵循 `docs/standards/WEB-业务状态机与闭环一致性规范.md`。

---

## 1. 要解决的问题

业务概念相关问题反复出现，根因不是某个组件写得不好，而是缺少统一治理层：

- 页面直接消费后端字段；
- 枚举中文化散落在页面；
- 同一个业务对象在不同页面使用不同选择器；
- 选中后只回显名称，没有关键业务事实；
- 新页面只通过人工审查，无法机器拦截；
- 清单按文件统计，不能检查“业务概念是否完整”。

本规范要求：**新增或修改任何业务概念前，先登记概念元数据，再实现组件和页面。**

---

## 2. 业务概念范围

以下对象必须纳入业务概念注册表：

| 概念 | 必须回显的业务事实 | 选择器要求 |
| --- | --- | --- |
| 项目 | 编号、客户、地址、状态、金额、设计师、项目经理、阶段 | 引导式项目选择器 |
| 客户 | 姓名、电话、负责人、状态、最近跟进、多房屋关系 | 客户专用选择器，不自动选房屋 |
| 房屋 | 客户、小区、楼栋、房号、面积、户型、状态、最近量房 | 房屋专用选择器，必须绑定客户 |
| 员工 | 姓名、角色、门店、团队、状态、员工编号 | 员工专用选择器，不显示薪酬等敏感信息 |
| 工人 | 姓名、工种、电话、状态 | 工人专用选择器 |
| 供应商/经销商 | 名称、合作状态、结算方式、账期、起结日 | 供应商专用选择器 |
| 应收节点 | 项目、类型、到期日、应收/已收/待收、状态、发票 | 应收专用选择器 |
| 应付单 | 项目、类型、收款方、到期日、应付/已付/未付、紧急状态、来源单号 | 应付专用选择器 |
| 增减项/合同变更 | 编号、合同、项目、类型、金额变化、状态、客户签认 | 增减项专用选择器 |
| 报价分项 | 分类树、品牌、系列、规格、区域、单位、价格、数量 | 报价分项专用选择器 |
| 账务分类 | 一级/二级树、方向、启停状态、完整路径 | 树形分类选择器 |

未来出现新业务对象，必须先向业务智能体完成 T15 评审并加入注册表，再开发。

## 3. 四层架构

```text
业务概念注册表
  -> 领域展示适配器
  -> 业务专用选择器 + 已选摘要卡
  -> 页面场景组件
  -> 自动门禁与验收
```

### 3.1 业务概念注册表

机器可读文件：

```text
docs/standards/business-concepts.json
```

每个概念必须声明：

- `key`：稳定概念键；
- `label`：业务中文名；
- `source`：远程对象、封闭字典或树形字典；
- `picker`：专用选择器实现路径；
- `selectedSummary`：选中后的回显形态；
- `identityFields`：业务身份字段；
- `displayFields`：必须展示的业务事实；
- `enumSets`：涉及的状态/类型/角色枚举；
- `dependencies`：依赖的上游概念；
- `clearRules`：上游变化时必须清空的字段；
- `businessRefs`：业务规则编号；
- `testCases`：必须覆盖的验收用例。

### 3.2 领域展示适配器

后端原始响应不得直接进入页面插槽。每个领域必须在 `src/domains/**/model.ts` 和 `meta.ts` 中完成：

1. 原始字段归一化；
2. 业务对象类型化；
3. 枚举中文标签和状态色映射；
4. 缺失值语义处理；
5. 选中摘要所需字段投影。

禁止：

- 模板中显示后端 PascalCase 枚举；
- 模板中直接显示 `raw.status/type/role/direction`；
- 用 `String(...)` 把对象或枚举直接展示；
- 页面自行拼接业务对象摘要。

### 3.3 专用选择器 + 已选摘要卡

所有业务对象选择器必须实现完整生命周期：

```text
空态
-> 打开并立即展示数据
-> 业务筛选/搜索
-> 选择对象
-> 全宽已选摘要卡
-> 更换/清除
-> 上游上下文变化时清空或重新校验
-> 保存时服务端复核
```

统一的是机制，不是视觉结构：

- 项目使用责任维度、状态来源、项目卡片；
- 客户使用阶段、负责人、客户卡片；
- 房屋必须绑定客户并显式选择；
- 员工使用角色、门店、团队、状态；
- 应收/应付使用逾期、临期、金额和核销状态；
- 账务分类使用树；
- 报价分项使用分类树、品牌/系列/规格和数量。

### 3.4 页面场景组件

页面不得重新拼选择器。页面只负责：

- 传入当前上下文；
- 消费选择结果；
- 调用服务端；
- 展示业务参考和风险；
- 处理失败、空态、权限和恢复。

## 4. 已选回显强制规则

所有远程业务对象选中后，不得只显示名称。必须使用与项目选择器一致的“已选业务摘要卡”。

摘要卡必须包含：

1. 对象类型和当前状态；
2. 业务主身份；
3. 业务编号；
4. 3–6 个决定下一步动作的业务事实；
5. 更换、清除操作；
6. 长文本换行，不得挤压金额和状态；
7. 占满表单容器宽度。

示例：

- 项目：状态、来源、金额、设计师、项目经理、阶段；
- 员工：角色、门店、团队、状态、员工编号；
- 应收：应收/已收/待收、到期日、逾期风险；
- 应付：应付/已付/未付、到期日、收款方、来源单号；
- 客户：负责人、状态、最近跟进、多房屋提示；
- 房屋：面积、户型、量房状态、地址。

## 5. 枚举与中文映射强制规则

### 5.1 统一形态

所有业务枚举必须定义：

```ts
export const XXX_STATUS_META: Record<XxxStatus, { label: string; tone: StatusTone }> = {
  ...
}
```

或：

```ts
export const XXX_TYPE_LABELS: Record<XxxType, string> = {
  ...
}
```

### 5.2 UI 禁用项

禁止在模板中直接渲染：

```vue
{{ row.status }}
{{ item.role }}
{{ detail.type }}
{{ ledger.direction }}
```

必须使用：

```vue
{{ XXX_STATUS_META[row.status].label }}
<StatusTag :text="XXX_STATUS_META[row.status].label" :tone="XXX_STATUS_META[row.status].tone" />
```

### 5.3 输入控件边界

- 普通单选/多选、账户、用途、方向：传统 `select` / `multi-select`；
- 单据核心类型且选项极少：紧凑 checkbox，单值语义；
- 远程业务对象：专用选择器；
- 树形字典：树选择器。

不得为了让选项可见，把所有 select 都替换为大块 checkbox。

## 6. 自动门禁

新增检查脚本：

```bash
npm run check:concepts
```

必须检查：

1. 注册表概念是否完整且引用文件存在；
2. 是否存在用 `el-select` 承载远程业务对象；
3. 是否存在未注册的专用选择器；
4. 是否存在裸枚举直接展示；
5. 是否存在业务对象已选择但没有摘要卡；
6. 是否存在依赖字段未清理；
7. 是否存在未映射中文的枚举。

静态检查通过只是最低门槛，真实浏览器仍必须覆盖正常、拒绝、空、失败、权限、长文本和三档分辨率。

## 7. 研发交付定义

任何业务概念相关需求只有同时满足以下条件才算完成：

- [ ] 业务规则已完成 T15/T16/T17 和业务裁决；
- [ ] 已登记或更新 `business-concepts.json`；
- [ ] 已定义领域模型和枚举 META；
- [ ] 已实现专用选择器；
- [ ] 已实现全宽已选摘要卡；
- [ ] 已处理依赖上下文、清除、替换、失败和恢复；
- [ ] 服务端保存时重新校验权限和归属；
- [ ] `npm run check:forms` 通过；
- [ ] `npm run check:concepts` 通过；
- [ ] 组件测试覆盖选择、清除、回显、依赖变化和异常；
- [ ] 真实浏览器覆盖三档分辨率和控制台零错误；
- [ ] 验收记录包含截图和真实数据路径。

## 8. 反模式

以下写法一律禁止：

1. 一个通用 `BusinessObjectPicker` 承载所有业务对象；
2. 远程业务对象使用普通 `el-select`；
3. 选择器只显示名称和一行描述；
4. 选中后仍是普通输入框样式；
5. 页面直接显示后端枚举英文值；
6. 每个页面自己维护中文标签；
7. 多房屋客户自动选第一套房屋；
8. 项目、客户、房屋、员工等对象在表单左右布局中因长名称挤压；
9. 只做静态检查，不做真实浏览器验收；
10. 只看构建通过，不验证业务概念回显和枚举中文。

---

## 9. 结论

避免遗漏的唯一可行方式，是把业务概念从“页面问题”提升为“平台元数据 + 组件契约 + 自动门禁”问题。

一句话规则：

> 先注册业务概念，再生成展示 Meta，再实现专用选择器和摘要卡，最后由自动门禁与真实浏览器验收共同收口。
