# 装得清 App 能力与理念研究（Web 规范的上游依据）

> 研究日期：2026-10-06
> 研究对象：`th4-decoboon-app`（微信小程序，线上版本 1.0.13）
> 研究目的：把 App 的**业务闭环能力、交互理念、设计规范**提炼为 Web 底层规范的上游依据
> 证据方式：App 源码（`src/roles`、`src/pages.json`、`src/components`、`src/domains`）+ App 文档（`docs/01`~`docs/09`）
> 结论时效：App 仍在迭代，本文结论需在 App 发版后复核

---

## 一、最重要的结论：App 的核心不是"页面"，是"角色闭环"

App 已有约 **112 个页面**（主包 14 + 15 个分包），但它的组织方式不是按页面分类，而是：

```text
角色 → 该角色今天要做什么 → 按工作阶段聚合 → 进入对象 → 推进状态 → 下一个角色接手
```

App 文档明确写着：

> 设计师 Tab 重构的核心理念：**不同角色看到不同的"今天要做什么"，而不是统一的对象列表。**

这是 Web 必须继承的第一条理念。

## 二、角色模型（8 类）

| RoleKey | 角色 | 职责定位 | Tab 配置 |
| --- | --- | --- | --- |
| `boss` | 企业负责人 | 全局经营与关键审批 | 工作台 / 客户 / 项目 / 财务 / 我的 |
| `storeManager` | 店长 | 门店经营、客户分配、设计师调度 | 工作台 / 客户 / 项目 / 我的 |
| `teamLeader` | 团队负责人 | 团队客户跟进与协同 | 工作台 / 客户 / 项目 / 我的 |
| `marketer` | 业务员 | 客户登记、跟进与转化 | 工作台 / 客户 / 项目 / 我的 |
| `designer` | 设计师 | 量房报价与施工排期 | 工作台 / **设计** / **报价** / 项目 / 我的 |
| `pm` | 项目经理 | 现场施工、节点与验收 | 工作台 / 客户 / 项目 / 我的 |
| `finance` | 财务 | 应收、收付款、结算、材料履约协同 | 工作台 / **财务** / 项目 / 动态 / 我的 |
| `customer` | 业主 | 只看自己的项目并参与验收 | 我的家 / 进度 / 动态 / 我的 |

### 2.1 「角色即视图」机制

- 同一套页面对不同角色返回**不同 Tab**（`ROLE_TABS` 映射）。
- 角色元信息（`ROLE_META`）只负责展示；**数据可见域由服务端 + 权限矩阵保证**。
- 新增角色只改角色映射层，**禁止在页面里散落角色 `if/else`**。

### 2.2 对 Web 的直接要求

- Web 的一级导航必须同样由「角色 + 权限」决定，而不是一套全量菜单。
- 设计师这种"职责跨界"的角色独占专属 Tab（设计 / 报价），Web 必须给对应的一级入口。
- Web 禁止出现"所有角色共用一套菜单、靠按钮隐藏做权限"的做法。

## 三、App 的五条核心业务闭环（业务叙事）

> 来源：`docs/02-闭环页面逻辑与高保真视图.md`

### 链路 A · 建企业 → 邀请 → 接受

```text
登录 → 创建企业（建 Company+BOSS，送试用）→ 老板工作台
→ 选岗位生成邀请令牌 → 对方打开小程序 → 输入 token+姓名+手机号+密码
→ 进对应角色工作台 → 负责人「团队成员」实时出现新成员
```

### 链路 B · 客户从哪来 → 登记跟进 → 转施工项目

```text
顾问登记客户（来源/阶段/意向小区/预算）→ 客户详情
→ 每次沟通写跟进（方式/内容/下次跟进）→ 列表显示最近跟进
→ 客户走到签约 → 转施工项目 → 系统自动生成 7 阶段施工计划 + 同频成员
```

### 链路 C · 项目经理怎么把工地干起来

```text
工地详情-进度看到 7 阶段时间线 → 点「开始拆除改造」→ 阶段进行中 + 发布开工动态（业主可见）
→ 阶段内拆解任务 → 任务「开始/完成并申请验收」→ 动态进时间线
→ 现场汇报（进度/打卡/材料/问题 + 照片 + 是否同步业主）→ 汇报即动态
→ 业主端实时出现照片与进展
```

### 链路 D · 阶段验收「同频拍板」（产品最关键闭环）

```text
PM 提交验收（结论/整改项/照片）→ 阶段变「待验收」，业主收到通知
→ 业主查看验收单+照片 → 「确认验收」或「有异议，驳回」
→  确认：阶段 done → 自动开启下一阶段 → 各方工作台同步刷新
→  驳回：阶段回进行中（整改）→ PM 收到整改任务 → 整改后重新提交
```

> 这是一个**强闭环**：提交 → 确认 → 开门 → 下一关。

### 链路 E · 老板/企业怎么「不打电话也知道」

```text
老板工作台：在建/待开工/待验收/停工 四指标 + 需要关注（待确认验收、停工）+ 最新动态
工地详情：整体进度（阶段权重自动算）+ 当前阶段 + 资金进度（合同/已收/收款率）
风险视图：停工项目标红可筛；消息中心推送逾期/停工预警
```

### 3.1 对 Web 的要求

- Web 的业务闭环必须能映射到这五条链路，且**同角色同状态动作可达**。
- 链路 C/D 的"现场"部分属于 App 主场；Web 要承接的是**排期、对账、多项目并行、验收台账**。
- 链路 E 是 Web 的核心价值区（老板经营管控层）。

## 四、各角色闭环摘要

| 角色 | 起点 | 关键接力 | 终点 | Web 应强化 |
| --- | --- | --- | --- | --- |
| 业务员 Marketer | 登记客户 | 跟进 → 预约量房 → 交接设计师 | 客户转设计 | 批量跟进、客户池筛选 |
| 设计师 Designer | 承接客户 | 量房 → 设计 → 报价 → 客户确认 → 转项目 → 排期 | 设计交付、业绩 | Excel 式报价、多客户并行、报价项目库 |
| 店长 StoreManager | 门店客户池 | 分配设计师 → 报价到项目 → 履约风险 → 团队通知 → 门店业绩 | 门店经营结果 | 分配队列、门店看板、风险台账 |
| 团队负责人 TeamLeader | 团队客户 | 客户经营 → 报价到项目 → 工地履约 → 业绩 | 团队产出 | 团队负荷、协同台账 |
| 项目经理 Pm | 被指派项目 | 核对报价（只读）→ 排期 → 开工 → 任务留证 → 现场动态 → 提交验收 | 交付与履约业绩 | 多项目排期、材料风险、验收台账 |
| 财务 Finance | 应收 | 收款核销 → 支出/应付 → 结算 → 账本 | 资金与结算 | 对账、批量核销、资金穿透 |
| 企业负责人 Boss | 全局 | 经营指标 → 风险 → 下钻 → 审批 | 经营决策 | 决策页、经营分析、风险中心 |

### 4.1 设计师职责边界（App 原文提炼）

**做**：承接本人客户、沉淀跟进、基于户型/面积/企业套餐生成报价（金额由服务端算）、
推动报价提交与客户确认、由已接受报价立项、按"阶段×区域×工艺×数量"编排施工任务、
查看节点留证与验收结果、查看本人业绩。

**不做（服务端同样拦截）**：看其他设计师的私人客户/报价/项目、做 PM 的开工与节点确认、
碰企业资金结算与全局经营数据、改服务端计算的金额/成本/进度。

### 4.2 项目经理职责边界（App 原文提炼）

**做**：项目/阶段/任务/日报的推进、节点留证、现场动态、材料状态、提交验收、履约业绩。

**不做**：获客、客户转交、报价编辑。
**数据来源**：全部由 `Project.manager = 当前员工` 反向确定（不是按客户负责人或报价创建人套用）。

> 这一点对 Web 极其重要：**不同角色的数据范围算法不同**，不能统一按 `Self` 处理。

## 五、App 的设计理念

### 5.1 五条设计原则（`docs/03-视觉与设计规范.md`）

| 原则 | 内容 |
| --- | --- |
| **角色优先** | 不同角色进不同工作台；首屏回答"我是谁/待处理/下一步"；客户侧只展示可公开事实 |
| **任务优先** | 每页只保留一个主任务；主操作固定品牌主按钮；高频动作不藏在多级菜单 |
| **信息分层** | 三层：标题与状态 / 关键事实 / 说明备注；**不用整块强色背景承载多层级信息** |
| **一致性** | 颜色、圆角、间距、字号、阴影全走 Token；图标统一 `JzIcon`，禁 emoji；跳转统一 `P.*` |
| **可执行** | 字段说明用途；错误指出具体问题与修正方式；空态给下一步；列表支持下拉刷新；成功后返回来源页并刷新 |

### 5.2 强视图六原则（`docs/02`「为什么业主一看就懂」）

1. **一个工地一张主图**——封面 + 整体进度 + 当前阶段 + 关键日期 + 成员头像墙，不用表格让人猜。
2. **阶段 = 竖向里程碑时间线**——绿点已验收 / 橙点进行中 / 灰点未开始 / 红点逾期。
3. **计划 = 横向进度条甘特**——一眼看到计划偏差。
4. **动态 = 卡片时间线**——谁、何时、哪个阶段/任务、做了什么、附现场照片、业主可见标记。
5. **验收 = 一次"拍板页"**——结论 + 整改项 + 照片 + 两个大按钮，把抽象流程变成一次点击。
6. **角色即视图**——客户只看到"我的家+动态+成员+相册"；员工按权限矩阵裁剪按钮。

### 5.3 对 Web 的要求（关键差异）

App 的强视图原则**解决的是"小屏一眼看懂"**。Web 的大屏必须解决**"看清楚、比得出来、批得动"**：

| App 解决 | Web 必须进一步解决 |
| --- | --- |
| 一眼看懂单项目 | 多项目横向比较、排期冲突、资源负荷 |
| 一次拍板（验收） | 验收台账、批量确认前置校验、驳回原因归类 |
| 时间线看懂过程 | 跨项目动态检索、按阶段/责任人筛证据 |
| 卡片承载信息 | 表格承载密度 + 固定列 + 批量选择 |
| 单对象推进 | 并行上下文（不丢筛选、不丢位置） |

**结论：App 的"强视图"是 Web 的下限，不是上限。**

## 六、状态体系

### 6.1 核心状态机（App 原文）

```text
Customer: New -> Following -> Quoted -> Signed -> Serving -> Finished
                          \-> Lost

Quote:    Draft -> Submitted -> Accepted -> Converted
                       \-> Rejected

Task:     Todo -> Doing -> Accepting -> Done
            \-> Cancelled（逾期仅作展示状态）

Stage:    Todo -> Doing -> Accepting -> Done
                    \-> Doing（驳回整改）

Project:  Preparing -> Ongoing -> Accepting -> Finished -> Settled
                         \-> Suspended
```

### 6.2 状态设计规则

- **前端只展示服务端返回状态，不自行推进。**
- 状态色板 14 个语义 tone（与 Web 同源）：
  `idle / todo / muted / closed / dark / doing / progress / alert / pending / done / blocked / info / special / accent`
- 状态必须"文字 + 颜色 + 位置"，不能只靠颜色。
- 驳回是**回到进行中**（整改），不是新增状态。

### 6.3 交互反馈与异常（App 原文）

- 所有请求统一走 `src/core/http.ts`；`success:false` 必须进入 `catch`。
- 先渲染加载态再渲染数据；空态区分"无数据 / 无权限 / 未配置主数据"。
- 保存、提交、状态推进**必须二次确认业务后果**。
- 成功后重新拉取服务端数据，**不在页面本地猜测状态**。
- 401 自动清理会话回登录页；越权返回明确但最小化的业务提示。

## 九、对 Web 的启示（继承 / 差异）

### 9.1 必须继承

1. 角色即视图——按角色给工作台与一级导航，不做全量菜单。
2. 首屏三问——我是谁 / 当前有什么待处理 / 下一步做什么。
3. 一页一主任务、一状态一主动作。
4. 信息分三层，不用强色块堆信息。
5. 状态由服务端给，前端只展示。
6. 保存/提交/状态推进必须二次确认，成功后重新拉取。
7. 空态区分"无数据 / 无权限 / 未配置主数据"，并给下一步。
8. 数据范围按角色算法不同（PM 走 `Project.manager` 反向确定），不能统一按 `Self`。
9. 成本不完整不显示利润；金额一律服务端算。
10. 品牌、状态语义、图标体系与 App 同源。

### 9.2 必须差异

1. **形态**：底部 TabBar → 左侧一级导航 + 阶段模式栏。
2. **密度**：卡片流 → 表格/多列 + 固定列 + 批量选择。
3. **并行**：单对象 → 多对象比较、不丢筛选上下文。
4. **输入**：触屏点按 → 键鼠 + 快捷键 + 批量编辑。
5. **输出**：屏幕查看 → 导出/打印/正式单据。
6. **经营**：App 看指标，Web 看"结论 → 风险 → 下钻"。
7. **现场类动作**（拍照留证、现场确认）留在 App，Web 承接其台账与对账。

### 9.3 禁止

1. 把 App 页面等比放大。
2. 按后端模型做 CRUD 页面。
3. 功能菜单堆砌。
4. 未经 App 验证的 Web 专属业务规则或接口。

## 十、补充研究：五大闭环深度（2026-10-06 补全）

> 来源：`docs/product/2026-09-20~2026-09-22` 系列产品设计 + `subpackages/finance/**` 实际页面。

### 10.1 企业负责人（Boss）能力地图

**首页信息架构（自上而下固定 8 段）**

```text
新企引导 → 个人名片 → 四项经营指示灯 → 经营驾驶舱入口
→ 四个高频经营动作 → 需要关注（预警队列）→ 需要关注的项目（最多 4 个）→ 经营动态
```

**四项经营指示灯与状态规则**

| key | 名称 | 统计口径 | 健康状态规则 |
| --- | --- | --- | --- |
| `signedAmount` | 本月签约额 | 本月签约额 | 达成 <60% → danger；60–79.9% → attention；≥80% → normal；未设目标按环比，<-20% attention |
| `receivedAmount` | 本月回款额 | 本月回款额 | 有逾期应收 → danger；无逾期但达成 <60% → attention |
| `grossProfit` | 本月项目毛利 | 本月**可靠**毛利 | 毛利为负 → danger；完整但达成 <80% → attention；**成本不完整 → unknown（「成本未完整」）** |
| `activeProjectCount` | 在建项目数 | 在建项目数 | 存在停工或计划逾期 → danger |

四态：`normal` 绿 / `attention` 黄 / `danger` 红 / `unknown` 灰（数据不完整，不能可靠判断）。

**四个一级功能域（固定）**：客户经营 / 方案设计 / 报价谈单 / 合同签约。
低频配置（成员、团队、报价项目库、套餐模板、供应商、订阅、账号）归入「我的」。
另有二级「经营专业工作台」六入口：量房经营、选材工作台、材料计划、履约驾驶舱、增减项经营、员工绩效。

**「需要关注的项目」只展示风险项目**（最多 4 个），风险来源：逾期应收 / 停工或计划逾期 / 材料超领 / 合同变更率异常。
每个风险项目展示：名称编号、状态进度、最高风险级别、风险原因、项目经理、**建议下一步动作**、下钻入口。

**项目 Tab 经营视角**

- 四指标卡：在建项目 / 在建合同额 / 回款率 / 本月新签项目（**与首页四指标不同，注意区分**）
- 双维度分段（带计数）：全部 / 待开工 / 施工中 / 停工 / 待验收 / 已完工
- 经营排序（仅负责人）：风险优先 / 金额最高 / 回款最慢 / 工期最紧 / 最新录入
- 项目经营卡片 7 层：识别行 → 风险条 → 资金行 → 交付行 → **利润行（仅负责人）** → 动作行 → 滚动居中高亮

口径硬约束：
- **在建** = `status ∈ {Preparing, Ongoing, Suspended, Accepting}`；`Finished`/`Settled` 不计入。
- **合同当前金额**优先 `ProjectContract.currentAmount`，为 0 时回退 `baselineAmount`，无合同回退 `Project.contractAmount`。
- 毛利不可确认时不参与统计，卡片显示「成本未完整」，**禁止 0 成本**。
- 实际成本/毛利/成本完整性**仅负责人可见**，其他角色服务端过滤。

**合同签约与履约（三页职责边界）**

| 页面 | 回答的问题 |
| --- | --- |
| 签约工作台 | 现在有哪些单要签、哪些在履约 |
| 签约确认台 | 这一单怎么签、签完生成什么 |
| 合同履约档案 | 这一单现在赚不赚钱、进展如何 |

签约确认台三步（可完成状态投影，必做分母固定 3）：

| key | label | 完成判定 | 异常态 |
| --- | --- | --- | --- |
| `quote` | 确认报价 | 报价 `Accepted/Converted` 且已关联合同 | 无已确认报价 → 禁签 |
| `contract` | 合同签约 | 合同存在且 `signedAmount>0`，`status ≥ Signed` | 签约失败 → 保留草稿 |
| `project` | 生成项目 | 合同 `status ≥ Effective` 且存在 `projectId` | 生效失败 → 仍停留签约台 |

金额六字段（冻结）：

```text
baselineAmount   报价基线金额       不随变更
signedAmount     最终签约价（冻结） 不随变更
currentAmount    当前合同金额       随已确认变更变化
receivableAmount 应收计划总额       随变更变化
receivedAmount   已收金额           随变更变化
outstandingAmount 未收 = 应收 − 已收
```

**签约与生效仅 BOSS 可执行**；其他角色看到「请联系企业负责人完成合同签约」。

### 10.2 财务闭环

**业务主导排序（不是按页面代码顺序）**

| 分组 | 顺序 | 设计理由 |
| --- | --- | --- |
| 资金收付 | 登记收款 → 登记付款 → 手工记账 | 先记录真实发生的资金事实 |
| 往来管理 | 应收计划 → 应付账款 → 工人工资 → 供应商往来 | 先看收入侧再看支出侧 |
| 账务核算 | 资金台账 → 项目账本 → 收付凭证 | 钱怎么流动 → 项目赚不赚钱 → 单据如何归档套打 |

**交互规则（原文）**

- 每个分组必须有业务说明，不能只显示功能名。
- 分组标题使用品牌渐变柱，形成明确层级。
- 登记类动作必须校验编辑权限；只读角色仍可查看列表和台账。
- 点击只读受限动作必须给出明确提示，**不能静默无响应**。
- 同一分组内保持业务顺序，不按使用频率或开发历史排序。
- **金额汇总一律以后端计算为准**，前端只展示。

**凭证入口**：合并为一张动作卡——标题「收付凭证」，说明「当前筛选 N 笔流水，可勾选生成凭证」，
次要动作「查看已有凭证」，主要动作「选记录生成凭证」；无可用流水时禁用，不进入空白选择模式。

财务分包实际页面 14 个：`ledger`（资金台账）、`receivables`、`receipts`、`payables`、`payments`、
`projects`（项目账本）、`project`（项目财务）、`partners`（供应商往来）、`entry`（财务登记）、
`project-picker`、`ledger-category-picker`、`vouchers`、`voucher-templates`、`voucher-template`。

### 10.3 主材选材闭环

**对象与归属**

```text
Property 房屋（唯一归属，propertyId 必填）
  └── MaterialSelection 主材选材记录（多版本）
        ├── designer 维护设计师
        ├── confirmerName / confirmedBy / confirmedAt
```

- 多房屋客户**必须显式指定房屋**，禁止串房。
- 草稿允许先建；**确认环节**要求已绑定合同或项目。
- 企业/门店/团队/负责人由登录员工复制，前端不可指定。

**状态与版本**

| 状态 | 进入方式 | 可编辑 |
| --- | --- | --- |
| `Draft` 草稿 | 保存草稿 | ✅ 原地保存 |
| `PendingConfirm` 待客户确认 | 提交客户确认 | ✅ 原地保存 |
| `Confirmed` 已确认 | 记录客户确认 | ❌ 修改即生成新版本 |

版本规则：未确认版本可原地保存；**已确认版本永久保留**，变更自动生成 `version+1` 新草稿；
「当前查看 = 版本号最大」。

**金额口径（强约束 —— 与钱完全解耦）**

| 维度 | 选材记录的影响 |
| --- | --- |
| 报价快照 / 合同金额 | **不变** |
| 成本 `ProjectCostContext` | **不参与、不改变** |
| 材料计划 / 采购 / 到货 / 库存 | **不生成、不修改** |
| 应收应付、利润 | **不变** |

> 验收口径：保存与确认选材后，上述对象逐字段不变。

**状态 × 角色 × 动作**

| 状态 | 设计师/管理者 | PM/履约 | 业务员/财务 | 业主 |
| --- | --- | --- | --- | --- |
| 草稿 | 编辑/提交/删除输入 | 只读 | 只读 | 不可见 |
| 待确认 | 编辑/记录确认 | 只读 | 只读 | 不可见 |
| 已确认 | 修改（生成新版本） | 只读 | 只读 | 不可见 |

### 10.4 合同增减项闭环

**对象**：`ContractChange`（变更单，1 张）+ `ContractChangeItem`（明细 1..n）

**五类变更**

| 类型 | 金额符号 | 成本符号 | 未开始/未采购联动 | 已开始/已采购联动 |
| --- | --- | --- | --- | --- |
| 增项 Add | 正 | 正 | 新增任务 + 材料计划 | 同左，保留原事实 |
| 减项 Remove | 负 | 负 | 任务转 Cancelled、材料计划转 Closed | 保留原事实，生成差异动态 |
| 替换 Replace | 净差额 | 净差额 | 关闭原范围，生成替代 | 保留原事实，生成替代范围 |
| 数量变更 Quantity | 差额 | 差额 | 直接调整未执行对象 | 保留原事实，生成差异对象 |
| 价格变更 Price | 差额 | 差额 | 直接调整未执行金额 | 保留原事实，生成差异对象 |

**强制口径**：无论哪类，**原报价与原合同行不变**，只更新合同 `currentAmount`、项目合同额及派生的应收/任务/材料/成本。

**状态机**

```text
[Pending 待审批] ──审批通过──▶ [Approved 审批通过] ──客户确认──▶ [CustomerConfirmed 客户已确认]（终态）
      │审批驳回                        │客户拒绝
      ▼                               ▼
[Rejected 已驳回] ◀───────────────────┘
      │
      ▼
[Cancelled 已取消]（仅 Pending 可撤回）
```

不可变规则：`CustomerConfirmed` 后不可编辑/删除/撤回；重复客户确认幂等；
已采购/已施工的事实**只可补偿，不可删除**；**客户拒绝不新增状态**，由发起方新建一张反向变更单走同一审批链。

**金额与成本口径**

```text
变更后合同金额 = 合同 currentAmount + Σ(变更单 amount)
变更后项目合同额 = 变更后合同金额
变更款应收 = amount（正数生成应收；负数冲减未收应收）
变更成本 = Σ(item.costDelta)
项目毛利 = 项目收入 − 项目成本
```

三条强制：① 成本缺失 → 毛利显示「成本未完整」，禁止 0；② 变更后合同金额 < 0 服务端拒绝；
③ 三种毛利（预计/动态/结算）不许混，页面须写明是「当前动态毛利」。

**权限红线**

- 发起：BOSS/店长/团队长/PM/设计师 ✅，财务 ✅，业务员 ❌，客户 ❌。
- 审批通过/驳回：**仅 BOSS 与财务**。
- **成本与成本变化对 PM / 设计师 / 业务员默认不可见**（整体隐藏，不显示 0 或 `--`）。
- **客户不登录小程序**：客户确认由 PM/负责人**现场代登记**（拍照 + 签名），不开放客户自助入口。
- 替换/数量/价格变更**必填原合同行**；增项/减项选填。
- 撤回仅 `Pending`，允许发起人本人或同团队负责人。

### 10.5 阶段验收整改闭环

**对象**：`ProjectStage` → `Acceptance`（1 阶段 1 张）→ `AcceptanceRound`（**append-only，不限条数**）

| 规则 | 口径 |
| --- | --- |
| 唯一归属 | 阶段级，`stage_id` 必填，不跨阶段 |
| 单据复用 | 同一阶段始终只有一张 `Acceptance`，轮次是子记录 |
| 追加不覆盖 | 每轮结论一旦写入**不可修改**，纠错只能发起新一轮 |
| 循环次数 | 无上限，`roundNo` 自然递增 |

**状态（三值，表示当前轮结果）**：`Pending` 待确认 / `Confirmed` 已确认 / `Rejected` 整改中。

**轮次流转**

```text
第 N 轮提交（Pending）
   ├── 业主确认 → Confirmed（阶段验收通过，闭环结束）
   └── 业主驳回 → Rejected（登记问题 + 整改责任人 + 截止日期）
            ↓ 现场整改
        第 N+1 轮提交（含整改说明与照片，Pending）→ 继续循环
```

关键不变量：同一阶段任何时刻**最多 1 个 Pending**；`Confirmed` 后不得再提交新轮次；
历史轮次的 `result/conclusion/confirmedAt` 不可修改；`roundNo` 不跳号。
重复提交幂等：已有 `Pending` 时直接返回该轮次，不新增。

**权限**：提交验收/整改反馈 = PM、履约专员、设计师（项目参与关系）；
登记整改责任人与截止 = PM、履约专员；
**业主确认/驳回 = 仅业主本人（授权会话），员工不得代录**。

**金额口径（强约束 —— 与钱完全解耦）**

| 维度 | 整改循环的影响 |
| --- | --- |
| 报价 / 合同金额 | **不变** |
| 项目成本 / 实际成本 | **不变**（返工成本不走系统，线下承担） |
| 应收 / 应付 / 结算 / 利润 | **不变** |
| 允许产生的派生指标 | 整改轮次数、整改时长、一次通过率（只读统计，**不写账**） |

### 10.6 五个闭环的研究结论

1. **两类闭环完全不碰钱**：主材选材、阶段验收整改。它们改变的是**事实与证据**，不是金额。
   Web 在这两处**不该出现金额汇总**，否则就是造伪。
2. **增减项是唯一会改合同金额的闭环**，且原报价/原合同行不可变，只累加派生值。
3. **Boss 的关心点不是台账，是"结论 + 风险 + 下一步"**：首页四指示灯带四态（含 unknown），
   风险项目必须给「建议下一步动作」。
4. **同一业务对象，不同角色的可见字段不同**（成本仅 BOSS/店长/团队长/财务），必须服务端过滤。
5. **确认主体按对象分权（2026-10-06 已裁决）**：
   - 增减项：**客户不登录小程序**，由 PM/负责人现场**代登记**签认，必须保留拍照与签名证据；
   - 阶段验收：**仅业主本人**确认/驳回，**员工不得代录**。
   两者针对不同对象，不是同一确认入口；`GAP-WEB-001` 已关闭，详见 `GAP台账.md`、`ANS-BIZ-20261006-001`、`DEC-015`。
