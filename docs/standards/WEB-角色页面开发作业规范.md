# Web 角色页面开发作业规范（角色能力包 v1.0）

> 状态：`生效（v1.1，2026-10-11 用户确认 v1.0；v1.1 由财务角色补第 5 类资产）`
> 适用对象：装得清家装企业 Web 工作台的全部员工角色 —— `Boss / StoreManager / TeamLeader / Marketer / Designer / Pm / Finance`
> 定位：把「设计师角色从 0 到可验收」的真实过程固化为**可复制的作业流水线**，用于后续角色页面开发。
> 适用场景：新增角色、角色新增页面、角色页面重构、存量角色回查。
> 上游依据（不重复其内容，只做编排与细化）：`WEB-建设核心思路.md`、`WEB-开发规范.md`、`WEB-工作台设计构建规范.md`（§14/§15/§16/§18）、`WEB-场景驱动工作台与多起点导航规范.md`、`WEB-沉浸式对象工作空间规范.md`、`WEB-客户场景三栏工作台规范.md`、`WEB-业务状态引导组件与接入规范.md`、`WEB-业务选择器与表单设计规范.md`、`WEB-业务概念全生命周期规范.md`、`WEB-业务状态机与闭环一致性规范.md`、`WEB-业务动作与闭环注册规范.md`、`WEB-业务指标与权限注册规范.md`、`WEB-业务页面系统注册规范.md`、`docs/standards/*.json`、`docs/product/roles/WEB-ALL-ROLE-BUILD-BOARD.md`、`docs/product/roles/WEB-ROLE-SCENARIO-MATRIX.md`、`docs/standards/WEB-治理迁移台账.md`。
> 边界：本规范**不新增、不修改任何业务口径**。对象、状态、动作、权限、金额、成本、利润一律以 `zhuangdeqing-business` 为准。

## 0. 一句话定义

**角色页面开发 = 以「一个角色的一条主链」为批次单元，按固定流水线 S0→S8 产出四类页面资产；每个阶段有明确准出物和门禁，跨角色可达性与读/写投影契约在编码前后各核对一次。**

一句话记法：**先冻结、后编码；先分类、后动手；本角色做完不算完，主链能交接才算完。**

---

## 1. 边界与不做什么

**做：** 角色工作台、场景工作台、对象工作面、承接层与工具页的规划、设计、实现、验收与知识回写。

**不做（越界即停）：**

1. 不改业务对象、状态、动作、权限、数据范围、金额/成本/利润口径 —— 回 `zhuangdeqing-business` 走 `T05 → T06/T12`。
2. 不新开 Web 专属 API/字段/状态/算法；只消费 App 已在使用的 Provider（`BLOCKED_PROVIDER` 时停止编码）。
3. 不做功能菜单堆砌与「从后端模型推导的增删改查页面」。
4. 不在 Web 端新增业主/客户侧入口（报价接受、验收确认属小程序/客户端边界）。
5. 不用 Mock / 空数组 / 本地布尔 / 旧值冒充「完成」。

## 2. 角色页面四类资产（先分类，再动手）

同一角色下的页面不是一种东西，**四类资产的验收口径不同**，混装是最常见的返工来源。

| 类别 | 定义 | 设计师实例 | 最低交付物 |
| --- | --- | --- | --- |
| **A 角色工作台** | 角色首页 / 经营总览，回答「今天先做什么」 | `/designer/workbench` | 主链站点、今日队列、角色场景卡、KPI 卡片、角色视角切换 |
| **B 场景工作台** | 「待我X」三栏，由服务端入站队列驱动 | 待我跟进 / 待我量房 / 待我设计 / 待我谈单 / 待我签约 | 三栏解剖、对象锚点、唯一主行动、状态引导、注册项 |
| **C 对象工作面 / 详情** | 以对象为中心的 360、工作区、台账面 | 客户 360、方案工作区、报价工作区、项目工地 | 锚点写回、信息块排序、承接层、动作回读、上下文恢复 |
| **D 承接层与工具页** | 抽屉/弹窗/全屏 + 低耦合独立工具 | 量房结论抽屉、报价表格、方案模版、报价项目库、我的业绩 | 表单五段、专用选择器、单据化确认、门禁 |
| **E 专业列表 / 对账台** | 以**筛选 + 明细 + 批量 + 汇总**为主的专业表格面（不是入站队列驱动的三栏） | 应收、应付、收款、付款、工人工资、员工工资、提成、退款、供应商往来、资金台账、项目账本 | 服务端汇总口径、批量选择与批量动作、分页与筛选写回 URL、页面级合计必须显式标注「当前页明细合计，正式汇总以服务端为准」 |

判定口径：

- A 回答「今天先做什么」；B 回答「怎么处理这一件」；C 回答「这个对象现在在哪一步」；D 回答「用哪个工具/怎么录入」；**E 回答「这一期的这笔账对不对」**。
- **E 类的判定要点**：它的第一性判据是**对账与勾稽**（来源、余额、期间、口径、凭证号），不是「对象现在在哪一步」；因此**禁止把 E 类页面按 B 类三栏工作台改造**（财务、对账、台账类角色的主要载体是 E）。
- **C 不得承担 B 的入站队列职责**；**D 不得成为主链的唯一入口**（独立工具页不占菜单主链语义时要显式降级到「经营与工具」组）。
- 类别判定必须在 S1 页面清单里逐页写清，禁止一个路由兼做两类。

## 3. 开发流水线 S0 → S8

> 与 `WEB-ALL-ROLE-BUILD-BOARD.md` 的批次状态机（`B0_* → BIZ_T05 → … → KNOWLEDGE_WRITEBACK → DONE`）一致；本节是**单角色视角的阶段细化**，把每个阶段的准出物与门禁写明。

### S0 · 事实与裁决（禁止编码）

- **输入**：业务卷宗、App 同对象页面、`docs/standards/APP-能力与理念研究.md`、现有合同/报价/项目真实数据。
- **动作**：整理「角色 → 对象 → 状态 → 动作 → 权限 → 金额影响」原始清单；对存在歧义或未冻结项提交 `T05`。
- **准出物**：`T06` 业务咨询答复或 `T12` 业务裁决与研发交接单；未裁决项登记为 `GAP`。
- **门禁**：**无 `T06/T12` 不得进入 S1**。缺少规则时停止，只允许调研、证据整理和需求澄清。
- **失败信号**：开始讨论交互细节、开始写组件、开始"先做个样子"。

### S1 · 页面清单与菜单信息架构冻结

- **动作**：产出角色的「页面清单」（按 §2 四类标注类别）；对齐 App 角色功能全清单，做覆盖度对照（App → Web）；按 `DEC-034 / BR-030` 拟定菜单（一级 ≤7 组、二级用场景语言、禁止模块 CRUD 命名）；列出本期做 / 不做 / 下沉。
- **准出物**：`WEB-<ROLE>-MENU-INFORMATION-ARCHITECTURE.md`（分析稿）+ `WEB-<ROLE>-MENU-FROZEN.md`（冻结稿，含裁决记录与命名对照表）。
- **门禁**：菜单唯一来源明确（现为 `src/roles/workbenchConfig.ts`）；每个菜单项都能指出承载页面与路由；未建页面标注状态而非静默省略。
- **设计师教训**：菜单与注册表曾出现「双来源漂移」——注册表里的条目从未出现在侧栏，侧栏是手写项。**必须以单一来源为准，并核对另一处是否已是死代码。**

### S2 · 注册表冻结（治理前置）

九张注册表 + 导航注册表必须**先于编码**冻结：

```text
docs/standards/business-concepts.json              业务概念（中文名/枚举/选择器）
docs/standards/business-state-machines.json        状态机与闭环一致性
docs/standards/business-action-policies.json       业务动作、权限、前置、幂等、reloadScopes
docs/standards/business-metric-definitions.json    指标公式、缺失值、数据范围
docs/standards/business-permission-policies.json   角色数据范围、敏感字段
docs/standards/business-page-states.json           页面状态
docs/standards/business-field-formats.json         字段格式
docs/standards/business-page-tasks.json            页面任务
docs/standards/business-acceptance-scenarios.json  验收场景
src/roles/routes.ts                                  角色路由集合（准入）
src/roles/workbenchConfig.ts                          角色静态菜单
src/roles/workbenchHome.ts                            角色首页场景卡片
docs/standards/WEB-工作台契约条款.md                  工作台业务条款（人读，机器不读）
```

- **准出物**：上述文件的新增/更新条目 + 变更清单。
- **门禁**：九项 `check:*` 全绿；动作的 `actionPolicyKeys`、`reloadScopes` 可追溯；未登记动作的页面只能显示「待业务确认」。
- **要点**：**注册表是页面的契约，不是文档**。页面实现完成后仍要回头核对注册表是否与实现一致（改实现必改注册表）。

### S3 · G1 迭代包（业务对齐）

- **动作**：按 `docs/product/designer/G1-迭代包.md` 的体例填写：边界与准入三问、≥2 个真实中小装企场景（含一人多岗）、页面生成公式、一级导航、业务闭环对齐、动作与 App 对齐清单、Provider 映射、权限矩阵、金额成本口径、可完成状态投影、待确认项。
- **准出物**：`G1-迭代包.md` + `iteration-packet.json`。
- **门禁**：每个 Provider 能指出 App 调用点，否则 `BLOCKED_PROVIDER`；`reloadScopes` 未登记写「待业务裁决」。

### S4 · G1.5 设计冻结

- **动作**：三栏解剖与中栏四段式、对象锚点、承载方式决策树、7 类状态设计、按钮层级 B1–B7、三档响应式、左栏队列高度与三栏协调、上下文连续与草稿守卫。
- **准出物**：`G1.5-设计冻结.md`（或等价文档）+ 组件与承接方式清单。
- **门禁**：符合 `WEB-工作台设计构建规范.md` §4–§14 强制项；表单符合 `WEB-业务选择器与表单设计规范.md` 五段分区；选择器为专用选择器。

### S5 · 实现

- **动作**：只实现冻结迭代包；一个批次只改一个角色的主链，禁止顺手重构其他角色。
- **准出物**：代码 + 页面文档 `docs/product/<role>/WEB-<ROLE>-*.md`。
- **门禁**：`npm run type-check`、`npm run build`、九项 `check:*` 全绿；遵守 §5 数据契约。
- **硬约束**：不做前端金额/成本/利润/完成度/状态计算；动作按服务端 `allowedActions` 与 `reloadScopes` 执行；未登记动作只能显示「待业务确认」。

### S6 · G2 渲染迭代（真实浏览器）

- **动作**：1440 / 1280 / 1024 三档实拍；量出中栏/左栏/右栏高度与 `pageScroll`；按 §14 反模式清单逐条批判；修正；**至少两轮**再渲染再批判。
- **准出物**：三档截图 + 渲染 JSON（含各栏高度与 `pageScroll`）+ 差距检查表。
- **门禁**：三档无横向溢出；三栏同屏 `pageScroll / viewport ≤ 1.4`；左栏底边与右栏对齐；控制台 0 error。
- **量化纪律**：用数据判断协调，不靠肉眼。

### S7 · G3 真实账号闭环验收

- **动作**：真实设计师账号 + 真实 Provider 数据，跑通本角色主链：正常 / 拒绝 / 越权 / 并发 / 闭环；写入后按 `reloadScopes` 回读；金额口径逐项核对。
- **准出物**：验收 run 目录 + 三档截图 + 网络/D B 对账 + `PASS / FAIL / BLOCKED / NOT_TESTED` 结论。
- **门禁**：Mock 数据**不得**计入 G3；未通过项必须显式登记，不得省略。

### S8 · 独立沉浸验收 + 知识回写 + 发布

- **动作**：由独立视角（非实现者）做换位审计；跨角色、跨端对账；产出问题台账；重大结论回写业务/过程知识库；按 `docs/operations/DEPLOY-BOUNDARY.md` 发布。
- **准出物**：独立审计报告 + 缺陷台账（P0–P3）+ 修复交付单 + 知识回写记录。
- **门禁**：P0/P1 未关闭不得宣称角色完成；未关闭的 `DEF-WEB-*` 不得被「全角色闭环已完成」掩盖。
- **纪律**：验收方**不得自行宣布业务验收通过**。

## 4. 十步构建法（单页 / 单工作台）

沿用 `WEB-工作台设计构建规范.md` §18.1，增加两步（可达性、投影契约）：

```text
1  认事实   读业务卷宗 + App 同对象页面，确认对象/状态/动作/权限，不凭记忆
2  选参照   以已达标工作台为参照，抽出「左队列 / 中对象 / 右引导」三栏骨架
3  定定位   一句话说清这个页面「是什么、不是什么」
4  写场景   ≥2 个真实中小装企场景（含一人多岗、多对象）
5  定入站   入站范围（角色/数据范围/阶段）+ 排序（逾期 → 今日 → 3 天内 → 未安排）
6  融信息   定义对象 Hero 融合哪些字段；划清与对象 360 的边界
7  定动作   唯一主行动 + 前置条件 + reloadScopes + 下一接棒；其余动作降级
7b 核可达   ★ 填 §6 可达性核对表：本页之后的每一步，谁、在哪端、哪个入口完成
8  做注册   workbench key / route / nav group / objectAnchor / task / acceptance scenario
8b 定投影   ★ 声明读模型来源与写模型回读方式（§5）：禁止用写响应覆盖读投影
9  渲染迭代 三档分辨率实拍 → 量高度与 pageScroll → 修正 → 再拍（至少两轮）
10 沉淀     写产品稿 + 更新规范 + 注册 AGENTS + 跑门禁
```

## 5. 数据契约（**本次新增细化 · 强制**）

> 来源：2026-10-11 设计师沉浸审计暴露的 3 个真实缺陷（XA-001 / XA-002 / XA-019）。

### 5.1 读模型与写模型分离

- **写操作（build / update / save / apply）的响应不等于页面的读投影。** 后端写接口多带 `@Properties` 白名单，只返回被改动的字段子集。
- **禁止**用写响应整体替换页面状态。正确做法：写成功后按 `reloadScopes` **重新拉取读接口**（`*/info`、`*/page`），或由后端返回完整投影后再替换。
- 反例（实测）：完成设计后前端用 `design/scheme/build` 响应覆盖方案 → 页面显示 0 个分项、¥0、按钮置灰，刷新才恢复。用户第一反应是「我的分项丢了」。
- 自查：页面中每一个 `xxx.value = resp.data` 都要能回答「这个响应是读投影还是写结果」。

### 5.2 摘要 / 抽屉必须复用服务端读投影

- 抽屉、弹窗、摘要条里展示的对象字段（电话、面积、户型、状态、负责人）**必须**来自与服务端同源的读投影，**禁止**前端从父页面局部变量拼装。
- 反例（实测 3 处复现）：安排量房抽屉、新建方案抽屉、发起合同抽屉把已有电话/面积/户型显示成「待补充 / 待确认」，而同一页客户 360 数据完整 —— 用户会怀疑「我刚才是不是没保存成功」。
- 自查：同一对象在同一屏出现两次以上时，字段值必须完全相同。

### 5.3 前端禁止自算

- 不计算金额、成本、利润、完成度、阶段、进度或状态机；不按 `status/stage` 拼状态文案或权限。
- 状态用 `BusinessStateTag`（未登记状态显示「待业务确认」）；下一步用 `NextActionPanel` 或等价服务端动作视图。
- 阶段关注字段业务口径未裁决前只能显示「待业务确认」。

### 5.4 Provider 映射与 `BLOCKED_PROVIDER`

- 每个 Provider 必须能指出 App 对应调用点；无法映射时标注 `BLOCKED_PROVIDER` 并停止编码。
- 低层远程选择壳只负责加载/分页/错误/回传，不得承载业务语义。

### 5.5 动作回读与部分确认

- 动作完成后必须按 `reloadScopes` 回读；回读失败显示「部分数据暂不可确认」。
- **禁止**用「暂无数据」「0」覆盖读取失败或部分确认；空数组不得伪装完成。

## 6. 跨角色与跨端可达性核对（**本次新增细化 · 强制**）

> 来源：设计师能独立跑通「客户→房屋→量房→设计→报价→提交客户确认」，但**在提交报价后主链断裂** —— 合同确认签约/生效在 Web 无入口、店长被路由守卫拒绝、业主确认必须小程序授权会话。这类问题**不是**本角色页面缺陷，但会直接让角色「做完却用不了」。必须在 S3/S4 之间强制核对。

### 6.1 主链责任矩阵（每个角色必填）

| 主链步 | 业务动作 | 责任角色 | 责任端 | 入口页面 | 可达性 | 证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 报价提交客户确认 | `quote/update(Accepted)` | 客户 | 小程序 | — | `BLOCKED_OWNER_SESSION` | 员工侧 403 |
| 确认合同签约 | `project/contract/update(Signed)` | Boss / StoreManager | Web | 待我签约 | `NO_WEB_ENTRY` | 无 `update` 调用 |
| … | … | … | … | … | … | … |

**准出要求**：本角色主链的每一步都必须写明「谁 / 在哪端 / 哪个入口 / 是否可达」。不可达的步骤必须登记断点类型，并在页面右栏给出**下一责任人**提示。

### 6.2 路由角色域一致性

注册表的角色范围必须与路由 `meta.roles`、视图可读范围一致。**核对三项**：

1. 注册表给该角色的入口，路由是否允许该角色进入；
2. 工作台上的入口链接，目标路由是否允许当前角色；
3. 数据范围（Company / Store / Team / Self / ProjectParticipant）是否与显示范围一致。

反例（实测）：店长工作台把「待我签约 / 待我谈单」放在 P0，点击 `href=/designer/contract` 直接跳 `/forbidden` —— 因为 `/designer` 路由组 `meta.roles` 缺 `StoreManager`。**产品让用户做的事，页面必须让他能进。**

### 6.3 断点分类（统一命名，禁止含糊）

| 类型 | 含义 | 处置 |
| --- | --- | --- |
| `NO_WEB_ENTRY` | Web 端根本没有该动作入口 | 补入口（若在 Web 责任范围内）或登记为跨端边界 |
| `ROLE_GUARD_DENIED` | 有入口但被路由/权限守卫拒绝 | P1 修复：对齐注册表与 `meta.roles` |
| `BLOCKED_OWNER_SESSION` | 必须业主/客户本人在小程序授权会话执行 | 属产品边界，不改；在 Web 显示责任人与去向 |
| `BLOCKED_PROVIDER` | Provider 无 App 调用点 | 停止编码，回后端/App 决策 |
| `BLOCKED_BIZ_DECISION` | 业务口径未裁决 | 提交 `T05`，页面显示「待业务确认」 |
| `API_SIMULATED` | 仅为验证后续链路而用接口模拟推进 | **必须显式标注**，不得计入 Web PASS |

### 6.4 完成后交接必须显式

- 本角色动作完成后，页面必须显示：去向、接棒人（下一责任角色）、下一状态、下游工作台。
- 反例（实测）：报价提交后页面变只读，只写「下一接棒：客户（决策）」，没有告诉设计师「该去找谁 / 我还能做什么」，体验上「停在原地」。

## 8. 验收证据协议

**目录与命名**（沿用既有约定，不覆盖历史）：

```text
docs/acceptance/runs/<run-id>/          run-id 形如 20261010-designer-project-site-refactor
  README.md                            本 run 的完成项、验证结论、数据说明、后续必须补验
  run.json                             机器可读结论（PASS/FAIL/BLOCKED/NOT_TESTED）
  raw/                                 原始证据（screenshots / network / sql / notes）
output/playwright/<role>-<topic>-<date>/  渲染截图与渲染 JSON
```

**四条硬性纪律：**

1. **Mock 标注**：用 Playwright 路由 Mock 只做「壳层 / 布局冒烟」，README 必须显式写明「**这不是 G3 真实数据验收，不代表功能已完成**」，并列出「后续必须补验」清单。
2. **三档强制**：1440 / 1280 / 1024；关键页面每档至少一张截图；`scrollWidth == clientWidth` 必须核对。
3. **负向强制**：涉及权限、金额、跨端、成本的改动必须带负向用例（拒绝/越权/并发/部分确认）。
4. **独立复核**：交付前由非实现者换位复核，复核结论单独成文，不替代原始发现文件。

**结论口径**：`PASS / FAIL / BLOCKED / NOT_TESTED` 四态必分，缺一不可；`BLOCKED` 必须写清阻塞原因与解除条件。

## 9.5 旧方案作废检查（强制 · 2026-10-11 新增）

**每当一个决定推翻/替代旧方案时，必须同批完成三件事**，缺一即为未完成：

- [ ] **定位旧方案所在的全部文档**（讨论稿、旧规范、旧注册表注释、旧评审记录），而不只是"最终稿"；
- [ ] 在旧文档**原位标注作废**：写明「本文 N 节已被 <新裁决/新规范> 取代，勿照此实施」，并指向新出处；
- [ ] 若是**讨论稿**且含与最终裁决相反的待裁决问题，必须逐条标注结论（否则几轮后会以"我们不是定了 X 吗"的形式回来）。

**为什么强制**：本工程已三次因旧表述误导（`EXP-015`）：台账表头已 CLOSED 而正文仍写"待裁决"；场景矩阵仍标 OPEN；设计器菜单**讨论稿**的 Q1 写着与最终裁决相反的"菜单唯一来源=注册表"，导致后续会话误以为"注册表该删"。

**判据**：新裁决落地后，用旧方案关键词全局检索一次；命中处非"已标注作废"即为不合格。
