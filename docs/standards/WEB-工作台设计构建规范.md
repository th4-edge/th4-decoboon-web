## 0. 一句话定义

```text
工作台 =
  入站队列
  + 对象工作面（对象 Hero + 当前阶段关注）
  + 唯一主行动
  + （为什么现在做 → 做完去哪）
```

工作台不是业务对象，不是模块页面，也不是"某个实体的增删改查入口"。它只回答一件事：

> **此刻轮到我处理什么，我该对哪一个对象做什么，做完交给谁。**

## 1. 从「待我跟进」「待我量房」提炼的设计思想

以下 11 条是本次规范的核心，是后续所有工作台的共同判断标准。

### S1 · 以"我"为中心的入站队列，不是模块台账

- 命名用使用者语言："待我跟进""待我量房""待我报价""待我收款"，禁止"客户管理""量房管理"等模块式命名。
- 队列只放**进入当前角色、当前场景入站状态**的对象。
- 徽标只统计"需要我处理"的数量或风险，不显示与我无关的总量。

### S2 · 先给结论，再给动作

- 工作台开头用一句话说明这段工作怎么干，例如：
  - 待我跟进："先看客户是谁、住在哪里、沟通到什么程度，再记录本次跟进和下次联系时间。"
  - 待我量房："先看任务队列，再确认客户与房屋，最后完成唯一主行动并交接到设计。"
- 页面首屏要先告诉用户"该做什么"，而不是先给一堆字段。

### S3 · 三栏回答三个问题

| 栏位 | 回答的问题 | 承载内容 |
| --- | --- | --- |
| 左栏 · 队列 | 现在有哪些对象需要我处理？ | 入站对象卡片、身份、锚点、状态、原因、时间 |
| 中栏 · 对象工作面 | 当前选中的对象真实事实是什么？ | 对象 Hero、当前阶段关注信息、当前场景所需事实 |
| 右栏 · 状态引导 | 为什么现在处理、能做什么、做完去哪？ | 原因、唯一主行动、阻断、完成后回读、下一接棒 |

三栏职责不得互相复制。尤其是**主行动只能出现在右栏**。

### S4 · 对象锚点显式且唯一，主对象随场景切换

- 待我跟进：**主对象 = 客户**，房屋作为 `activeProperty` 子锚点，需要量房/设计时才显式选择房屋。
- 待我量房：**主对象 = 房屋**，客户降为归属信息（"客户"是卡片上的次要字段）。
- 同一条业务链在不同场景可以换主对象，但**同一场景的主对象必须唯一**。
- 锚点必须写进深链接、路由、刷新恢复和抽屉上下文；未指定时不得默认第一条。

### S5 · 唯一主行动，动作策略来自服务端

- 右栏只突出一个视觉最重的主按钮。
- 主行动文案、可用性、阻断原因来自服务端投影（如 `mainActionLabel` / `allowed` / `blockReason`），前端只负责渲染。
- 其余动作降级为"其他合法动作"，不得与主行动同权。
- 前端**禁止**按 `status` / `stage` / 日期自行推导下一步。

### S6 · 以"为什么现在处理"开头

- 右栏第一块先给原因，再给按钮：`riskReason` / 入站原因 / 到期状态。
- 队列卡片也要带一行原因，让用户不点开就知道为什么它在列表里。
- 原因缺失时显示"待业务确认"，不得用默认文案掩盖。

### S7 · 动作完成必须回读 + 交接，不自动跳走

- 动作成功后按 `reloadScopes` 回读关联对象。
- 完成后显示：去向、接棒人、下一状态、下游工作台。
- "下一项"只能由用户**显式点击**；不得在动作完成后自动切换对象，避免用户不知道刚操作了谁。
- 任一回读失败显示"部分数据暂不可确认"，不得用旧值、空数组或 0 伪装完成。

### S8 · 上下文连续，禁止二次搜索

- 从队列点一条 → 直接进入对象工作面，同一页内不允许再搜索一遍同一对象。
- 多字段表单用右侧抽屉承接，抽屉顶部先展示客户/房屋上下文，再展示录入区。
- 刷新、浏览器前进后退、深链接必须恢复：对象 + 子对象 + 工作面 + 必要筛选。
- 关闭抽屉后焦点和滚动位置回到进入前。

### S9 · 一屏完成，信息密度分级

- `1440×900`、`1280×900` 下，左队列、中对象事实、右主行动与全部关键操作必须在**一个屏幕内**可见。
- 队列内部可滚动，但页面关键操作不得因列表增长被推出首屏。
- 事实用摘要 + 分组 + 展开承载，禁止把每个字段拆成独立卡片。
- 空态、异常态、无权限、规则未命中都必须有设计，不能只做正常态。

### S10 · 状态表达统一

- 复用 `StatusTag` / `BusinessStateTag`，未登记状态显示"待业务确认"。
- 状态必须"文字 + 颜色 + 位置"共同表达，禁止只靠颜色区分类别。
- 同一业务事实在 App 与 Web 必须同源同口径。

### S11 · 中栏 Hero 按"当前阶段"聚焦，不做字段平铺

- 中栏 Hero 不是对象档案页，它只回答一个问题：**在当前阶段推进这个对象，我最需要看哪几条事实？**
- 不同阶段重点不同（见 §4.2）；重点字段 ≤4 个，放第一视觉层；其余降级为背景或折叠。
- 重点字段由服务端 `stageFocus` 投影给出，前端不得按阶段自行拼重点。
- 阶段重点缺失时显示"待业务确认"，不得用全量字段平铺掩盖。

## 2. 工作台标准解剖（Anatomy）

所有工作台按下面的纵向结构组装，顺序固定：

```text
① 工作台头 header
   eyebrow（领域 · 场景） / 标题（待我X） / 一句话任务说明 / 队列总量与风险计数 / 刷新

② 工具条 tools
   搜索（按对象身份字段） + 队列筛选（按入站维度） + 计数

③ 三栏主体 layout
   左栏 队列 queue
   中栏 对象工作面 workSurface = 对象 Hero + 当前阶段关注 + 场景事实
   右栏 状态引导 guide

④ 全局反馈 feedback
   动作错误 / 上下文部分错误（"部分数据暂不可确认"）/ 恢复路径

⑤ 承接层 carry
   就地操作 / 抽屉表单 / 确认弹窗 / 全屏工作区 / 安全门
```

### 2.1 各区块职责

| 区块 | 必须 | 禁止 |
| --- | --- | --- |
| 工作台头 | 场景标题、任务说明、队列量、风险/到期计数、刷新 | 经营大屏指标、与当前队列无关的统计 |
| 工具条 | 搜索 + 入站维度筛选 + 计数 | 把筛选做成第二套导航、隐藏当前筛选态 |
| 左栏队列 | 身份、锚点、状态、原因、时间、选中高亮 | 承载主行动或操作引导（见 §4.1） |
| 中栏工作面 | 对象 Hero 身份 + 当前阶段重点（≤4）+ 场景事实 + 子锚点显式选择 | 复制右栏主行动、堆砌与当前阶段无关的历史 |
| 右栏引导 | 原因 → 唯一主行动 → 完成回读 → 其他动作 → 下一接棒 → 下一项 | 多个同权主按钮、前端自算状态 |
| 承接层 | 抽屉顶部带上下文、失败可恢复 | 抽屉叠抽屉、弹窗叠弹窗 |

### 2.2 页面独立性：统一的边界（强制）

**每个工作台 = 独立路由 + 独立页面组件 + 独立注册项。**

禁止用一个页面靠参数分发多个"业务语义不同"的工作台（例如 `/designer/customers?surface=followup|measure`）。
业务语义不同的工作台必须各有自己的路由、组件，并在三份静态源（`routes.ts` / `workbenchConfig.ts` / `workbenchHome.ts`）各自声明，否则会出现：

- URL 语义错位（`?surface=measure` 的主对象其实是房屋）；
- 标题 / 面包屑 / 埋点要靠 `if surface` 特判，加一个工作台要改多处；
- 路由级 `meta.title` / `meta.roles` / 懒加载无法按工作台切分；
- 注册表的 `deepLink` 与真实路由不是 1:1，且按 `path.split('?')[0]` 去重时会互相顶掉。

**统一边界**：

| 层 | 是否统一 | 说明 |
| --- | --- | --- |
| 设计规范（本文件） | **统一** | 信息权重、状态表达、交互时序、验收 |
| 设计系统（`tokens.scss` + 通用组件） | **统一** | 色彩 / 字阶 / 间距 / StatusTag / WorkbenchState / 抽屉组件… |
| 几何骨架（三栏栅格、队列高度预算、sticky、断点） | 可收敛 | **已收敛到 `src/styles/workbench-shell.scss`**（`workbench-layout / workbench-queue / workbench-queue-scroll / workbench-workspace / workbench-guide`）。只含几何、不含业务语义，页面 `@include` 后可自行覆盖；队列卡片、Hero、引导面板仍由各页实现 |
| 对象 / 状态 / 动作 / 字段 / 锚点 / 主行动 / 信息权重 | **禁止统一** | 各页自有，按 §4.5 各自取舍 |


**菜单来源（2026-10-09 裁决，见 `GAP台账.md` GAP-WEB-013）**：

| 角色 | 来源 | 职责 |
| --- | --- | --- |
| **菜单唯一来源** | `src/roles/workbenchConfig.ts`（静态） | 每个菜单项显式给出 `key / label / path`，分组与顺序由各角色静态定义 |
| **角色静态源（唯一来源，不参与运行时判断）** | `src/roles/routes.ts` / `workbenchConfig.ts` / `workbenchHome.ts` | 路由集合 / 菜单 / 首页卡片；由 `check:workbenches`＋`check:workspaces` 校验 |
| **业务条款（人读，机器不读）** | `docs/standards/WEB-工作台契约条款.md` | 原注册表条款归档：入站状态 / 上下文恢复 / 未保存保护 / 状态→主行动… |

菜单按角色**逐角色静态重建**（Designer 已作为样板），迁移期缺 label/path 的项由 `RoleSideNav` 回退查注册表；
**全部角色显式化后必须删除该 shim**。迁移工具：`npm run audit:menus` / `npm run audit:menus:report`。
原注册表派生菜单（`sidebarNavForRole`）与 `WorkbenchLayout.vue` 已下线，不得复活为第二套菜单来源。
详见 `GAP台账.md` GAP-WEB-013。
**迁移与兼容**：历史上参数化的路由必须保留 302 重定向（保留查询参数），旧深链接、书签、已发布客户端不得失效。

## 3. 主对象与锚点判定

判定原则：**主对象 = 当前场景下使用者要推进并要做决策的那个对象；归属对象降级为上下文。**

| 业务链阶段 | 主对象 | 子锚点 | 队列卡片第一视觉 | 中栏 Hero |
| --- | --- | --- | --- | --- |
| 客户跟进 / 邀约 | 客户 | `activeProperty`（可空） | 客户姓名 | 客户 Hero |
| 量房 | 房屋 | 客户（归属信息） | 房屋名称 / 地址 | 房屋 Hero |
| 设计 / 报价 | 房屋（或方案） | 客户 + 版本 | 房屋 / 方案 | 方案 Hero |
| 项目 / 施工 | 项目 | 阶段 / 任务 | 项目名称 | 项目 Hero |
| 验收 / 整改 | 项目（或验收单） | 房屋 + 阶段 | 项目 / 验收单 | 验收单 Hero |
| 财务 | 项目 / 单据 | 应收应付 / 台账对象 | 单据编号 / 项目 | 单据 Hero |

### 3.1 锚点规则

1. 客户主线：客户 + `activeProperty`；多房屋必须显式选择，未选择时显示选择提示。
2. 项目主线：项目 + 当前阶段 / 任务 / 单据。
3. 财务主线：项目 + 应收应付 / 收付款 / 台账 / 凭证对象。
4. 队列类工作台：队列 + 选中对象。
5. 锚点必须写入路由和上下文恢复状态；未指定时不得默认第一条。

## 4. 三栏职责边界（强制）

### 4.1 左栏 · 队列

- 只展示当前角色、当前数据范围、当前场景入站状态内的对象。
- 列表项必须同时表达**对象身份 + 锚点**；没有子锚点时明确显示"待补充"，不得伪造。
- 以房屋为主对象的场景，卡片第一视觉层级展示房屋（名称、小区/地址、面积/户型），客户降为归属信息。
- 卡片带一行**入站原因 / 风险原因**，让用户不点开也能判断优先级。
- 排序、风险原因、在途状态以服务端聚合/投影为准，前端只做已裁决的筛选切换。
- 当前选中项必须高亮。
- **左栏不展示操作引导、主行动或完成回读**；这些统一放右栏（统一两页现状差异）。
- 空态必须说明为什么为空、如何恢复或刷新，不得只显示"暂无数据"。

#### 4.1.1 待我设计左栏：客户分组 + 房屋子卡（强制）

待我设计的业务锚点是 **客户 + 房屋 + 方案**，左侧不得沿用“客户列表 + 中栏再选房屋”的流程。

**唯一业务源**：复用 App 已有 `statistic/workbench/design/page`。该 Provider 返回客户 + 房屋级平铺事实；Web 仅按 `custId` 做展示分组，不得据此合并或删除房屋。

**入队规则**：

1. 仅接收已有完成量房事实的房屋（`measureAt != null`）；只有预约量房时间的房屋留在待我量房。
2. 一个客户可以有多套房屋，每套房屋必须独立成为一张子卡。
3. 同一房屋可以有多套设计方案；方案加载必须先确定 `activePropertyId`，再加载该房屋下的方案。
4. 左侧计数按**房屋数**和**客户组数**同时表达，不得只显示客户数。

**选择规则**：

| 操作 | 结果 |
| --- | --- |
| 点击客户分组头 | 默认选中该组服务端排序第一的房屋 |
| 点击房屋子卡 | 精确选中 `customerId + activePropertyId` |
| 筛选 / 搜索后当前对象仍在结果中 | 保持当前选择 |
| 筛选 / 搜索后当前对象不在结果中 | 自动切到新结果第一套房屋；结果为空则清空中栏与右栏 |
| 方案卡片点击 | 进入该方案工作台；方案推进、编辑、报价等操作不在队列页执行 |

**中栏承接**：左侧一旦确定 `activePropertyId`，中栏「房屋」块只展示当前房屋摘要、量房输入与维护/登记入口，不再重复渲染房屋选择器，也不提供新增房屋；之后按「设计方案 → 诉求 → 跟进」顺序展开。

**禁止**：客户级 `customer.measured` 前端过滤、客户级方案池自动选第一套、选中客户后不明确房屋就开始加载方案、中栏第二次选择房屋。

### 4.2 中栏 · 对象 Hero 与阶段关注

中栏由三段组成，顺序固定：

```text
① 对象 Hero 身份层     —— 我是谁、在什么状态、归属谁
② 当前阶段关注层       —— 推进这个对象此刻最需要看的 2–4 条事实
③ 场景事实层           —— 该场景需要的业务面板（沟通记录 / 量房证据 / 方案 …）
```

#### 4.2.1 Hero 结构分层

| 层 | 内容 | 视觉处理 |
| --- | --- | --- |
| L0 身份层 | 主对象名称 + 状态标签 + 风险/等级 + 归属对象一句话 | 最大字号，单卡片顶部 |
| L1 阶段关注层 | 当前阶段重点字段（≤4），只放决定下一步和风险的事实 | 强调：品牌浅底 / 数字 tabular-nums / 语义色 |
| L2 背景事实层 | 支持判断但不主导动作的字段（面积、预算、负责人…） | 小字、次级色 |
| L3 折叠层 | 低频 / 历史 / 完整档案字段 | 不占首屏，进"查看全部"或对象档案 |

**硬约束**：Hero 是**一个卡片**，L0–L2 在卡片内分层融合，禁止把每个字段拆成独立卡片。

#### 4.2.2 阶段关注矩阵（机制）

Hero 的重点字段不是固定字段表，而是随阶段变化，由服务端投影给出：

```ts
// 服务端 stageFocus 投影（契约，字段名待接口冻结）
interface StageFocusView {
  objectKey: string          // customer | property | project ...
  status: string             // 当前阶段
  focusFields: Array<{
    key: string              // 业务字段键
    label: string            // 中文标签
    value: string | number | null
    emphasis?: 'default' | 'warning' | 'danger' | 'success'
    unit?: string
  }>                        // ≤4
  backgroundFields?: Array<{ key: string; label: string; value: string | null }>
  updatedAt?: string
}
```

规则：

- 前端只渲染 `focusFields`，**不得**按阶段在前端拼重点字段。
- `focusFields.length > 4` 视为投影错误，前端只取前 4 并记录告警。
- 重点字段值缺失 → 显示"待补充"，不编造。
- `emphasis` 为 `warning/danger` 时，必须同时有文字，不得只靠颜色。

#### 4.2.3 分阶段重点（建议默认，需 T05/T06 裁决）

> **字段与阈值必须经 `zhuangdeqing-business` 裁决后才能冻结**，未裁决前只能显示"待业务确认"。

#### 4.2.4 客户 Hero 与房屋 Hero 的构成

> 字段清单以 §4.7「对象 Hero 家族」为准；本节只保留工作台侧的融合要求。

**客户 Hero（参考「待我跟进」）必须融合：**

- 姓名、阶段、风险、评级/评分等级色；
- 联系电话、来源、小区/地址、面积、预算、负责人、设计师；
- 是否加微信、到店次数、最近到店、客户标签摘要；
- 客户画像摘要（装修目的、开工窗口、风格偏好、决策方式、关注点），支持在当前页完善；
- 至少一个"完整档案"次级入口，但当前起点动作（写跟进、记录微信、记录到店）不得被强制转到客户 360。

**房屋 Hero（参考「待我量房」）必须融合：**

- 房屋名称/小区/楼栋/房号/地址、状态、风险；
- 面积、户型、原始结构摘要；
- 量房进度（预约/已量/待补），现场照片、结构图、附件数量；
- 客户归属信息（姓名、电话）降为一行；
- 量房结论与设计可用性摘要；
- 当前场景不展示成本与利润。

#### 4.2.5 Hero 视觉与信息融合规则

1. 单卡片，顶部身份行 + 中间阶段关注条 + 底部背景事实，禁止拆卡。
2. 身份行：名称（`$font-title`）+ 状态标签 + 风险/等级标签，左对齐；子对象锚点摘要紧随其后。
3. 阶段关注条：2–4 个等宽单元，标签在上（`$font-caption`），值在下（`$font-body`，数字 `tabular-nums`）；`warning/danger` 用语义色 + 文字。
4. 背景事实条：小字次级色，一行最多 5 项，超出进"查看全部"。
5. 头像/图标只做识别，不承载信息。
6. 多子对象（房屋）在 Hero 内显式选择，未选择显示选择提示，禁止默认第一条。
7. Hero 高度受控：在 1440×900 / 1280×900 下 Hero + 右栏主卡片 + 全部关键操作必须同屏。

#### 4.2.6 Hero 反模式

1. 把对象所有字段都平铺进中栏。
2. 每个字段一张卡 / 一个指标卡。
3. 不同阶段用同一套字段，不体现当前重点。
4. 前端按阶段自行拼重点字段。
5. 未选子锚点默认第一条。
6. Hero 里塞主行动按钮，与右栏冲突。
7. 只靠颜色标记风险，没有文字。
8. 长文本不截断、不折叠，把关键事实挤出首屏。

### 4.3 右栏 · 状态引导

固定按以下顺序组织：

1. **为什么现在处理**：服务端风险原因、到期状态或入站原因。
2. **唯一主行动**：只突出一个主按钮（按钮层级见 §6）；服务端未允许时禁用并显示阻断原因。
3. **完成后的回读**：动作成功后必须重新读取的范围。
4. **其他合法动作**：联系客户、打开对象档案、进入下一场景等，降级为次级按钮。
5. **下一接棒**：完成后去向、下一状态和下一位责任人；没有下一对象时显示空态。
6. **下一项切换**：只能由用户显式点击，动作完成后不得自动切换。

### 4.4 客户信息与客户诉求板块（强制）

**客户诉求是客户事实，不是独立工作台**。`DesignRequirement`（诉求 / 排斥点）属于客户，必须能在客户经营与量房工作台内直接看到并记录。

> 适用范围：本条适用于**客户 / 房屋仍是当前重点**的工作台（待我跟进、待我量房）。
> 进入设计、报价、签约阶段后，客户四项按 §4.5 降为**弱化**，不得继续铺开四板块挤占当前阶段业务重点。

规则：

1. **客户为主对象的工作台**（待我跟进）：中栏在 Hero 之下增加「客户诉求」板块，展示该客户前 N 条诉求（标题 / 类型 / 分类 / 优先级 / 空间 / 说明），并提供「记录诉求」入口。
2. **房屋为主对象的工作台**（待我量房）：中栏除房屋 Hero 外，必须提供「客户信息」板块，固定四块：
   `基本信息 / 客户画像 / 跟进信息 / 诉求信息`。
3. 两处都必须提供「客户诉求」操作按钮（图标 + 文字），统一使用 `src/components/design/RequirementFormDrawer.vue`，走既有 Provider `design/requirement/save`，**不新开 API**。
4. 诉求标签（类型 / 分类 / 优先级 / 状态）统一取自 `src/domains/design/requirementOptions.ts`；画像展示统一取自 `src/domains/crm/portrait.ts`，禁止各页再复制一份中文表。
5. 客户画像、跟进、诉求读取失败时按 §10 表达"部分数据暂不可确认"，保留已成功区块，不得用空数组伪装"没有诉求"。
6. 诉求数量与内容来自服务端投影，前端不得自行推断客户"已确认/已落实"。

**反模式**：把客户诉求做成只能从独立菜单进入的队列页；在中栏只给"诉求 N 条"数字而不给内容；各页各写一套诉求中文标签。

### 4.5 阶段驱动的信息权重（强制）

**核心规则**：不同阶段，使用者关注的业务点与业务概念不同；工作台必须**有层次、有目标**地呈现，而不是每页都铺同一套信息。

同一客户在业务链上依次经过：

```text
客户 → 房屋 → 方案 → 报价 → 合同
```

**越靠后阶段，焦点越交给下游对象；上游对象降为一行归属信息——可追溯，但不与焦点同权。**

#### 4.5.1 权重阶梯（按工作台）

| 工作台 | 客户基本信息 / 画像 / 跟进 / 诉求 | 房屋 / 量房 | 设计方案 | 报价 | 合同 | 焦点对象 |
| --- | --- | --- | --- | --- | --- | --- |
| 待我跟进 | **重点** | 常规（可为空） | — | — | — | 客户 |
| 待我量房 | **重点**（Hero 下方完整呈现，不进 L1） | **重点**（进 Hero L1） | — | — | — | 房屋 |
| 待我设计 | 弱化 | **重点** | **重点** | 常规 | — | 方案 |
| 待我报价 | 弱化 | 常规 | **重点** | **重点**（含报价调整） | — | 报价 |
| 待我签约 | 弱化 | 常规 | **重点** | **重点** | **重点** | 合同 |

#### 4.5.2 三档权重怎么呈现

| 权重 | 呈现位置 | 具体形态 |
| --- | --- | --- |
| **重点（L1）** | 中栏 Hero 的 L1 阶段关注层（§4.2） | ≤4 项，品牌底/大号数字，占首屏上半部；右栏主行动围绕它 |
| **重点（支撑）** | Hero 下方的完整板块 | 完整呈现该阶段仍高频使用的信息（如量房阶段的客户四项），但不得做成第二个 L1 |
| **常规** | Hero 的 L2 背景层 | 一行小字事实（面积、负责人、版本号等），不与重点抢视线 |
| **弱化** | Hero 之外的一行归属信息 | 一句话摘要（`客户名 · 电话 · 房屋`）+「查看客户信息 / 完整档案」入口；**不占 L1/L2，默认不铺四板块** |

> 弱化的落地实现：**默认折叠 + 按需展开**。默认只渲染一行归属摘要；
> 用户主动点「展开客户信息」后才显示完整区块（基本信息 / 画像 / 跟进 / 诉求），再点「收起」回到一行。
> 这样既保证"当前阶段重点不被挤掉"，又保证"弱化 ≠ 删除"（§4.5.3 第 1 条）。

#### 4.5.3 硬约束

1. **弱化 ≠ 删除**：被弱化的对象必须保留可追溯入口（一行摘要 + 完整档案 / 抽屉），不得从页面上消失。
2. **L1 只允许一组"重点"**：中栏 Hero 的 L1 阶段关注层一次只能聚焦一个业务概念组，否则等于没有重点。
   支持性信息（如待我量房阶段的客户四项）放在 Hero 下方**完整呈现**，不进入 L1，也不与 L1 抢视觉。
3. **重点随主行动走**：右栏唯一主行动操作哪个对象，中栏 L1 就必须聚焦该对象的事实。
4. **对象链可读**：中栏必须能看出该对象在 `客户 → 房屋 → 方案 → 报价 → 合同` 上的位置与上下游关系。
5. **归属信息一行化**：上游对象统一压成一行（名称 + 关键联系 + 阶段），不得保留完整四板块。
6. **跨页一致**：同一对象在不同工作台的"重点/常规/弱化"由本表统一决定，页面不得自行提高或降低权重。

#### 4.5.4 参考实现（五段权重已落地）

| 工作台 | 文件 | 重点（L1） | 客户归属 |
| --- | --- | --- | --- |
| 待我跟进 | `DesignerFollowUpTasksView.vue` | 下次联系 / 最近沟通 | Hero 内完整呈现 |
| 待我量房 | `DesignerMeasureTasksView.vue` | 预约情况 / 量房时间 / 现场准备 | Hero 下方完整板块 |
| 待我设计 | `DesignerDesignWorkspaceView.vue` | 方案阶段 / 设计进度 / 方案金额 / 报价状态 | `DesignSchemeContext` 一行 |
| 待我报价 | `DesignerQuoteListView.vue` | 报价阶段 / 报价金额 / 客户决策 | 一行归属 + 按需展开 |
| 待我签约 | `DesignerContractHandoffView.vue` | 合同/报价/方案事实 | 一行归属 + 按需展开 |

待我设计的量房输入并入当前房屋卡：摘要展示量房时间、状态、设计师结论和证据数量，原始结构 / 尺寸 / 客户诉求按需展开；不再单独占一个中栏业务块。

#### 4.5.5 反模式

1. 待我设计/报价/签约仍把「基本信息 / 客户画像 / 跟进信息 / 诉求信息」四板块全量铺开。
2. 把客户信息与当前阶段业务信息做成同等视觉权重。
3. 弱化时直接删除客户归属，导致无法追溯"在给谁做设计/报价"。
4. 同一页出现两个"重点"区域。

### 4.6 中栏信息架构（唯一 Hero + 关注度排序，强制）

> 与《WEB-沉浸式对象工作空间规范》的关系：该规范的"对象身份条 + 当前工作面"在本规范中细化为
> **① 唯一 Hero + ② 业务信息块**；两者不冲突。
> 2026-10-09 用户裁决修正：中栏**只允许一张 Hero**，对象不再单独成 Hero。

中栏固定为：

```text
① 唯一 Hero          客户为基准形态；本页对象信息**追加到标题行**（如"· 恒大绿洲3栋1802 [已量房]"）
② 本页业务信息块      按关注度依次排列，含跨阶段事实（客户诉求 / 跟进记录）
③ 历史与时间线        折叠，不占首屏
```

**硬约束**：

1. 中栏**只允许一张 Hero**；禁止出现第二张 Hero（关联对象不再单独成 Hero）。
2. Hero 主体形态统一为**客户 Hero**：客户身份 / 客户标签 / 客户画像 / 编辑基本信息；
   本页对象（房屋 / 方案 / 报价 / 合同）以"**标题行追加 + 一个业务信息块**"补充，**不改主体**。
3. L1 关注层按页面插槽传入（§4.5），不由对象类型决定。
4. ② 的块按**关注度**排序（**主行动依据优先**）；块的集合与顺序由各页自定义，
   跨阶段事实（客户诉求 / 跟进记录）按 §4.5 权重落在其中。
5. Hero 只给**结论**，② 给**明细**；同一事实不得在 Hero 与 ② 之间做等重重复（允许"结论 vs 明细"）。

**每页对照**：

| 页面 | ① 唯一 Hero | ① 标题行追加 | ② 业务信息块（按关注度） |
| --- | --- | --- | --- |
| 待我跟进 | 客户 | — | 装修房屋 → 最近沟通 → 客户诉求 |
| 待我量房 | 客户 | 本次房屋 | 预约量房信息 → 房屋信息 → 诉求信息 → 跟进信息 |
| 待我设计 | 客户 | **当前房屋（标题前置）+ 方案名/版本/方案状态（标题追加）** | **房屋（当前房屋摘要 + 量房输入，不再重复选择/不新增房屋）→ 设计方案（状态卡片）→ 诉求信息 → 跟进信息** |
| **待我谈单**（原待我报价） | 客户 | **报价编号 + 版本 + 报价状态**（标题行追加） | 方案信息 → 报价信息/调整 → **谈单资料（谈单 PPT · 报价 PDF）** → 诉求信息 → 跟进信息 |
| 待我签约 | 客户 | **合同编号 + 报价编号 + 合同状态**（标题行追加） | 合同信息 → **签约资料（方案 · 谈单 PPT · 报价 PDF · 合同 PDF）** → 诉求信息 → 跟进信息 |

### 4.7 唯一 Hero 与标题行对象信息（强制）

Hero 只有**一种形态**：客户 Hero。各页在本页语境下把对象信息**追加到标题行**。

```text
ObjectHeroCard（唯一骨架，唯一实现）
├── L0 主体身份        客户名 / 评级 / 阶段 / 风险 / 电话
├── 客户标签行         已加微信 / 到店次数 / 客户标签
├── 标题行追加（可选）  · 房屋名「明细」+ 状态标签
├── L1 当前阶段关注层   页面插槽传入（§4.5 / §4.6）
├── L2 背景事实层       客户事实（面积 / 预算 / 负责人 / 设计师）+ 客户画像
└── footer             编辑客户基本信息
```

**标题行追加内容**（`#title-extra` 插槽，紧随客户名/评级/阶段/风险标签之后）：

| 页面 | 标题行追加 | 形态 |
| --- | --- | --- |
| 待我量房 | `恒大绿洲「3栋 1802」 林女士 [已量房]` | **房屋名（小区）** + 「楼栋 房号」+ **客户名** + 客户阶段/风险标签 + **房屋状态标签**；房屋信息在客户名**之前** |
| 待我设计 | `· 现代简约方案 V2 [待谈单]` | 方案名 + 版本 + 方案状态标签 |
| 待我报价 | `· BJ-2026-001 V3 [待客户决策]` | 报价编号 + 版本 + 报价状态标签 |
| 待我签约 | `· HT-2026-001 [待生效]` | 合同编号 + 合同状态标签 |

实测（待我量房）：

```text
标题行  恒大绿洲「3栋 1802」  林女士  A级客户  跟进中  待确认  ·  已量房
        └─房屋名─┘└─明细─┘  └客户名┘  └────── 客户标签 ──────┘   └房屋状态┘
字号    20px / 700   20px / 600   18px / 700
```

**字形规则（对象优先）**：

| 元素 | 字号 | 说明 |
| --- | --- | --- |
| 对象名（房屋名 / 方案名 / 报价号 / 合同号） | `$font-h1`（20px）· 700 | **大于客户名** |
| 「明细」（楼栋房号 / 版本 / 状态补充） | `$font-h1`（20px）· 600 | 与对象名同级，颜色降为次级 |
| 客户名 | `$font-title`（18px）· 700 | 基准字号，不再放大 |

即：**对象信息在客户名之前，且字号大于客户名**——保证"先看对象、再看客户"的阅读顺序。

> 待我量房（及后续页面）把对象信息放在**客户名之前**，形成"先看对象、再看客户"的阅读顺序。

**硬约束**：

1. 中栏只允许一张 Hero；**禁止** `CustomerHeroCard` + `PropertyHeroCard` 之类并列。
2. Hero 主体永远是**客户**；房屋 / 方案 / 报价 / 合同**不得替换 Hero 主体**（不得把客户降为副行）。
3. 对象信息只以"**标题行追加**"进入 Hero；其明细放 §4.6 的 ② 对应业务信息块。
4. L1 由页面插槽传入，不由对象类型决定。
5. 标题行追加统一为"**对象名「明细」· 客户名 · 状态标签**"；对象信息置于**客户名之前**，客户状态标签之后追加对象状态标签。
6. **对象优先的字形**：对象名与「明细」用 `$font-h1`（20px），客户名用 `$font-title`（18px）——对象字号必须**大于**客户名。
6. 共享实现：`ObjectHeroCard`（骨架）+ `HeroFocusItem`（L1 项）；各页只提供内容，不复制样式。

**反模式**：把房屋做成第二张 Hero；让对象替换 Hero 主体；对象明细塞进 Hero；标题行重复展示同一房屋信息；各页各写一套 Hero 样式。

### 4.8 多对象与多方案（强制）

**待我设计 · 新建方案（2026-10-10 用户裁决）**：

- 新建方案必须支持两种方式：`按方案模版创建`、`创建空白方案`，默认优先方案模版。
- 方案模版选择器打开即展示已发布且当前员工可见的模版；支持搜索，匹配当前房型/面积的模版优先排列。
- 表单分区固定为：`业务上下文 → 创建方式 → 方案模版 → 方案基础信息`；不得把模版选择藏在空下拉框里。
- 方案名称、风格、户型、说明必须按客户画像和当前房屋尽量预填；模版选中后，风格和说明可继续由模版事实补充。
- 按模版创建复用 `design/template/instantiate`；实例化后通过 `design/scheme/update` 写回本次名称/风格/户型/说明。
- 创建成功后进入方案工作台，不在待我设计队列页继续编辑方案内容。

**待我设计 · 设计方案卡片（2026-10-10 用户裁决）**：

- 卡片必须体现方案业务特征：方案名、编号、版本、风格、面积、空间数、设计项数。
- 卡片主视觉必须是**方案状态变迁**：`设计中 → 待谈单 → 已讲解 → 已选中`，不得把推进按钮放回卡片。
- 点击卡片进入方案工作台；设计编辑、状态推进、报价、谈单材料等操作只能在方案工作台完成。
- 卡片操作只允许**复制**和**删除**。删除最终以服务端门禁为准，前端不得自行删除有报价/谈单事实的方案。
- 单方案也必须显示一张卡片，不因方案数为一而隐藏，避免用户误以为方案不存在。

1. 同一页面存在**多个同类型对象**（如多个设计方案、多个报价版本）时，中栏必须先给**对象轨道**（可切换），再展示选中对象的信息行 + 该对象的业务信息块。
2. **单对象时不渲染轨道**（禁止空轨道）。
3. 轨道项至少给出：名称 / 版本或编号 / 状态 / 关键量（空间数、金额等）。
4. 切换轨道项 = 切换对象锚点，必须写回 URL（§11）并支持刷新恢复。
5. 待我设计：`DesignSchemeRail` 改为方案业务卡片组；卡片展示方案标识、核心事实和状态变迁，仅保留复制/删除，点击卡片进入方案工作台；单方案也显示卡片。
6. **方案必须按「客户 + 房屋」聚合**：`listSchemes(customerId)` 返回结果要按当前 `activePropertyId` 过滤后再进轨道，
   否则多房屋的方案会混在一起——设计师无法判断"这套方案是哪套房的"。切换房屋时同步重载该房屋的方案。
7. **中栏块序即关注度序**：客户 Hero → 房屋（对象锚点）→ 设计方案（含轨道）→ 量房信息 → 诉求 → 跟进。

### 4.10 谈单与签约资料（强制）

**设计 → 谈单 → 签约** 是装企业务推动的三个关键节点，各节点必须给出该节点**真正要用的业务资料**，不能只列"报价事实"这类数字。

| 节点 | 必须展示 |
| --- | --- |
| 待我设计 | 方案信息（名称/版本/状态/空间数/设计项数）· 设计进度 · **量房输入** · 客户诉求 · 跟进记录 |
| **待我谈单** | **方案信息** · 报价信息与调整 · **谈单资料**：谈单 PPT（生成/重新生成/打开）· 报价 PDF（生成/打开）· 客户诉求 · 跟进记录 |
| 待我签约 | 合同信息 · **签约资料**：方案信息 · 谈单 PPT · 报价 PDF · **合同 PDF** · 客户诉求 · 跟进记录 |

资料接口（复用既有 Provider，禁止新开 API）：

| 资料 | Provider | Web 封装 |
| --- | --- | --- |
| 谈单 PPT | `design/talk/page` · `design/talk/build` · `design/talk/info` | `designApi.listTalks / buildTalk / talkInfo` |
| 报价 PDF | `document/quote/build` · `document/record/page` | `documentApi.buildQuote / quoteRecords` |
| 合同 PDF | `document/contract/build` · `document/contract/records` | `documentApi.buildContract / contractRecords` |

硬约束：

1. 谈单 PPT 与 PDF 都是**服务端产物**，前端只触发生成与打开，不自行拼接内容。
2. 生成失败显示"暂不可确认"并保留重试，不得用本地预览伪装已生成。
3. 资料块用使用者语言（"生成谈单 PPT""打开报价 PDF"），禁止出现 Provider 名、`reloadScopes` 等研发术语。
4. 右栏不得出现"完成后回读"这类研发术语；统一为「**其他合法动作**」+ `WorkbenchQuickAction`。

### 4.8.1 方案工作台排版（2026-10-10 用户裁决）

方案工作台不是待我设计列表页的放大版，`DesignItemSheet` 是主工作面。

**固定顺序**：

```text
方案上下文
→ 当前阶段关注层（4 项结论）
→ 下一步业务行动（有则显示）
→ DesignItemSheet（设计分项主工作面）
→ 量房输入 + 图纸与参考图（支撑区）
```

**硬规则**：

1. 头部只保留当前状态允许的动作和唯一主行动，不得同时铺开所有状态按钮。
2. `DesignItemSheet` 必须优先出现在支撑资料之前；空间、量房、参考图不得把它推到首屏以下。
3. 空间管理改为抽屉，主页面不再用空间卡片大网格占位；空间卡片的编辑/删除在抽屉内完成。
4. 量房输入与图纸参考图放底部支撑区，宽屏两列，窄屏一列；图纸参考图默认折叠，展开后再维护上传。
5. 方案状态推进、报价生成和客户选中操作只在方案工作台内提供，动作完成后再回写列表状态。

**空间区域栏与尺寸重算（2026-10-10 用户裁决）**：

- 空间管理并入 `DesignItemSheet` 左侧“区域 / 分类”栏，不再做独立二次“空间管理”抽屉。
- 区域行展示区域名称、分项数量和金额；提供编辑入口打开空间尺寸表单。
- 空间保存后由服务端重算公式分项，公式结果同步回分项表和金额。
- 设计分项必须有工程量来源：`Formula` 由公式自动产生，`Manual` 由设计师手工填写。
- 修改空间尺寸只重算 `Formula` 分项；`Manual` 分项保留数量并显示“手工量”，避免覆盖设计师判断。
- 全屋共享公式 `SUM(A)`、`SUM(P)`、`SUM(WP)` 也必须随任一区域尺寸变化重算。
- 尺寸不足时保持待补尺寸状态，数量归零，不参与正式金额汇总。

**设计分项表（2026-10-10 用户裁决）**：

1. 品牌、规格不再单独占列，统一合并进“报价项目”列；项目名称下方展示 `品牌 · 规格 · 分类`，缺项显示 `—`。
2. 列顺序固定为：`# · 区域 · 报价项目（含品牌规格）· 单位 · 工程量 · 材料价 · 人工价 · 金额 · 备注 · 操作`。
3. 金额列与操作列在横向空间不足时锁定在右侧，保证滚动查看中间字段时仍然可比较金额并执行操作。
4. 常规 1440 桌面宽度下表内不得出现横向滚动条；≤1280 允许横向内容滚动，但不显示滚动条轨道，只保留触控/触控板横向滚动。
5. 分项表不得因为品牌或规格新增列；如字段继续增加，优先折叠进项目副标题或详情，而不是继续扩列。

### 4.9 跨阶段事实（客户诉求 / 跟进记录）

1. 客户诉求与跟进记录属于**跨阶段事实**，在 5 个工作台中栏都必须可见（§4.6 的 ③ 段）。
2. 权重按 §4.5：待我跟进 / 待我量房 = **重点**；待我设计 / 待我报价 / 待我签约 = **常规（默认折叠）**。
3. 形态统一：使用共享区块 `src/components/customer/CustomerContextPanels.vue`（诉求 + 跟进），禁止各页各写一套。
   页面只传 `requirements` / `follows`、决定 `order`（面板顺序）与 `emphasis`（primary 完整 / normal 默认折叠），
   并通过 `@record-requirement` / `@record-follow` 打开自己的抽屉；不提供入口时用 `can-record-*` 关掉按钮，避免死按钮。
4. 记录入口统一：诉求用 `RequirementFormDrawer`，跟进用写跟进抽屉。
5. **弱化 ≠ 删除**：折叠时仍要显示条数与最近一条摘要。

## 5. 主行动推导契约（强制）

1. 主行动 = `f(服务端状态, 服务端允许动作, 阻断条件)`；前端只渲染，不计算。
2. 主行动有四种展示形态：

| 形态 | 条件 | 展示 |
| --- | --- | --- |
| 可执行 | 服务端允许且无阻断 | 品牌实色主按钮（B1），展示主行动文案 |
| 不可执行 | 有缺失字段或前置条件 | 按钮禁用 + 明确阻断原因 + 恢复路径 |
| 待业务确认 | 状态/规则未登记或规则未命中 | 按钮禁用 + "待业务确认" |
| 已完成 | 当前对象已交接给下游 | 显示已完成状态 + 去向，不再显示可执行主按钮 |

3. 队列筛选只改变可见集合，**不得改变对象状态或主行动**。
4. 一个工作台一次只允许一个视觉最重的主按钮。
5. 主行动文案使用使用者语言，禁止出现"服务端、对象锚点、主链、回读、队列"等研发术语。

### 5.1 阻断提示规范（强制）

"主行动因前置条件不满足"属于**阻断**，不是普通保存失败，必须让用户立刻看见并知道怎么办。

**表现**：

```text
主行动按钮副标题 = 预先说明阻断条件（如"需先完成首次跟进（首联）"）
用户点击 → 模态弹窗（ElMessageBox）
弹窗 = 标题（还不能预约量房）+ 原因（谁、为什么）+ 恢复路径（怎么做）
弹窗必须提供可执行恢复动作（如"去写跟进"），并保留"稍后再说"
```

**硬约束**：

1. **必须模态**：阻断提示必须用模态弹窗，禁止只依赖页面底部的 `el-alert`；底部提示会随页面滚动落到首屏之外。
2. **必须给恢复路径**：弹窗至少一个可执行按钮，点击后直接进入解除阻断的动作（如写跟进、建立房屋），不能只给"知道了"。
3. **必须可解释**：说明"哪个对象、缺什么、做完什么才能继续"，禁止只给错误码或技术文案。
4. **必须预先可见**：按钮副标题展示阻断条件，让用户点之前就知道会被拦。
5. **服务端同类拒绝同样走模态**：服务端返回阻断类错误（如"先完成首次跟进"）时，同样弹出模态并给恢复路径，不得只写进内联错误条。
6. **瞬时失败保留内联**：网络/保存失败仍用内联提示，但必须位于首屏可见区域（工具条下方），不得放在三栏之后。
7. **文案不用研发术语**：不出现"服务端、状态机、校验失败、blockReason"等内部表达。
8. **统一实现，禁止各页自造**：阻断模态统一使用 `src/core/blockedNotice.ts` 的 `notifyBlocked()`，新页面不得复制一份实现；新出现的阻断入口必须复用同一套标题/原因/恢复路径结构。

**反模式**：只改按钮禁用不给原因；错误只写在页面最底部；弹窗只有"知道了"没有下一步；阻断文案带内部字段名。

## 6. 操作按钮主次 UI 规范

### 6.1 按钮层级（B1–B7）

| 层级 | 名称 | 视觉 | 数量约束 | 典型场景 |
| --- | --- | --- | --- | --- |
| B1 | 主操作 | 品牌实色 `$brand-600`，最大最重 | **同一可视区域唯一** | 写跟进、保存、确认安排、登记量房、创建并进入设计 |
| B2 | 沟通操作 | 品牌浅底 `$brand-50` + 品牌图标 | 可多个 | 打电话、记录加微信/更新微信 |
| B3 | 记录操作 | 绿/橙浅底 + 语义图标 | 可多个 | 记录到店、上传现场照片、上传结构图 |
| B4 | 次级操作 | 白底 + `$border-color` 边框，中性色 | 可多个 | 完整档案、打开客户 360、查看下一项、取消 |
| B5 | 提醒操作 | 橙色底/边 `$warning-*` | ≤1 | 暂不跟进、设为休眠 |
| B6 | 恢复操作 | 绿色底/边 `$success-*` | ≤1 | 恢复跟进、恢复可用状态 |
| B7 | 危险操作 | 红色 `$danger-500` | ≤1，且必须二次确认 | 删除、不可逆操作 |

### 6.2 硬约束

1. **唯一主行动**：同一可视区域（右栏主卡片 / 抽屉 footer / 弹窗 footer）最多 1 个 B1。
2. **主次分明**：B1 必须实色、字重最重、尺寸最大；B2–B4 不得使用品牌实色。
3. **图标 + 文字**：B2/B3 必须"图标 + 标题 + 一句话说明"（参考跟进页 quick 卡），禁止图标单独表意。
4. **颜色不滥用**：语义色只用于对应层级；禁止用红色表达普通次要操作。
5. **禁用有原因**：禁用态 = 降透明度 + 保留文案 + 同时显示阻断原因；禁止只灰掉不解释。
6. **加载不跳动**：加载态 = 按钮内 spinner + 禁用 + 保持原宽度。
7. **危险必确认**：B7 必须二次确认、说明后果、服务端幂等、留审计。
8. **文案是动词**：按钮文案以动词开头（写跟进、安排量房、登记量房结论），禁止"提交""确定"这类无对象文案。
9. **按钮必须带图标**：所有功能按钮（建立/新增/编辑/删除/写跟进/打开档案等）必须"图标 + 文字"，禁止纯文字功能按钮；图标只做识别，不单独表意。

### 6.3 位置与排列

- **右栏主卡片**：B1 位于"原因 / 下一接棒"之间，占整行宽度；B2–B4 在主卡片下方的"其他合法动作"分组。
- **抽屉 / 弹窗 footer**：次级操作（取消）在左，B1 在最右；移动端 B1 占整行。
- **列表 / 卡片紧凑态**：只允许 B1 的紧凑变体或 B4；一个列表项最多 1 个动作入口。
- **分组间距**：主行动与次级动作之间用分隔或分组标题，避免视觉同权。

### 6.4 Element Plus 映射

| 层级 | 映射 |
| --- | --- |
| B1 | `<el-button type="primary">` 或页面 `.xx__primary`（颜色取品牌 token） |
| B2 | 页面自定义 quick 卡（Element 无对应），颜色取 `$brand-50` / `$brand-600` |
| B3 | 页面自定义 quick 卡，颜色取 `$success-*` / `$warning-*` |
| B4 | `<el-button>`（默认） |
| B5 | `<el-button type="warning" plain>` 或自定义 |
| B6 | `<el-button type="success" plain>` 或自定义 |
| B7 | `<el-button type="danger">` + 二次确认 |

所有颜色必须来自 `src/styles/tokens.scss`，禁止裸色值、裸字号、裸圆角。

### 6.5 业务推进点重点标注（强制）

每个工作台有一个**业务推进点**——能把当前对象推进到下一阶段的那一步（如「待我跟进」的**预约量房**）。

要求：

1. 业务推进点在动作组中**排第一位**，并做重点标注：整行宽度 + 品牌边框/浅底 + **实色品牌图标**（图标本身即强调，不用文字标签）。
2. **禁止叠加文字标签**（如"业务推进""推荐"）：说明文字只放在按钮副标题或右栏原因里，避免同屏出现第二套强调语义。
3. 业务推进点仍是**次级动作**，不得与右栏唯一主行动（B1）同权；主行动永远只有一个。
4. 前置条件不满足时，按 §5.1 弹阻断模态，并在按钮副标题预先说明条件。

**反模式**：业务推进点与普通动作同权重排在一起；用纯色大按钮抢占右栏主行动；在按钮角上叠"业务推进/推荐"之类标签。

### 6.6 右栏动作按钮：内容变、样式与文案统一（强制）

右侧引导的**按钮集合**按页面与服务端允许动作变化，但**样式、文案规范与语义色必须统一**。

| 维度 | 变 | 不变 |
| --- | --- | --- |
| 按钮集合 | 按页面业务特征 + 服务端 `allowedActions` | — |
| 样式 | — | 统一 `WorkbenchQuickAction`（禁止各页自造按钮样式） |
| 文案 | 具体动作名 | **动词开头** + "什么时候用 / 会产生什么结果" |
| 语义色 | 具体动作 | 下表统一 |

**语义色对照**：

| 语义 | tone | 示例 |
| --- | --- | --- |
| 沟通 | `brand` | 打电话 |
| 微信 / 联系 | `contact` | 记录加微信 / 更新微信 |
| 事实记录 | `record` | 记录到店 |
| 客户诉求 | `requirement` | 客户诉求 |
| 次级 / 档案 | `outline` | 完整档案 |
| 提醒 | `warn` | 暂不跟进 |
| 恢复 | `success` | 恢复跟进 |
| 量房 / 房屋 | `measure` | 预约量房 / 维护房屋档案 |
| **唯一主行动** | 右栏主卡片 B1 | 写跟进 / 安排量房 / 新建方案 / 提交报价 / 合同生效 |

**硬约束**：

1. 同一语义在不同页面必须用同一 tone（"打电话"在 5 个页面都是 `brand`）。
2. 主行动（B1）只在右栏主卡片出现一次；其余动作一律降级为 quick 卡。
3. 业务推进点（如"预约量房"）可整行强调，但不得与 B1 同权（§6.5）。
4. 按钮文案禁止出现研发术语（服务端 / 状态机 / 回读 / 锚点）。
5. 前置条件不满足时按 §5.1 弹阻断模态，并在按钮副标题预先说明条件。

**反模式**：各页各写一套按钮样式；同一语义在不同页用不同颜色；按钮只有图标没有文字。

## 7. 弹窗与抽屉规范统一

### 7.1 承接方式决策树

```text
这个动作需要用户输入或确认吗？
├─ 不需要，就地完成且低风险           → L0 就地操作
└─ 需要
   ├─ 属于客户经营/房屋场景（domain=customer）
   │                                  → 抽屉 el-drawer（域内统一，见下）
   ├─ 1–2 个字段 或 纯确认 / 风险提示   → 弹窗 el-dialog
   ├─ ≥3 个字段 / 业务上下文强 /
   │  可逆编辑 / 需边看中栏对象边填      → 抽屉 el-drawer
   └─ 复杂编辑 / 批量 / 对账 / 导入导出  → 全屏工作区
危险 / 不可逆 / 金额 / 权限 / 删除       → 安全门（二次确认弹窗）
```

> **域内一致性优先于字段数**：`WEB-客户场景三栏工作台规范.md` 规定客户经营操作统一使用右侧抽屉，
> 因此 `domain=customer` 的客户/房屋场景一律用抽屉（含单字段的"安排量房"），
> 只有纯确认（休眠、删除、二次确认）才用弹窗。其他域再按字段数走上面的分支。

### 7.2 抽屉规范（L1，工作台默认承接方式）

- 方向 `rtl`，宽度：480（轻量）/ 520（标准）/ 680（多字段）。
- 固定结构：

```text
① 上下文条：CustomerPropertyContext（客户 + 房屋 [+ 方案]），占满宽度
② 分区标题：说明这一段录什么
③ 录入区：按表单规范分区分组
④ 说明 / 风险：el-alert 或一句话结果说明
⑤ footer：取消（B4） + 唯一主行动（B1，最右）
```

- 标题用动词短语：写客户跟进、完善客户画像、记录客户微信、建立房屋、安排量房。
- 抽屉顶部必须先给上下文，再给录入区；用户不能靠记忆确认在操作谁。
- 关闭前有未保存草稿必须触发守卫（保存后关闭 / 放弃并关闭 / 取消）。

### 7.3 弹窗规范（确认 / 短表单）

- 宽度：500（确认 / 单字段）/ 620（短表单）/ 720（中等表单）。
- 固定结构：标题 + 可选上下文 + 内容 + footer（取消 + 唯一 B1）。
- 仅用于：确认、≤2 字段短表单、结果/风险提示、安全门。
- 必须 `append-to-body`；同一时刻只允许一个弹窗。

### 7.4 关闭、遮罩与草稿守卫

1. 未保存草稿时，ESC / 取消 / 点遮罩 / 关闭按钮统一走同一守卫：保存 / 放弃 / 取消。
2. 禁止抽屉叠抽屉、弹窗叠弹窗；抽屉内需要确认时，用抽屉 footer 内的确认，不叠加新弹窗。
3. 关闭后焦点回到触发按钮，滚动位置恢复到进入前。
4. 打开承接层时中栏对象上下文保持可见（宽屏），用户始终知道在操作谁。

### 7.5 两个参考页面的统一结论（已冻结，已实施）

按本规则，现有实现需要一次收敛：

| 动作 | 现状 | 统一后 |
| --- | --- | --- |
| 写客户跟进 | 抽屉 | 抽屉（保持） |
| 完善客户画像 | 抽屉 | 抽屉（保持） |
| 记录客户微信 | 抽屉 | 抽屉（保持） |
| 设为休眠 / 恢复跟进 | 抽屉 | 改为**确认弹窗**（单确认 + 原因字段） |
| 建立房屋 | 抽屉 | 抽屉（保持） |
| 安排量房 | 弹窗 | 已改为**抽屉**（520px，带上下文） |
| 登记量房结论 | 弹窗 | 已改为**抽屉**（680px，多字段 + 附件） |
| 新建设计方案 | 弹窗 | 已改为**抽屉**（620px，多字段，带上下文） |
| 删除房屋 | 弹窗 | 安全门确认弹窗（保持） |

### 7.6 反模式

1. 同一类多字段表单，有的用抽屉、有的用弹窗。
2. 抽屉里再开抽屉、弹窗里再开弹窗。
3. 抽屉顶部没有客户/房屋上下文。
4. 弹窗承载 ≥3 字段的长表单。
5. 关闭不守卫草稿，直接丢失输入。
6. footer 出现多个同权主按钮。

## 8. 表单设计规范（工作台落地）

> 完整规则以 `WEB-业务选择器与表单设计规范.md` 和 `WEB-业务概念全生命周期规范.md` 为准；本节只写工作台承接层的落地要求，不重复、不覆盖总规范。

### 8.1 表单分区（固定五段）

```text
1 业务上下文        客户 / 房屋 / 项目（占满宽度）
2 主录入区          业务对象正文
3 短字段区          金额 / 日期 / 类型 / 账户（可并排）
4 业务参考 / 风险区  服务端事实 + 风险提示
5 主行动            唯一 B1
```

### 8.2 落地规则

1. `label-position="top"`，标签 + 必填标记 + 一句说明。
2. 长文本、备注、复合对象占整行；金额、日期、类型等短字段可两列并排。
3. 业务上下文卡（客户 + 房屋）占满宽度，放在录入区之前。
4. 输入项保持中性底色，不用颜色区分字段；颜色只用于状态、风险、金额口径提示。
5. 不建立重复的"录入区 + 预览区"；结果对象即主界面。
6. 校验三层：即时（失焦/变更）+ 提交前 + 服务端最终校验；金额、成本、权限、状态、归属一律服务端裁决。
7. 错误表达：字段级错误就地显示 + 顶部错误汇总；失败保留用户输入，不清空表单。
8. 保存动作唯一 B1；保存成功后按 `reloadScopes` 回读；失败显示"暂不可确认"并保留草稿。
9. 普通枚举用 `select` / `multi-select`；业务对象用专用选择器，禁止只给搜索框。
10. 已选业务对象卡满宽、信息区稳定；长名称不破坏布局。
12. **上传字段统一用标准组件** `src/components/form/FileUploadField.vue`：
    - 图片（`contentType=image/*` 或图片扩展名）→ **缩略图 + 点击全屏预览**（`el-image` + `preview-src-list`，支持左右切换）；
    - 视频（`contentType=video/*` 或视频扩展名）→ **首帧缩略图 + 播放角标**，点击弹窗内嵌播放（`<video controls>`）；
    - 其他文件 → 「文件名 + 新窗口打开」；
    - 上传 / 移除 / 上限计数 / 禁用 / 部分成功回写 / 失败提示**全部内建**；
    - **禁止**各页自写 `<input type="file">` + 文件列表 + 手写移除按钮；
    - 私有文件必须经 `fileApi` 授权（`businessType` 决定业务域），不得直接拼下载路径。

11. **日期时间字段统一用两段式控件** `src/components/form/DateClockField.vue`（「年月日」`el-date-picker type="date"` + 「时分」`el-time-select` 下拉，30 分钟一档，含今天/明天/后天快捷）；
    **禁止**直接用 `el-date-picker type="datetime"`——现场录预约/量房时间时要在日历与时间滚轮之间来回操作，不便。
    对外 `v-model` 统一为 `YYYY-MM-DD HH:mm:ss`，日期与时间都选完才回填。

### 8.3 门禁

- 编码前：`T15`（选择器）→ `T16`（表单分区与结果确认）→ 必要时 `T17`（单据化）→ `T06/T12` 业务裁决。
- 编码后：`npm run check:forms`、`npm run check:concepts` 必须通过。

## 9. 数据契约

> **边界（2026-10-11 用户裁决，替代 2026-10-09 的 `GAP-WEB-013` 口径）**：
> Web 前端重构**不再需要逻辑注册表**。每个角色沉淀三份**静态源**，都**不参与任何运行时判断**：
> `src/roles/routes.ts`（该角色可到达的路由集合）、`src/roles/workbenchConfig.ts`（该角色左侧菜单）、
> `src/roles/workbenchHome.ts`（该角色首页场景卡片）。
> `docs/standards/workbench-navigation.json` **已删除**。它的**业务条款**（入站状态、上下文恢复、未保存保护、
> 状态→主行动、空态/异常态、交接对象…）归档到人读文档 `docs/standards/WEB-工作台契约条款.md`，
> **机器门禁不再读那份文档**——门禁只校验上面三份静态源（`check:workbenches` / `check:workspaces`）。

### 9.1 静态清单契约（三份静态源）

同一个页面可以出现在多个角色的集合里：**在各角色集合里各自声明**即可，不需要（也不允许）再造一层
「公共注册表 + 按角色过滤」。页面内部按角色渲染差异属于**页面逻辑**，不是准入逻辑。

#### 9.1.1 路由集合 · `src/roles/routes.ts`

| 约束 | 说明 |
| --- | --- |
| 每角色一份 | `routesByRole: Record<EmployeeRole, RouteRecordRaw[]>`；登录后**只装载当前角色的集合**（查表＝数据分离，不是 `if`/白名单） |
| 无 `meta.roles` | 不再用路由元数据做角色判断；区域级判断（`isDesignerArea` 之类）与临时白名单一并禁止 |
| 越权落点 | URL 不在本角色集合、但属于别的角色的已知路径 → `/forbidden`；完全不存在 → 404 |
| `homePath` 自洽 | `workbenchConfig[role].homePath` 必须在该角色路由集合内（门禁强校验，防结构漂移） |
| 服务端兜底 | 前端集合只管**准入与呈现**；权限与数据范围的真正兜底在服务端（Provider 角色校验 + 数据范围裁剪） |

#### 9.1.2 菜单 · `src/roles/workbenchConfig.ts`

- 每项**静态显式** `key/label/path`，不查表、不回落；`path` 必须在该角色路由集合内（否则就是死链）。
- 一级导航 ≤ 7 项；命名用场景语言，禁止模块 CRUD 命名（`DEC-034` / `BR-030`）。

#### 9.1.3 首页场景卡片 · `src/roles/workbenchHome.ts`

字段（`HomeWorkbenchEntry`）：

```text
key / label / domainLabel / groupLabel
scenario（进入场景）/ objectAnchor（对象锚点）
mainAction（当前任务）/ handoff（完成后交接）
priority / decisionStatus / to（落地页）
```

硬约束（`npm run check:workbenches` / `check:workspaces` 逐条校验）：

- `key`、`label` 在**同一角色内**唯一；`label` 禁止"管理"式模块命名。
- `priority` ∈ `P0 | P1 | P2`；`decisionStatus` ∈ `approved | pending_business_review`。
- `to` 必须是 `/` 开头的路径或 `null`；`approved` 的卡片 `to` 必须在该角色路由集合内**可达**。
- `decisionStatus !== 'approved'` 时 `to` **必须为 `null`**（未裁决不得把落地页写成数据；卡片只显示「待业务确认」）。
- 数组顺序**即展示顺序**（首页不做排序）；顺序变更要在本文件注释里说明理由。

#### 9.1.4 业务条款（人读，机器不读）

`docs/standards/WEB-工作台契约条款.md` 保留了原注册表里**没有其他归宿**的条款：

```text
kind / roles（历史口径）        inboundStates（入站状态）
mainline / currentWorkSurface   actionPolicyKeys（动作策略键）
contextKeys / contextRecovery   unsavedChangesGuard（未保存保护）
reloadScopes（刷新范围）         primaryActionByState（状态→主行动）
handoffTo / emptyState / exceptionState / businessRefs
```

用途：**页面实现与验收的人工对照**。改这些条款不会改变门禁结果；要改「入口/排序/落地页」请改前三份静态源。


前端不得从这些字段自行推导新的状态机或阶段重点；缺失的规则统一回退为"待业务确认"。

## 10. 状态与异常（必须覆盖的 7 类）

| 状态 | 触发 | 要求 |
| --- | --- | --- |
| 加载中 | 初次或刷新读取 | 骨架屏，保留布局，不闪空态 |
| 真实为空 | 确实没有入站对象 | 说明为什么为空 + 可做什么 + 刷新 |
| 筛选后为空 | 有对象但被筛掉 | 提示清除搜索/筛选，不得说"没有需要处理的" |
| 读取失败 | 接口失败 | "暂不可确认" + 重试；不得显示空数组 |
| 部分失败 | 主数据成功、关联失败 | 保留成功区域 + "部分数据暂不可确认" |
| 无权限 | 数据范围不允许 | 说明原因和可返回路径，不生成越权区块 |
| 规则未命中 | 状态/动作未登记 | "待业务确认"，主行动禁用 |

**红线**：空队列 ≠ 读取失败 ≠ 任务完成。三者必须用不同表达，禁止互相冒充。

## 11. 交互规则

### 11.0 对象锚点的 URL 键名（强制）

所有工作台的深链接、刷新恢复与切换都必须使用下表键名，**禁止各页自造**（同一对象在不同页面必须同名）：

| 锚点 | 键名 | 说明 |
| --- | --- | --- |
| 客户 | `customerId` | 客户主键 |
| 房屋 | `activePropertyId` | 本页当前生效的房屋；多房屋必须显式选择（历史 `propertyId` 仅作读取兼容） |
| 设计方案 | `schemeId` | 待我设计当前方案 |
| 报价 | `quoteId` | 待我谈单 / 待我签约当前报价 |
| 合同 | `contractId` | 待我签约当前合同 |

写入规则：

1. 切换对象（队列项 / 轨道项）后立即 `router.replace({ query })` 写回，**保留其他查询参数**。
2. 子对象变化必须同时清理其下游锚点（例如换客户要清 `schemeId`；换报价要清 `contractId`），避免出现"客户 A + 客户 B 的报价"这种错配锚点。
3. 载入时优先按 query 恢复；query 指向的对象不存在时回退到队列第一条，并再次写回 URL（不保留失效锚点）。
4. 未选择锚点时不得默认第一条后**不回写**——自动选中同样要写回，保证 URL 与页面对齐。



1. 选中队列项 → 中栏 Hero 和右栏同步切换，选中态高亮。
2. **切换队列筛选 / 搜索必须联动中栏与右栏**：新结果包含当前对象则保持；不包含则自动切到新队列首位并重载对象上下文；结果为空则清空选中，中栏与右栏回到"先选择对象"空态。禁止只切左栏、中栏仍停留在旧对象。
3. 动作成功后按 `reloadScopes` 回读；回读期间保留当前对象上下文。
4. 动作完成后不自动切换对象；"下一项"由用户点击，并显示进度 `n/m`。
5. 多字段录入统一用右侧抽屉，抽屉顶部必须带客户/房屋上下文（见 §7）。
6. 未保存草稿时切换对象、关闭抽屉或进入安全门，必须提供：**保存后切换 / 放弃并切换 / 取消**。
7. 禁止抽屉叠抽屉、弹窗叠弹窗。
8. 键盘可达：所有可点击项可 Tab 聚焦，焦点可见，禁止 `outline: none`；屏幕阅读器可读出当前选中对象、阶段重点、主行动、阻断原因和完成去向。

### 12.4 左栏队列高度与三栏协调（UI 设计规范）

**目标**：三栏在首屏内形成稳定整体感；**左栏队列不得成为页面高度的决定者**。

**结构**：

```text
.queue        容器：sticky、边框、圆角、overflow:hidden
├── .queue-head   固定表头（标题 + 计数）
└── .queue-list   唯一内部滚动区，受控高度
```

**高度预算公式**：

```scss
.queue {
  display: flex;
  flex-direction: column;
  max-height: calc(100vh - var(--workbench-queue-top) - #{$space-4});
  overflow: hidden;
}
.queue-list { flex: 1 1 auto; min-height: 0; overflow: auto; }
// --workbench-queue-top = 该页面三栏在视口中的起始 y（由各页按断点声明，如 295/265px）
```

`--workbench-queue-top` = 该页面三栏在视口中的起始 y（工作台头 + 工具条 + 顶部间距），按断点声明：

| 页面 | 断点 | 顶部 y 实测 | 声明值 |
| --- | --- | --- | --- |
| 待我跟进 | >1300px | 295 | `295px` |
| 待我跟进 | ≤1300px | 265 | `265px` |
| 待我量房 | 1440px | 327 | `327px` |

**硬约束**：

1. **顶部对齐**：三栏 `align-items: start`，共用同一 top offset，顶部齐平；左栏不因内容短而上浮。
2. **左栏可见高度受首屏约束（>1024 断点）**：`queue.height ≤ 100vh - queue.top`。左栏高度 = `min(内容高度, 视口预算)`，不强行与其他栏等高；≤1024 单列时本条不适用（见第 7 条）。
3. **页面高度不由左栏决定**：队列条数增加只增长 `.queue-list` 的滚动内容，不增加 `pageScroll`；当左栏内容超过视口预算时，左栏不得成为最高列。
4. **唯一滚动区**：滚动条只允许出现在 `.queue-list`；`.queue` 容器不滚动，避免与页面滚动条形成双滚动。
5. **最小可见条目**：不滚动时左栏至少完整显示 1 条并露出第 2 条，让用户知道可滚动；否则说明头部块或 offset 过大。
6. **空态不撑高**：真实为空时用受控高度的空态（如 220–240px），不把页面撑到一屏以上。
7. **≤1024 取消内滚**：`.queue-list { max-height: none }`，单列交由页面滚动。

**页面长度指引（仅三栏同屏断点，>1400px）**：`pageScroll / viewport` 目标 ≤1.4，上限 ≤1.6。
超过上限说明**中栏未分层/未折叠**（不是左栏问题），应先收敛中栏 Hero 与事实区，禁止通过削减左栏内容来达标。
两栏（1025–1400px）与单列（≤1024px）断点由页面滚动承载，不设页面上限。

> 阈值修订记录（2026-10-09）：原为「目标 ≤1.2 / 上限 ≤1.4」，基于仅含 Hero + 两个上下文块的早期版本测得 1.12。
> 在 §4.4（客户诉求板块）与 §4.5（L1 阶段关注层）落地、且 `WEB-客户场景三栏工作台规范` §5 要求「房屋与最近沟通上下排列」之后，
> 中栏信息完整时实测 1.45（hero 373 + 上下文 569），故按实测把上限调到 1.6。**结构性硬判据不变**：
> 左栏内部滚动、左栏底边与右栏对齐、页面高度不由左栏决定。

**实测参考（v4，2026-10-09）**：

| 页面 | 断点 | 左栏队列 | 左栏底边 | 右栏底边 | 中栏工作面 | pageScroll/视口 | 左栏内滚 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 待我跟进 | 1440×900 | 589 | 884 | 910 | 958 | 1.45 | 是 |
| 待我跟进 | 1280×900 | 619 | 884 | —（两栏，右栏下移） | 958 | 2.19（两栏） | 是 |
| 待我跟进 | 1024×768 | 709（单列，规则 2/3 不适用） | — | — | 958 | 3.72（单列） | 否 |
| 待我量房 | 1440×900 | 557 | 884 | 753 | 428 | 1.04 | 是 |

> 说明：左栏改为「卡片按视口定高 + 列表内部弹性滚动」（`max-height: calc(100vh - var(--workbench-queue-top) - 16px)`），
> 1440 下左栏底边与右栏底边**完全对齐（均 884）**，即上一版"左栏偏短"的问题已消除。
>
> 结论：跟进页在 1440/1280 下左栏内部滚动、不贡献页面高度。左栏是否成为最高列取决于中栏信息量，不作为硬判据。

**反模式（一票否决）**：

1. 左栏用 `height: 100vh` 或固定大高度强行撑满。
2. 左栏随列表条数无限增长，把中栏/右栏推出首屏。
3. 左栏容器和页面同时出现滚动条。
4. 左栏与中栏顶部不对齐，形成"断头"。
5. offset 写死却不随头部块高度变化，换角色/换场景后失配。

**统一要求**：左栏统一采用「卡片定高 + 列表弹性滚动」；`--workbench-queue-top` 由各页在其 layout 上按断点声明（跟进取 295/265px，量房取 327px），不写死在列表上。

**交付证据**：三档分辨率渲染 JSON 必须包含 `queue/workspace/guide` 的 `height` 与 `pageScroll`。参考实现证据：`output/playwright/designer-followup-v6-render.json`、`designer-followup-v6-{1440,1280,1024}.png`、`designer-measure-v4-schedule-drawer.png`。

## 18. 构建方法：从「待我跟进」构建过程提炼

> 来源：Codex 对话「新增设计师客户经营待我跟进页」（2026-10-09）。
> 产物：`src/views/designer/DesignerFollowUpTasksView.vue`、产品稿 `docs/product/designer/WEB-DESIGNER-FOLLOW-UP-WORKBENCH.md`、渲染记录 `output/playwright/designer-followup-v3-render.json` 与 `designer-followup-v6-render.json`。

### 18.1 十步构建法

```text
1  认事实     读业务卷宗 + App 同对象页面，确认对象/状态/动作/权限，不凭记忆
2  选参照     以「待我量房」为参照，抽出"左队列 / 中对象 / 右引导"三栏骨架
3  定定位     一句话说清这个页面"是什么、不是什么"（不是通讯录、不是 360 替代）
4  写场景     ≥2 个真实中小装企场景（含一人多岗、多房屋）
5  定入站     入站范围（角色 / 数据范围 / 阶段）+ 排序（逾期 → 今日 → 3 天内 → 未安排）
6  融信息     定义对象 Hero 融合哪些字段；划清起点边界（本页 vs 对象 360 都能完成本页动作）
7  定动作     唯一主行动 + 前置条件 + reloadScopes + 下一接棒；其余动作降级
8  做注册     workbench key / route / nav group / objectAnchor / task / acceptance scenario
9  渲染迭代   三档分辨率实拍 → 量高度与 pageScroll → 修正 → 再拍（至少两轮）
10 沉淀       写产品稿 + 更新规范 + 注册 AGENTS + 跑门禁
```

### 18.3 五条教训

1. **先分栏定高，再填内容**：三栏必须"顶部对齐、分栏定高、内部滚动"，否则页面会随某栏内容增长而失衡（v1 的问题）。
2. **对象 Hero 要融合，不要拆卡**：把身份、阶段、风险、关键事实、画像收进一个卡片（v1 → v3 的收敛方向）。
3. **用数据判断协调，不靠肉眼**：每轮都要真实浏览器量出 `queue/workspace/guide` 高度与 `pageScroll`，用 §12.4 的阈值验收。
4. **区块级规则必须验"联动"，不只验"渲染"**：筛选、搜索、切换对象这类交互，要同时验中栏与右栏是否跟随，否则会出现"只切左边"的隐性断链（v6 修复）。
5. **强调要有节制**：同一个强调语义只保留一处（如业务推进点用图标与版式强调，不再叠文字标签），避免同屏出现两套"最重要"（v6 修复）。
