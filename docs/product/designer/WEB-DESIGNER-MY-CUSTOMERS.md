# 设计师「我的客户」页面分析（客户经营 · 讨论稿）

> 状态：`ANALYSIS`（待确认后端方案后进入编码）
> 上游：`WEB-DESIGNER-MENU-FROZEN.md` D2/D3（客户经营组，菜单项改名「我的客户」）
> 业务事实源：`SCN-014 设计师客户全链沉浸式推进`、`BR-001 客户—房屋—报价—项目主链`、`SCN-001 获客跟进到量房`、`DEC-002 六条冻结映射`、`GAP-004`（已关闭）
> 范围：设计师角色的客户列表 + 客户 360；**不改**业务对象、状态机、权限定义

---

## 1. 结论摘要

1. **菜单层已定**：`客户与设计` → 改名 **`我的客户`**；「客户与设计」页面本身**保留**（作为设计/量房推进的对象工作区），不被删除。
2. **Web 缺的不是"客户页面"，是"设计师视角的客户经营页"**：现有 `DesignerCustomersView` 已经有客户池 + 客户 360 雏形，但它把「客户经营」和「设计推进」揉在一个页面里，**没有设计师统计与分类**，列表也不是卡片，360 的主行动只是一个字符串映射，**没有和状态机真正联动**。
3. **关键发现（后端缺口，必须决策）**：库里已有一个客户经营聚合 Provider `customer/customer/overview`，字段非常合适（`stageCounts` / `metrics` / `customers.riskLevel/riskReason/nextAction/idleDays`），但它**不能给设计师用**：
   - `CustomerOverviewContext.report()` 第一行就是 `tenantContext.requireBoss(principal)` → 设计师调用直接失败；
   - 取数方式是 `findByCompany_ComId(comId)` **全量实体**再在 Java 里 `enrich` + 过滤 → 违反 `rules.md §0.4 / DEC-036 / BR-031`（统计汇总必须聚合/投影 SQL，禁止全量实体 + Java 循环）。
   - 所以：**要么新建一个设计师口径的聚合 Provider，要么先改造既有 Provider**。这是本轮唯一硬前置。
4. 现成的分页 Provider `customer/customer/page` **已经是设计师口径**（本人负责 ∪ 指派给我设计），可以直接做列表数据源；但它同样存在「全量取回再 Java 过滤」的问题，且**不返回任何统计**。

## 2. App 端对照（设计师客户）

### 2.1 客户阶段（App 与 Web 一致，8 阶段）

| 阶段 key | App 标签 | 语义 |
| --- | --- | --- |
| `intention` | 待首联 | 刚登记，未完成首次联系 |
| `following` | 跟进中 | 已建立联系，持续跟进 |
| `pendingMeasure` | 待量房 | 已约定/待安排量房 |
| `quote` | 方案报价 | 进入设计 / 报价推进 |
| `sign` | 已签约 | 合同已签 |
| `construction` | 施工中 | 项目在管 |
| `done` | 已完工 | 项目完工 |
| `lost` | 已流失 | 异常终态 |

`DEC-002` 冻结补充：客户摘要主阶段用经营漏斗；**当前房屋执行阶段**另外按 量房/设计/报价/合同/项目 渲染；多房屋必须显式 `activePropertyId`；`Submitted` 显示"待客户决策"；`Draft` 不进正式轨道；`Signed` 与 `Effective` 分开。

### 2.2 App 客户列表（`pages/customer/list.vue`）

- **筛选**：全部 / 待首联 / 跟进中 / 待量房 / 报价 / 签约 / 施工 / 完工 / 流失（设计师可见全部 9 项）。
- **分类统计**：按阶段计数（每个筛选项带数量）。
- **卡片上的两类"经营时钟"**（这是 Web 完全没有的）：
  - 跟进提醒：`逾期 N 天` / `今日跟进` / `N 天后` / `下次 MM-DD`
  - 生命周期：`黄金期 0-3天` / `升温期 4-7天` / `保温期 8-15天` / `沉睡风险 15天+`
- **排序**：风险优先等。

### 2.3 App 客户 360（`subpackages/customer/pages/detail.vue`）

结构顺序：
1. **身份头**：姓名 + 阶段标签 + 联系方式 + 标签 + 负责人/设计师两栏
2. **联系动作**：电话 / 微信
3. **主行动卡**（唯一主行动，带 loading 态）
4. 分区错误条（部分数据加载失败 → 重试）
5. 装修房屋列表（多房屋切换）
6. 后续分区（诉求 / 方案 / 报价 / 合同 / 项目）

**主行动是状态驱动的**（App 的实现）：

| 判断顺序 | 条件 | 主行动 |
| --- | --- | --- |
| 1 | 已有项目 | 查看工地 |
| 2 | 已有确认/在途报价 | 查看报价流转 |
| 3 | 业务员且有量房或已指派 | 查看业务流转 |
| 4 | 销售阶段=报价且有报价权限 | 生成报价 |
| 5 | 销售阶段=设计（**当前房屋已量完**）| 进入设计转化 |
| 6 | 销售阶段=量房 | 未约定→约定量房；已约定未指派→指定设计师；否则→录入量房 |
| 7 | 销售阶段=跟进 | 写跟进 / 约定量房 |
| 8 | 兜底 | 首次联系 |

> App 代码里有一条明确的历史坑（FIX-008）：**设计阶段必须以"当前选中房屋已量完"为准，不能用客户级 `measureAt`** —— 多房屋客户只要约定过一次量房，客户级字段就永久有值，会把所有房屋误判为设计阶段。

### 2.4 App 缺失项（Web 需要补的）

- App 没有独立的「客户经营统计」页给设计师；统计能力在店长/BOSS 视角。
- App 没有"客户 360 按状态切换**展示内容**"，只有主行动切换。

## 3. Web 现状（`DesignerCustomersView.vue`，1287 行）

已有的：关键词搜索、阶段下拉筛选、客户池列表、客户 360（身份 + 预算/面积/设计师/下次跟进）、`nextAction()` 字符串映射、跟进时间线、写跟进表单、约定量房、改负责人/指派设计师、专用选择器。

缺的：
1. **没有统计**：没有阶段计数、没有生命周期分类、没有跟进提醒分类。
2. **列表不是卡片**：是纯文本按钮行，扫视效率低。
3. **360 与状态机没有真正联动**：`nextAction()` 只返回一句话，没有**原因 / 缺失条件 / 责任人 / 完成后状态**，也不随状态改变区块；`DEC-002` 要求的"双视图（客户主阶段 + 当前房屋执行阶段）"没有实现。
4. **存在自造阶段**：`customerDisplayStage()` 造了一个 `measured` 假阶段（`intended`/`following`/`pendingMeasure` + measured → 'measured'），属于前端自造状态机，与 `GAP-004` 的冻结结论冲突。
5. **无 `activePropertyId` 强制**：多房屋客户没有"必须先选房屋"的硬门禁（`BR-001` / `DEC-002`）。

## 4. 后端缺口（本轮唯一硬前置）

| 项 | 现状 | 结论 |
| --- | --- | --- |
| `customer/customer/page` | **已是设计师口径**（本人负责 ∪ 指派给我），但全量取回 + Java 过滤，无统计 | 可临时做列表；统计不合格 |
| `customer/customer/overview` | 字段齐全（stageCounts/metrics/riskLevel/riskReason/nextAction/idleDays），但 `requireBoss` + 全公司 + 全量实体 | **设计师不可用，且违反统计规则** |
| 设计师客户统计（分阶段计数 / 风险分类 / 跟进到期分类） | **不存在** | 需要新建 |
| 索引 | `idx_cust_customer_company_designer (com_id, designer_id, cust_id)` 已存在 | 新建聚合可直接用 |

### 4.1 建议：新增设计师口径聚合 Provider

```text
路由：customer/myCustomer/overview        （能力名：report）
入参：Employee（@User 注入）+ keyword/stage/sort/current/size（统计域允许内部字段）
数据范围：本人负责 ∪ 指派给我设计（复用现有 Designer 口径），服务端强制，不接受前端 comId/empId
返回（聚合/投影 SQL，标量 + 分页投影，禁止全量实体 + Java 循环）：
  asOf
  stageCounts[]      { key,label,count }          -- 一次 GROUP BY status
  riskCounts[]       { key,label,count }          -- 逾期/今日/3天内/7天内/沉睡
  metrics[]          { key,label,value,valueType }-- 在途客户 / 待量房 / 推进中报价 / 本月签约
  customers[]        { custId,name,telNo,community,area,budget,status,grade,
                       owner,designer,lastFollowAt,nextFollowAt,measureAt,
                       idleDays,riskLevel,riskReason,nextAction,
                       quoteAmount,signedAmount,projectId,projectName }
  current,size,total,hasMore
```

**并且必须先修正既有 `overview` 的口径问题**（`requireBoss` + 全量取数）：建议把 `requireBoss` 改为"按登录员工角色解析数据范围"，取数改为聚合 SQL；否则同一份客户经营数据会出现两套实现、两套口径。

### 4.2 好消息：派生规则已经存在，可以直接复用

核实结果 —— `Customer` 上的经营字段**都是 `@Transient` 只读投影**，由 `CustomerOverviewContext` 现算，规则如下（不应重写一套）：

| 派生字段 | 现有规则 |
| --- | --- |
| `idleDays` | 距 `max(lastFollowAt, lastVisitAt, measureAt, handedOffAt, createTime)` 的天数 |
| `quoteAmount` | 取最近报价金额 |
| `signedAmount` / `projectId` / `projectName` | 取最近合同（签约金额为 0 时回退当前金额） |
| `riskLevel` / `riskReason` / `nextAction` | `riskAndAction()`：已流失→"查看流失原因"；无负责人→High"未分配负责人"→"先分配负责人"；跟进逾期→High"跟进已逾期 N 天"→"立即处理逾期跟进"；待量房且未指派设计师→… |

**结论**：设计师 Provider 应当**复用 `riskAndAction()` / `enrich()` 的判定规则**（保证同一客户在 BOSS 视角与设计师视角给出同一个风险与主行动），只把「数据范围」和「计数方式」改成设计师口径 + 聚合 SQL。这样既满足统计规则，又不会产生第二套业务口径。

## 6. 状态 × 推荐操作 × 展示内容（核心：状态机联动）

规则：**主行动有且只有一个**；不满足前置条件时不显示动作，显示"缺失条件 + 责任人"。

| 客户阶段 | 展示重点区块 | 唯一主行动 | 前置不满足时 |
| --- | --- | --- | --- |
| 待首联 `intention` | 联系方式、来源、首次跟进记录 | **完成首次联系**（写跟进） | 无手机号 → 提示补全联系方式 |
| 跟进中 `following` | 跟进时间线、下次跟进、意向/预算 | **写跟进 / 约定量房** | 无房屋档案 → 先建房屋（不以客户地址替代） |
| 待量房 `pendingMeasure` | 房屋档案、量房时间、设计师指派 | 未约定→**约定量房**；已约定未指派→**指定设计师**；否则→**录入量房** | 未建房屋 → 阻断并说明 |
| 方案报价 `quote` | 当前房屋的量房结果、诉求、方案、**当前报价版本** | 报价在途→**查看报价流转**；否则→**生成报价 / 进入设计转化** | 当前房屋未量完 → 不得进入设计（FIX-008） |
| 已签约 `sign` | 合同状态（区分 Signed / Effective）、来源报价 | **查看合同流转 / 发起交接** | 非 Effective → 不显示"进入项目" |
| 施工中 `construction` | 项目阶段、我方职责节点 | **查看工地** | 无项目 → 显示数据异常待确认 |
| 已完工 `done` | 验收结论、交付留痕 | **查看工地**（只读） | — |
| 已流失 `lost` | 流失原因、历史跟进 | **无主行动**，只读；提供"重新激活"仅在有业务规则时 | 规则未命中 → 禁用并显示原因 |

> 依据：`SCN-014`「右侧显示唯一主行动、原因、责任人、缺失条件和完成后状态」；`DEC-002`「规则未命中或状态未映射时显示待业务确认，主操作禁用并保留查看原因」；`BR-001`「报价、合同和项目必须绑定明确客户与房屋」。

## 7. 落地范围与顺序

1. **先定后端**（第 4 节）：设计师口径聚合 Provider 是否新建；既有 `overview` 是否同批修正口径。
2. **再定页面归属**：「我的客户」（列表 + 360）与保留的「客户与设计」（设计/量房推进工作区）如何分工 —— 我的建议：
   - `我的客户` = 客户经营入口（统计 + 卡片列表 + 客户 360 + 状态驱动主行动）
   - `客户与设计` = 从 360 的主行动进入的**推进工作区**（房屋/量房/诉求/方案/报价），保留现有能力
3. 前端实现：菜单改名 → 新页面 → 状态机矩阵接入 → 四档分辨率与状态回归。
