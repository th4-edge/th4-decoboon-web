## 二、A 类 · 挡主链（直接影响角色能否闭环）——建议优先拍板

### A1. 主材选材的角色范围三方不一致（`GAP-WEB-019`）

**事实**：注册表 `pm.materialSelection.roles` 与前端路由 = `Designer / Boss / StoreManager / Finance`（**无 Pm**）；后端 `project/service/materialplans/update` = `Boss / Pm / Finance`（**无 Designer / 无 StoreManager**）；App 口径是**项目经理**负责材料状态。→ 结果是**设计师被当成选材主行动、进去保存会被拒；Pm 反而没有入口**（Pm S1 已登记 `ROLE_GUARD_DENIED`）。

**选项与后果**：

| 选项 | 后果 |
| --- | --- |
| ① 以 **Pm** 为责任角色：前端/注册表补 Pm，Designer 降为只读或代录 | 与 App 一致；但设计师「现场代录选材」的现有文案与主行动要改 |
| ② 以 **Designer** 为代录角色：后端放宽写权限 | 与 App 口径冲突；App 侧将来会出现同样的越权尝试 |
| ③ 三方收敛为一处事实源 + 加一致性门禁 | 治本；但要先定"谁负责"（仍需①或②之一） |

**影响角色**：Pm、Designer、StoreManager（选材入口）、Finance。

**✅ 已裁决（2026-10-11）**：范围 = **设计师 / 店长 / 企业负责人**（Pm 与 Finance 不在范围）。
落地：注册表与前端路由 roles 已改并复验（店长可进、财务被拒）；**后端 `materialplans/update` 需同步为同一集合**（见 `WEB-DECISIONS-20261011-LANDING.md` §六 交付项 1）。

### A2. 店长能否进入项目工作面（开工 / 阶段「本项不涉及」撤销）

**事实**：App 明确给店长 `act:startStage`（2026-09-23 用户裁决）、`act:stageNotApplicable`；但 Web `/pm` 路由 `meta.roles = ['Pm','Boss']` **不含店长** → 店长在 Web 上**无法开工、无法撤销阶段判定**。后端 `project/stage/update` 本身**允许** `Boss / Pm / StoreManager`。

**选项与后果**：

| 选项 | 后果 |
| --- | --- |
| ① 放行店长到 `/pm/workbench`（写动作由服务端裁剪） | 最小改动；但 `/pm` 页面文案与主行动是 Pm 视角，店长看到会觉得"这是别人的工作台" |
| ② 为店长建门店范围的项目工作面（`statistic/store/report` 类的入口下钻） | 体验最贴合店长；工作量中等 |
| ③ 明确店长不在 Web 开工（仅小程序） | 与 App 能力基线不一致，需在文档上写明理由 |

**影响**：StoreManager 主链（开工 → 履约 → 验收）在 Web 上断开。

**✅ 已裁决（2026-10-11）**：**店长能进项目工作面（开工 / 阶段撤销）**。
落地：`/pm` 组 roles 加 `StoreManager` + 工作台文案角色化；实测店长可见 **23 个本店项目**。

### A3. 项目成员指派入口的归属（`XA-016` 的店长侧）

**事实**：后端 `project/project/update` 的 `requireMemberEditor` = **Boss 或本门店店长**；但「项目成员」卡在 `/designer/projects`，店长被守卫拒 → **店长有这个权限却没有入口**。

**✅ 已裁决（2026-10-11）**：入口归属 **店长 / 企业负责人**。
落地：守卫白名单 + `/designer/projects` 及其 3 个子工作面的 `roles` 均加 `StoreManager`；实测店长可进入并「调整项目成员」。
**遗留（登记）**：入口仍在设计师页面上，语义不够干净 → 建议后续抽到店长自己的项目工作区（结构改动）。

### A4. 报价项目库公式口径（`GAP-WEB-017`）

**事实**：`catalog_item.formula` 全库为**中文口径**（`(人工单价) × 工程量`），进入设计分项后**不参与区域重算**（已按 `DEC-063` 降级并标「公式待修订」）；而设计分项体系用**专业变量**（`A/P/CP/WP`）。→ 同一报价存在**两套公式体系**，工程量自动化能力被削弱。

**✅ 已裁决（2026-10-11）**：取 **②**——明确「按固定工程量、不参与重算」并显式标注；**并删除不符合规则的数据**。

**已落地**：设计分项侧原有「公式待修订」标记；本轮**补上报价侧常驻说明**（此前报价侧无任何标注）。

**⛔「删除不符合规则的数据」未执行——需你指定范围**（只读盘点见 `WEB-DECISIONS-20261011-LANDING.md` §五）：

| 表 | 总量 | 中文口径 | 删除后果 |
| --- | --- | --- | --- |
| `catalog_item` | 680 | **680（100%）** | 删 = **清空企业报价项目库**（事实源）→ 不可执行 |
| `db_design_item` | 516 | **319** | 分布在 46 个方案，其中 **24 个已 Selected** → 删 = 破坏已选中方案与下游链路 |

三种可能的本意：① 把库内公式**改写**为专业变量（含 6 类明细表迁移）；② 只清理 `db_design_item` 的 Draft 部分（Selected/Ready 保留并标注）；③ 清理其它"脏数据"（请给判据）。

**影响**：Designer（选分项）、Finance（工程量口径）、Boss（成本）。

### A5. 客户接受报价的登记责任人与 Web 入口（`GAP-WEB-018`，含安全项）

**事实**：报价 `submitted` 后，**员工会话调用 `quote/update(Accepted)` 返回 200** → 存在「员工可代客户置位」的口径与安全风险；同时 Web 无客户侧入口（业主在小程序），设计师提交后**不知道该找谁**。

**✅ 已裁决（2026-10-11）**：登记责任人 = **设计师**。
落地（前端）：报价工作区在 `submitted` 状态新增「登记客户已接受」（设计师/Boss 可见，调既有 `quote/update(Accepted)`）；接棒与去向改为「下一责任方＝设计师（本页登记客户接受）」；实测按钮与确认框正常（**未执行写入，点取消**）。
**⛔ 待后端**：`quote/update` 当前仅拦 `Marketer`，**其他任意员工仍可置 Accepted** → 需收紧为**设计师**（交付项 2）。

**影响**：全角色（报价→合同链路）、合规。

## 五、D 类 · 原以为"可自办"，**逐条核实后已缩小**（2026-10-11 复核）

| 原列 D 项 | 核实结论 | 应归 |
| --- | --- | --- |
| 凭证 **P3 来源单号列宽/字号** | ❌ 不可（前端）：`VoucherPdfRenderer` 用 `PdfPTable(columns)` **等宽自动列**，PDF 列宽不由模板 mm 配置决定 → 折行只能改**后端渲染器** | **B 类**（后端渲染） |
