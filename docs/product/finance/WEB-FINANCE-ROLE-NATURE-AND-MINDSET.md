## 一、一句话定位

> **财务不生产业务事实，只核对、勾稽、归档、呈现别人的事实；并对任何可能被误当成「账」的数字负责。**

设计师在前端**创造**事实（方案、报价），项目经理在现场**推进**事实（施工、验收），财务在末端**接收**事实并把它变成可核对的资金与经营记录。因此财务页面的第一性判据不是「好不好用」，而是 **「账实是否相符、勾稽是否平衡、口径是否唯一、是否可追溯」**。

## 二、与 Designer / Pm 的本质差异（思维层，而非功能层）

| 维度 | Designer | Pm | **Finance** |
| --- | --- | --- | --- |
| 生产什么 | 创造事实（方案/报价） | 推进事实（施工/验收） | **不生产事实**，只核对与归档 |
| 时间视角 | 当下这一单 | 当前阶段 / 今天 | **期间**（账期 / 月份 / 结算期）+ 历史追溯 |
| 空间视角 | `Self`（本人客户） | `Self`（本人项目） | **`Company`**（跨项目、跨门店汇总） |
| 核心动作 | 生成、提交 | 推进、留证 | **核对、核销、更正、出凭证、结算** |
| 错误代价 | 报价错 → 重报 | 验收错 → 驳回整改 | **款项错 → 必须冲正/作废，不可静默修改** |
| 可逆性 | 高（版本化重报） | 中（驳回重验） | **低**（已发生的资金与凭证只能留痕更正） |
| 交互形态 | 单对象深工作区 | 项目队列 + 工作面 | **专业列表 + 批量 + 对账**（表格密度与键盘效率优先） |
| 首屏第一答案 | 这个客户下一步做什么 | 哪个项目要推进 | **今天的钱对不对**：该收/该付/未核销/待出凭证/利润是否完整 |
| 成功判据 | 方案被客户接受 | 阶段验收通过 | **账实相符、勾稽平衡、口径唯一、可追溯** |
| 页面对比对象 | 客户 / 房屋 | 项目 / 阶段 | **同一期间的汇总与明细**（自己跟自己、账跟实对） |

**一句话对比**：设计师页面回答「下一步做什么」，PM 页面回答「哪个项目要推进」，**财务页面回答「这笔钱的事实对不对、能不能入账、跟谁勾稽」**。

推论（对页面的直接约束）：

1. **财务页面天然是对账界面**：任何金额都要能被追问「从哪来、跟谁核销、是否有凭证」。
2. **财务页面天然是批量界面**：单笔处理是 App 的活；Web 的价值在批量筛选、批量核销、批量出凭证、键盘操作、多列对账。
3. **财务页面天然是只读优先**：大部分时间在「看 + 核对」，写入只发生在少数被严格门禁保护的节点上。

## 三、七条财务公理（判据 → 对页面/表单/凭证设计器的硬约束）

### 公理 1 · 事实优先于录入（来源单据原则）

- **判据**：能追溯到合同、采购、工资、材料计划的金额**必须走来源单据，禁止手工记账**（`DEC-016` L1）。
- **约束**：
  - 手工记账仅限**无来源事实**：`项目杂费 / 企业费用 / 其他收入 / 资金调拨`（`LedgerManualPurpose`）；
  - 手工录入表单必须显式标注「手工录入（无来源单据）」，与来源单据生成区分；
  - 列表必须能显示「来源单据」列（合同号/采购单/工资单），让财务一眼判断可追溯性。

### 公理 2 · 一笔业务只写一次事实（幂等 + 语义分层）

- **判据**：**应收 ≠ 收入、应付 ≠ 成本、付款 ≠ 成本**；收付款必须幂等（`DEC-016` L1、`G1 动作冻结`）。
- **约束**：
  - 术语纪律：页面只允许用 **应收 / 已收 / 应付 / 已付 / 资金收入 / 资金支出 / 现金流**；**禁止**出现「收入」「成本」「利润」指代资金流水（现金流 ≠ 利润）；
  - 提交必须防重复（幂等键由服务端裁决）；重复提交要给出「已处理，请勿重复提交」而不是静默成功；
  - 表单不得出现任何暗示「这笔计入会计收入」的文案。

### 公理 3 · 勾稽与核销（Write-off）

- **判据**：收款必须核销应收、付款必须核销应付；**金额不得超过待核销余额**。
- **约束**：
  - 核销表单**默认带出「待核销余额」**并把输入上限锁在待核销金额内；
  - 超额时给出**可恢复的阻断原因**（不是 disabled 了事），并指到正确的应收/应付单；
  - 动作完成后按 `reloadScopes` 回读「应收/应付 + 收款/付款 + 台账 + 项目账本」。

### 公理 4 · 完整度先于精度（禁止伪利润）

- **判据**：任一应计成本缺失 → `costComplete=false`、`grossProfit=null`、`grossMargin=null`，显示「成本未完整」；**禁止按 0 成本计算并展示伪利润**（`MET-002`、`DEC-016` L1）。
- **约束**：
  - 金额组件遇到 `null` 必须渲染「成本未完整」，**不得渲染 ¥0.00**；
  - KPI 卡、表格、项目账本、凭证、PDF、结算页**同一条规则**，不允许某处兜底；
  - 成本完整性要有独立可视状态（不是藏在明细里），因为它是「能不能相信这个利润」的前提。

### 公理 5 · 口径唯一（一概念一名、同名同公式）

- **判据**：同一业务含义只有一个标准名；**同名不同公式是财务级缺陷**（`DEC-018 / BR-016`）。
  - 已实测冲突：Web 财务工作台「本月回款」= `monthReceiptAmount`，App = `monthIncome`（`MET-005`）；麦鸿 2026-10 两处分别为 8,780 / 28,130。
- **约束**：
  - 页面出现的**每一个金额**都必须能指到 `MET-*` 口径；
  - 同名指标跨端必须同公式；发现不一致**先停手登记 `GAP`，不得由前端选一个"看起来对"的**；
  - 按 `DEC-018` 要求，产品内必须**可查看口径说明**（来源、公式、时间、范围、缺失值）。

### 公理 6 · 单据化与凭证归档（不可变、不回溯）

- **判据**：**凭证不改变款项事实**；同笔重打**同号**；发布后版本**不可变**；模板修改**不回溯**历史凭证（`BR-006`、`DEC-020`）。
- **约束**：
  - 凭证设计器必须有 **草稿 → 发布（生成不可变版本）** 的门禁；已发布版本只读；
  - 打印/重打是**只读动作**，不得顺带修改金额；
  - 合并出证只允许**同一对方 + 同一项目 + 同款项类型**；
  - 预览必须支持**样例数据 / 真实数据脱敏**两种模式。

### 公理 7 · 边界自觉（不当会计）

- **判据**：装得清**管项目和钱，不管税和账**；**原始/业务凭证 ≠ 法定记账凭证**；任何数字不得被误当成会计、税务或审计依据（`DEC-016` 红线、`GAP-022`）。
- **约束**：
  - 页面**禁止**出现会计语义命名：会计科目、借贷分录、过账、报表、记账凭证字号；
  - 凭证类型只允许**业务/原始凭证**：收款、付款、工资、结算、报销、退款、质保金、资金调整；
  - 对外与页面文案不得暗示已支持法定总账 / 税务申报。

## 四、对「表单」与「凭证设计器」的专项约束（本次重点）

### 4.1 财务表单的六条硬约束

| # | 约束 | 依据 |
| --- | --- | --- |
| 1 | **来源单据区**必须存在：显示合同/采购/工资/材料计划来源；手工录入要显式标注 | 公理 1 |
| 2 | **金额只读**：金额由服务端给，前端只格式化；表单内不得出现自算金额 | `WEB-开发规范`、公理 2 |
| 3 | **核销余额与上限**：默认带出待核销余额，超限阻断且可恢复 | 公理 3 |
| 4 | **幂等提交**：防重复；重复提交给明确提示而非静默成功 | 公理 2 |
| 5 | **五段分区 + 结果确认**：按 `WEB-业务选择器与表单设计规范.md`，单据化动作还要过 `T17` | 表单总规范 |
| 6 | **回读与部分确认**：成功后按 `reloadScopes` 回读；失败显示「部分数据暂不可确认」 | `WORKSPACE` 规范 |

### 4.2 凭证设计器的四类用户与设计判据

| 用户 | 诉求 | 设计答案 |
| --- | --- | --- |
| 不懂版式的财务 | 「给我能用的凭证」 | **平台基线兜底**：无企业模板时回退平台基础模板，不能出现「无法打印」 |
| 要套打的财务 | 「按我们公司的格式」 | 复制平台模板 → 企业草稿 → 编辑 → **发布为不可变版本** |
| 要品牌化的老板 | 「带上我们的抬头/签章位」 | 字段显示名、联次、签章位、盖章位、备注；平台模板只读 |
| 会计/外部会计 | 「导出给会计用」 | 导出与打印**不改事实**；不承诺记账凭证能力（`GAP-022`） |

**凭证设计器必须有的三道门禁**（当前实现已具备部分，需逐项核对）：

1. **必填字段不可删除**（发布前校验：必填、来源绑定、金额规则、分页、PDF 渲染）；
2. **版本门禁**：草稿可改、已发布不可改；历史版本只读；模板修改不回溯凭证；
3. **渲染一致性**：预览 = 真实渲染（PDF），打印分页可视化，样例/脱敏双模式。

## 六、本次「财务思维」落地的三条作业纪律

1. **先问口径，再问交互**：任何财务页面的改动，先确认它要展示/写入的金额属于哪个 `MET-*` 口径、来源单据是什么、缺失时怎么表示；口径不清就停手登记 `GAP`。
2. **对账优先于美化**：设计财务页面时，第一优先级是「能不能对上」——来源、勾稽、余额、期间、凭证号；排版与动效排在后面。
3. **写入必须留痕且不可覆盖**：财务的写操作只有两种结局——**成功（事实加一笔）** 或 **阻断（给原因）**；不存在「悄悄改掉一个金额」。更正只能通过更正/作废/冲正，不能原地覆盖。
