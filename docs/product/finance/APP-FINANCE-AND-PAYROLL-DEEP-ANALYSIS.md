# 小程序 App 财务工作台与员工薪酬 · 深度分析与 App→Web 对照

> 状态：`S0 事实认读 + 深度分析（2026-10-11）`
> 定位：小程序是业务基准（`WEB-建设核心思路` 四条公理之一「App 为准」）。本文在**动手构建/优化 Web 财务页面前**，先把 App 的财务工作台与员工薪酬读透，提炼产品与用户思维，再据以判断 Web 该补什么、不该抄什么。
> 代码基准：`th4-decoboon-app` @ 工作区当前版本（`src/pages/finance/index.vue`、`src/subpackages/finance/*`、`src/subpackages/payroll/*`、`src/domains/finance|payroll/*`、`src/roles/catalog.ts`、`src/roles/permission.ts`）。
> 业务依据：`DEC-016`（边界三层）、`DEC-018 / BR-016`（口径一致）、`BR-015`（员工工资与提成）、`DEC-046 / BR-038`（工资单确认前置）、`MET-005 / MET-006 / MET-007`、`GAP-022 / GAP-023 / GAP-031 / GAP-033`。
> 本文只做**事实认读与差异分析**，不新增、不修改任何金额/成本/利润/权限口径。

## 一、结论摘要

1. **App 的财务工作台首答是「账上还有多少钱」，不是「赚了多少」。** Hero 第一位是**当前账面现金余额**，并在期初未承接时明确提示「余额为过程参考」。
2. **App 主动解释口径**：内置「财务数字怎么算？」区块，专门区分 `累计收款 / 本月回款 / 资金收入 / 已收金额 / 现金流` 五个最容易混的钱，且口径取自**后端指标字典** `statistic/metric/dictionary`（`DEC-018` 要求「产品内可查」的落地形态）。**Web 完全没有这个能力。**
3. **App 把「为什么不能做 + 我该先做什么」当成一等功能**：工资单确认前逐项校验，每条阻断都带**可执行的下一步**（检查薪酬方案生效期 / 去确认考勤 / 处理实发为负项）；而 Web 只是直接调接口、失败才弹错误。
4. **App 用一条资金闭环链替代四个孤立数字**：应收 → 已收 → 应付 → 已付。
5. **Web 财务工作台的整体视角更偏「老板经营结果」**（Hero 是项目利润），**App 更偏「财务资金安全」**（Hero 是现金余额）。两者不是对错，而是**首页第一答案的取舍**——财务角色应以现金与勾稽为第一答案，经营结果应有独立位置。
6. **员工薪酬是 App 财务的第二条主线**（14 个页面 / 20+ Provider），Web 目前只覆盖其中约 1/3，且**缺最关键的「薪酬工作台」与「工资单详情（阻断清单）」**。

## 二、App 财务工作台解剖（`src/pages/finance/index.vue`，329 行）

页面自上而下 8 段，每段都有明确职责：

| # | 区块 | 内容 | 设计意图（读出来的） |
| --- | --- | --- | --- |
| 1 | **Hero · 账面现金余额** | `cashBalance` 大字 + 期初未承接提示「期初未承接，余额为过程参考」 | **财务第一性答案是钱**，不是利润；且**不确定的数字要自曝不确定** |
| 2 | Hero 栅格 | 项目合同额 / 已收÷应收（回款率 %）/ 经营项目 active÷total | 三个"盘子有多大、收回多少、在跑几个" |
| 3 | **风险待办 · 三 tab** | 逾期催收 / 临期应收 / 待付，卡片直接跳对应应收/应付 | 入站队列按**风险类型**分类，而不是按对象类型 |
| 4 | 4 个 KPI | 待收工程款（副：逾期）/ 本月回款（副：累计收款）/ 待付账款（副：合同应付）/ 本月支出（副：现金流） | **每个数都带一个"容易混的另一个数"作副标题**——用对比消除误读 |
| 5 | **「财务数字怎么算？」** | 5 条口径释义 + 后端指标字典渲染 | 财务级能力：**口径必须在产品内可查**（`DEC-018`） |
| 6 | **资金闭环图** | 应收 → 已收 → 应付 → 已付 四节点链 | 财务是**勾稽思维**：一条链看钱怎么流，比四个孤立数字好 |
| 7 | **财务快捷入口 · 四组** | ①资金收付（登记收款/客户退款/登记付款/手工记账）②往来管理（应收计划/应付账款/工人工资/供应商往来）③**员工薪酬（员工薪酬/员工工资/员工提成）**④账务核算（资金台账/项目账本/收付凭证） | 分组顺序 = **业务闭环顺序**（先登记事实 → 再管计划 → 再核算），不是菜单罗列 |
| 8 | 最近流水 + 全部台账 | 5 条卡片流 | 从"数字"下钻到"凭证级事实" |

**权限与只读**：`can(session.role,'edit:finance')` 控制写入口；无权限时按钮**置灰并按需 toast「当前账号仅可查看财务数据」**——只锁写、不锁读。
**性能取舍**：内存会话缓存（不写本地存储），下拉刷新强制回源。

### 3.2 状态机（`src/domains/payroll/meta.ts`，App 是唯一事实源）

| 对象 | 状态 |
| --- | --- |
| 薪酬方案 | 草稿 / 生效 / 失效 |
| 考勤 | 草稿 / 待确认 / 已确认 / 已入工资单 / 申诉中 / 已退回 |
| 提成 | 待计提 / 已计提 / 待发放 / 发放中 / 已发放 / 已关闭 / 已冲减 |
| 工资单 | 草稿 / 待确认 / 已确认 / 部分发放 / 已发放 / 已关闭 / 已作废 |
| 工资项 | 草稿 / 已确认 / 已发放 / 已作废 |
| 工资条 | 待发放 / 已发布 / 已作废 |

> **"提成"与"工资"是两条独立的状态流**：提成从"待计提 → 已计提 → 待发放 → 发放中 → 已发放"，工资单从"草稿 → 待确认 → 已确认 → 部分发放 → 已发放"。这一点决定了 UI 不能把它们合成一张表。

### 3.3 工资单确认的硬前置与「可执行下一步」（**本次最重要发现**）

依据 `DEC-046 / BR-038`，`sheet-detail.vue` 在**点击确认之前**就逐项校验并渲染阻断清单：

| 阻断项 | 判定 | 给出的下一步 |
| --- | --- | --- |
| 无工资项 | `items.isEmpty` | 「检查薪酬方案生效期，或重新生成工资单草稿」+ **跳转重建** |
| 考勤未确认 | `!attendanceComplete` | 「确认全部员工月度考勤后才能确认工资单」+ **跳转考勤** |
| 实发为负 | 任一 `netAmount < 0` | 「需人工处理后才能确认」+ **跳转工资项** |
| 提成未结清 | 有未结清提成 | **不阻断**，且明确提示「提成与工资独立结算、独立发放，**不影响本次工资确认**」 |

确认后的业务效果（页面文案明示）：**「按实发生成员工工资应付并计入项目/企业成本；工资条在发放完成后才对员工可见」**。

## 四、从 App 提炼的产品哲学（财务角色的「用户思维」五条）

1. **首答是「钱在哪」**：财务每天打开的第一个问题不是"赚了多少"，而是"账上多少、该收该付多少"。首页第一答案放错位置，后面的信息再准也是跑偏。
2. **不确定要自曝**：「期初未承接，余额为过程参考」——财务最怕把过程参考当成真账。**数字的置信度必须和数据一起显示**。
3. **口径要主动解释，而不是等人问**：「财务数字怎么算？」把五个最易混的钱讲清，且与后端指标字典同源。**同名不同公式 = 财务级缺陷**（`MET-005` 已实测 Web/App 不一致）。
4. **不能做的时候，告诉他先做什么**：阻断不是终点，阻断要带**可执行的下一步**；能独立结算的（提成 vs 工资）要明确说互不影响，避免财务误停整条发薪流程。
5. **可见性有明确时点**：工资条**发放完成后**才对员工可见；只读角色只锁写入口，读全放开。

## 五、App → Web 对照矩阵

### 5.1 财务工作台

| 能力 | App | Web 现状 | 判断 |
| --- | --- | --- | --- |
| 首页主视觉 | **账面现金余额**（+期初未承接提示） | 「项目经营结果」= 利润（成本不完整时显示「成本未完整」） | **取舍不同**：Web 是老板视角。财务角色应以资金为首答，经营结果另置 |
| 现金余额位置 | Hero 第一位 | 4 个 KPI 中的**第 4 个** | ❌ 财务角色下最重要的钱被降级 |
| **口径释义** | ✅ 5 条，取后端指标字典 | ❌ 无 | ❌ `DEC-018` 要求产品内可查，Web 缺失 |
| **资金闭环图** | ✅ 应收→已收→应付→已付 | ❌ 无 | ❌ 缺勾稽可视化 |
| 风险待办 | 三 tab（逾期/临期/待付） | 两 PanelCard（逾期催收含临期 / 优先付款） | ✅ Web 双栏更适合宽屏，可保留 |
| KPI 组 | 待收/本月回款/待付/本月支出（各带副数） | 待收/本月回款/待付（副：其中工资）/本月现金流 | ⚠️ Web 多「其中工资」（有用）；但缺 App 的「每个数带对照数」纪律 |
| 快捷入口 | 四组，含**员工薪酬组** | 仅「登记资金事实」下拉 4 个动作 | ❌ 缺分组导航；**员工薪酬无入口** |
| 只读角色 | 写入口置灰 + toast | 「本店财务只读」按钮 | ✅ 等价 |
| 最近流水 | 卡片流 | 表格 | ✅ Web 更优（宽屏密度） |

## 七、下一步建议（以产品思维打磨，不追速度）

**第一批（纯前端可做，不依赖裁决，价值最高）**

1. **工资单确认阻断清单**（缺口 1）——把 App 的"为什么不能确认 + 我该先做什么"完整搬到 Web；
2. **薪酬工作台**（缺口 3）——`payroll/workbench/report` 已有，补一屏进度盘；
3. **口径释义区块**（缺口 2）——先确认 Web 侧指标字典 Provider，再补。

**第二批（需一次产品裁决，避免我自己定口径）**

4. 财务首页信息层级：**现金余额是否为第一答案**（本文 §4 原则 1 的建议）；
5. 我的工资条 / 门店薪酬是否在 Web 承载（缺口 10）。

**第三批**

6. 资金闭环可视化、财务快捷入口分组（缺口 4–6）；
7. 考勤录入、提成发放批次、删除类动作（缺口 7–9）。

> 打磨纪律：本角色的每一个页面，先回答**「财务此刻要判断什么」**，再决定放什么数字；**不确定的数字必须显示确定性**；**阻断必须带下一步**。
