# Web 业务选择器与单据化表单设计方法

> 执行真源：`docs/standards/WEB-业务选择器与表单设计规范.md`。本文保留设计演进和方法说明。


> 目的：整理本轮从“项目选择器”到“单据化表单”的演进，形成 Web 后续业务选择与复杂录入场景的统一设计理解。
> 上位依据：`DEC-021`、`DEC-022`、`DEC-023`、`DEC-024`、`DEC-025`、`DEC-026`、`DEC-028`、`BR-019`、`BR-020`、`BR-021`、`BR-022`、`BR-023`、`BR-024`、`BR-026`。
> 本文件是 Web 实现方法，不替代业务智能体事实源。

---

## 1. 本轮演进过程

### 阶段一：普通下拉

业务对象直接绑定到 `el-select`，页面先加载列表。

问题：

- 用户必须先点击才能看到数据。
- 项目、客户不会因为业务增长而保持有限。
- 下拉难以表达状态、负责人、金额、阶段等业务上下文。
- 长名称容易影响布局。

### 阶段二：统一业务对象选择器

把项目、客户、工人等都抽象成同一个通用选择器。

问题：

- 不同业务对象被压成同一种列表结构。
- 账务分类的树形结构、项目状态分组、报价分项品牌/规格等业务特征丢失。
- 统一变成了“结构统一”，而不是“使用语义统一”。

纠正：统一选择机制，不统一业务结构。

### 阶段三：对象专用选择器 + 统一使用机制

项目选择器开始体现：

- 项目状态分组；
- 正常/接管来源；
- 门店、设计师、项目经理；
- 常用项目；
- 项目卡片与业务标签。

同时保留统一的选择、清除、分页、失败恢复和服务端校验机制。

### 阶段四：引导式项目选择器

项目选择器从“搜索 + 列表”升级为：

```text
左侧责任维度 + 顶部经营维度 + 主区项目卡片 + 精细搜索
```

核心变化：

- 打开即展示数据。
- 搜索退居辅助。
- 项目卡片提供金额、状态、设计负责人、施工负责人、阶段等选择依据。
- 已选项目使用全宽摘要卡，不再挤压左右表单。

### 阶段五：表单分区

表单从普通控件网格升级为：

```text
业务对象选择区
-> 短字段输入区
-> 结果预览/确认区
-> 主行动区
```

核心变化：

- 项目、客户、应收、应付等业务对象占整行。
- 金额、日期、账户等短字段可以并排。
- 提交前必须让用户确认系统将产生什么结果。

### 阶段六：结果对象驱动的单据化表单

对于具有稳定单据形态的业务动作，进一步取消“字段表单 + 结果预览”的重复结构。

最终业务对象直接作为可编辑主界面。

应收节点就是当前样板：

```text
项目上下文卡
+ 可编辑应收节点单据
+ 项目资金参考侧栏
+ 创建应收节点
```

### 阶段七：区域视觉与控件密度纠偏

颜色不是逐项标注字段，而是：

- 整个表单区域使用柔和渐变；
- 输入控件保持中性；
- 状态标签保留状态色；
- 右侧参考区保持自己的区域背景。

控件密度：

- 普通单选、多选使用传统 select / multi-select；
- 应收类型等单据核心类型放在节点名称下方，使用紧凑 checkbox 视觉组，但保持单值语义；
- 不为普通选项使用大尺寸选择卡。

## 2. 我的设计理解

### 2.1 一致性是语义一致，不是布局复制

必须统一：

- 业务字段含义；
- 选择、清除和回传结果；
- 状态和错误表达；
- 权限和数据范围；
- 提交和服务端复核。

可以不同：

- 控件的视觉结构；
- 选择器的布局；
- App/Web 的交互方式；
- 卡片、树、级联、表格等表达形态。

### 2.2 选择器必须先帮助用户判断，再帮助用户搜索

搜索是最后的精确定位手段，不是首屏唯一入口。

好的业务选择器应首先回答：

- 这个项目属于谁？
- 当前是什么状态？
- 来源是什么？
- 金额和负责人是谁？
- 用户应该优先看什么？

### 2.3 表单就是业务结果

应收节点不是“输入一堆字段”。

应收节点就是一张应收收据/节点单据：

- 项目是上下文；
- 节点类型、名称、阶段、金额、日期构成单据正文；
- 项目资金参考帮助用户确认；
- 保存就是发行这张节点单据。

### 2.4 颜色表达区域，不表达每个字段

正确：

- 左侧单据区域整体渐变；
- 右侧资金参考区域整体渐变；
- 状态用标签表达；
- 普通输入项中性。

错误：

- 金额一个颜色；
- 日期一个颜色；
- 每个指标卡一套颜色；
- 页面像多个独立告警块拼在一起。

### 2.5 控件密度服从任务

- 少量且关键的类型选择：节点名称下方紧凑 checkbox。
- 普通类型、账户、用途：传统 select。
- 多选：传统 multi-select。
- 远程业务对象：专用选择器。
- 大对象选择：先进入专用选择面板，选中后显示全宽摘要卡。

## 3. 推荐的选择与表单决策树

```text
是否是后端固定枚举？
├─ 是：普通 select / multi-select
└─ 否
   ├─ 是否是可配置字典/树？
   │  ├─ 是：专用字典/树选择器
   │  └─ 否：业务对象
   │     ├─ 是否需要搜索、分页、权限过滤？
   │     │  ├─ 是：专用业务对象选择器
   │     │  └─ 否：可直接显示的少量选项
   │     └─ 选中后是否影响上下文？
   │        └─ 是：显示全宽上下文摘要卡
```

## 4. 项目选择器最终设计

### 未打开选择器

显示当前选择或者“选择所属项目”。

### 打开选择器

- 顶部：项目状态、正常/接管来源。
- 左侧：门店、设计师、项目经理。
- 主区：项目卡片。
- 辅助：名称/编号/客户/地址精细搜索。

### 已选项目卡

- 占满容器宽度。
- 左侧：状态、来源、项目名称、编号、客户地址。
- 右侧：合同金额、设计负责人、施工负责人、当前阶段。
- 操作：更换、清除。
- 项目名称可换行，不挤压右侧。

### 外部标题

项目上下文卡已经具备语义，不再重复显示“所属项目”等外部标签。

## 5. 客户与房屋选择器最终设计

### 客户选择器

- 打开即展示客户卡片，搜索只作精细补充。
- 左侧按客户阶段组织，主区展示姓名、状态、电话、小区/地址、等级、负责人和最近跟进。
- 客户选择只回传客户，不自动替用户选择房屋。

### 房屋选择器

- 必须绑定当前客户；没有客户上下文时不可打开。
- 展示小区/楼栋/房号、面积、户型、房屋编号、状态和最近量房。
- 一客户多房屋时必须显式选择，禁止用第一套房屋兜底。
- 切换客户后，当前房屋、量房结论和方案必须清空或重新校验归属。

### 表单中的使用

- 客户和房屋上下文采用只读上下文条，不重复堆放输入控件。
- 量房、方案、设计诉求等表单先确认客户/房屋，再进入本对象字段。
- 普通枚举仍使用传统 select；只有业务对象使用上述专用选择器。

## 6. 应收节点单据最终设计

### 结构

```text
项目上下文卡
├─ 应收节点单据
│  ├─ 节点名称
│  ├─ 应收类型（紧凑 checkbox，单值）
│  ├─ 合同阶段 / 触发条件
│  ├─ 应收金额
│  ├─ 到期日
│  ├─ 发票
│  └─ 说明
└─ 项目资金参考
   ├─ 合同金额
   ├─ 累计已收
   ├─ 待收金额
   └─ 逾期金额
```

### 设计原则

- 项目卡没有外部重复标签。
- 金额与日期不单独着色，保持中性，放在统一的单据区域中。
- 应收类型位于节点名称下方。
- 右侧资金参考使用独立区域背景。
- 不再重复显示“应收节点预览”。
- 所有正式状态和金额以服务端为准。

---

## 7. 禁止事项

- 从后端表结构直接生成下拉。
- 所有业务对象共用一个通用列表选择器。
- 打开后只有搜索框或空白下拉。
- 用大块卡片承载普通枚举。
- 逐字段使用不同颜色。
- 在表单和预览区重复展示相同事实。
- 因长名称破坏表单栅格。
- 前端自行计算正式金额、成本和利润。
